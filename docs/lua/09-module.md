追加、拒绝空标题、把一条印成一行，这些函数已经各写过一遍。若它们散落在脚本顶层，下一个例子还会再抄。模块在 Lua 里不是一种新的结构，它就是一张表，字段是函数。表可以是局部的。局部表不会跑进全局环境，也不会假装自己来自另一份文件。这一章把待办的动作放进名为 todo 的局部表。同一份源码里，谁能看见 todo，谁就能调用。文件之外没有人能 require 到它，因为根本没有第二份文件。

require 的设计是按名字查找，加载那份文件，执行它，并记住返回的表。查找能避免同一模块执行两次，返回的表成为别人共享的那一份。这在多文件程序里是对的。在这个抽屉里，查找会离开眼前的脚本，去磁盘上找 todo.lua 一类的路径。那些路径不存在，加载失败，终端上是查找错误，不是待办的条数。失败不能当例子跑，否则每一轮核对都在确认「文件确实不在」，和买笔无关。所以下面这一块标成只读。读它，是为了记住边界，不是为了把注释里的调用放进下一块。

```lua norun title="另一份文件不在这次进程里"
-- require("todo") 会按名字去找别的文件。
-- 这一课只有眼前这一份源码，不要加载它。
```

本地表的写法可以很直。先 `local todo = {}`，再 `function todo.add(...)`。后一种语法等于给表的字段赋值一个函数。字段名就是调用时写在点号后面的那个词。三个动作够这一章用：add 往序列末尾放标题，count 交还长度，line 把完成标记和标题拼成一行。它们都放在同一张表上，因为它们是一组合同，不是三个偶然同名的全局函数。合同放在一起，改空标题的规则时不会漏掉其中一份拷贝。

```lua run expect="3" title="本地表上的追加和计数"
local todo = {}
function todo.add(list, title)
  list[#list + 1] = title
  return #list
end
function todo.count(list)
  return #list
end
local items = {}
todo.add(items, "买笔")
todo.add(items, "交表")
todo.add(items, "浇花")
print(todo.count(items))
```

count 信任 `#`。调用方若挖了洞，计数会失准，这是表那一章的合同，模块没有魔法可以回避。把清单放在模块外面传进来，而不是藏进闭包，是这一章的取舍。外面能看见条目，调试时可以打印第一条。外面也能破坏序列。闭包那一章选择挡住表，模块这一章选择把表留给调用方，模块只提供动作。两种都是表：一个是数据，一个是函数的集合。不要把函数表和清单表混成一张，否则 `#` 会看见混进来的键，或者 ipairs 停在一个函数上。数据归 items，动作归 todo。

空标题的拒绝可以藏在表外面的局部函数里。那个函数不放进 todo，调用方就点不出来。这是模块的隐私，靠词法范围，不靠关键字 private。隐私的好处是空串的定义只有一处。坏处是测试不能直接点那个内部函数，只能通过 add 的结果观察：空串应当被拒绝，回信应当被记下。观察结果比观察内部名字更接近周衡的用法。他不会调用一个叫 nonempty 的函数，他只会看见纸上有没有新的一行。

```lua run expect="拒绝" title="私有判断不放进表"
local todo = {}
local function nonempty(title)
  return type(title) == "string" and title ~= ""
end
function todo.add(list, title)
  if not nonempty(title) then
    return false
  end
  list[#list + 1] = title
  return true
end
local items = {}
local kept = todo.add(items, "回信")
local dropped = todo.add(items, "")
if kept and not dropped then
  print("拒绝")
else
  print("没拦住")
end
print(#items)
```

第二行是 1。空串没有占用一格。返回 false 而不是 error，是这一块的选择：调用方用布尔决定要不要数，脚本不必进入 pcall。上一章的 error 适合「空白是编程错误，必须看见消息」。这一章的 false 适合「空白是输入里可能出现的一行，拒绝即可」。两种失败不要混用。若 add 有时抛错、有时返回 false，调用方每一处都得两套接法。模块的合同应当挑一种，并在同一张表的所有字段上保持。

成行是第三种动作。未完成用一个空格当标记，完成用 x。标记和标题之间再放一个空格，于是未完成的买笔看起来像行首有空白。打印时空白容易被忽略，期望锁定买笔这个词，同时我们在文字里说明行首有标记。若希望空白也稳定可见，可以把标记换成「未」和「完」两个汉字，完全避开空格。汉字标记更适合这张纸。下面改用汉字，避免期望去匹配一个容易被看丢的空格。

```lua run expect="未 买笔" title="成行也是表上的函数"
local todo = {}
function todo.line(item)
  local mark = item.done and "完" or "未"
  return mark .. " " .. item.title
end
local item = { title = "买笔", done = false }
print(todo.line(item))
```

done 为 false 时走「未」。若 done 缺失而是 nil，同样走「未」。挂了 __index 的条目若默认 done 为 false，line 看到的也是未。模块不必知道默认来自元表，它只读字段。这是表与表之间的松耦合：todo 不调用 setmetatable，条目可以是裸表。松耦合的代价是 line 不会替你补默认主人。主人若要印在行里，调用方先保证字段在，或者自己挂元表再交给 line。

真实程序里，这份 todo 表会被 return，另一文件 require 之后拿到同一张。返回值在单独运行的脚本里不会自动打印，所以这一课即使 return todo，终端上仍要靠 print 才有字。我们连 return 都不依赖，因为没有另一个文件来接收。把模块留在局部，是迁就单文件运行时的做法，也是一种可读的做法：打开这一块就能看见全部函数，不用跳到别的路径。代价是不能在两块可运行示例之间共享 todo 的定义。每一块都要把要用的函数再写一遍。重复换来每块可单独抄走。这和开篇的新进程是同一笔账。

不要把模块放进全局变量 todo 来「方便下一块」。下一块是另一个进程，全局留不下来。留在当前进程里，却会让一块脚本后半部分不小心改到前半部分的字段。局部名字在块结束时就不可见了，但我们的一块就是整个脚本，局部和全局的差别主要体现在：局部不会撞上语言自己的名字，也不会被一个拼写错误的赋值悄悄创建成第二个全局。拼写错误的全局会和真正的 todo 并存，你调用的仍是旧的，新的空表没人理，调试时非常安静。

函数表也可以挂元表，缺的动作去另一张默认动作表里找。待办的动作就三个，挂 __index 会让人不知道 line 到底写在哪。动作少的时候，显式字段比继承清楚。动作多到要分层，再考虑元表。过早的模块继承会把「未 买笔」的来源藏进两张表，改一个默认函数，所有没覆盖的模块一起变，和默认优先级的连带是同一类意外。

同一张 todo 上的函数可以通过 self 或者显式的 todo 互相调用。显式写成 todo.count(list) 在 add 里面，读起来能看见依赖。用 self 就得用冒号定义和冒号调用，漏一个冒号，self 会变成第一条待办甚至变成一个字符串，随后的字段访问直接报错。报错能看见，但信息是对 nil 或字符串取索引，不是「你忘了冒号」。四行模块用点号和显式表名，啰嗦，啰嗦换来不用解释冒号。等模块长到很多方法都要带上自己，再考虑冒号。现在三个函数，点号足够。

把 todo 返回给调用方，是多文件程序的接口。单文件脚本返回值会被解释器忽略，不会打印。若你既 return 又希望看见条数，仍然要 print。不要用返回值代替打印，抽屉上的核对读的是标准输出，不是脚本的返回值。返回值留给真正的 require。require 在这一课里是只读的，所以返回也可以不写。不写的好处是读者不会去找接收返回值的那一份文件。那份文件不存在，找它会把注意力从本地表上挪走。

模块里的函数闭包可以共享一张私有的默认优先级。那个数字不放在 todo 字段上，外面改不到。条目自己的优先级仍由调用方放在记录里。私有默认只在调用方没给的时候使用。使用时要区分 nil 和 0：0 可能是合法优先级，不该被默认值换掉。判断用 == nil，再取私有的那个数。这样模块既有隐藏状态，又不把隐藏状态做成第二张谁都能改的全局清单。隐藏状态越多，测试越只能从输出推断。三个函数以内，隐藏一张默认数字还可以。再多就应当交回给调用方，让状态留在 items 里。

文档块之间不能共享这个模块。你在一块里写好的 todo.add，下一块必须再写。这看起来像没有模块的好处。好处发生在一块内部：循环、校验、成行都点同一个表，而不是三份互相漂移的局部函数。一块内部的复用已经值得一张表。跨块的复用被进程边界挡住了。要跨块，就得把源码复制过去，复制是可见的。可见的复制比一个会过期的隐藏预加载更适合这门课。

名字 todo 可以换成别的局部名字，字段也可以用中文键，但中文键要用括号赋值，调用时也要括号，点号只接受标识符。标识符用英文，标题用中文，两种文字分工，读代码时能分开「这是机制」和「这是纸上的句子」。全部用中文键能跑，例子会变长，错误信息里的键也不如英文字段稳定。稳定的字段名方便期望只锁定买笔这种数据，而不是锁定函数名。函数名不进输出，数据进输出。

若 add 写在局部函数里再赋给 todo.add，效果和 function todo.add 相同。先定义局部函数的好处是可以递归，或者在定义时还不能看见整张表。追加不需要递归。直接写 function todo.add 更短，读的人知道这个函数的家在表上。家在表上，就不要再留一个全局 add。全局 add 会遮住你的眼睛：调用 add 时用的是全局，改的却是 todo.add，两边不一致。不一致时条数不变，你以为表坏了，其实调用没走到表上的那个函数。

## 小结

模块在这里是一张局部表，add、count、line 是它的字段。require 另一份文件只出现在只读块里，因为抽屉没有那份文件。私有的空标题判断留在表外，调用方用返回值判断拒绝还是记下。清单和函数表分开，长度才不会被函数键干扰。每一块仍要自己把用到的函数写出来，下一块不会继承这一张 todo。
