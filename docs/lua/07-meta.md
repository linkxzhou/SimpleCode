每一条待办都有标题，完成与否却常常省略。周衡的纸上，没画圈就是未完成，他不会在每一行再写一遍「未完成」。表没有这个习惯。键不存在时，取值得到 nil。nil 在条件里和 false 一样关掉分支，所以碰巧能把「没写 done」印成未完成。碰巧不可靠：你无法把「没写」交给元表去补一个默认的主人，因为查找已经结束在 nil，不会再问别处。元表是一条附加的规则：某些事件发生时，去调用你提供的行为。这一章只用一种事件，__index。它在键缺失时触发。我们不写运算重载，不写 __newindex，也不把待办装成另一套语法。

setmetatable 把一张元表挂到待办上，元表里的 __index 指着默认表。以后读 item.owner，若 item 自己没有 owner，就到默认表里取。默认表里有 owner = "周衡"，于是读到周衡。rawget(item, "owner") 不走元表，仍然是 nil。这两个结果要同时看，才知道周衡是借来的，不是写在这一条上的。只打印 item.owner，会以为构造函数已经抄了一份。

```lua run expect="表里没有主人" title="缺键才去默认表"
local defaults = { done = false, owner = "周衡" }
local item = setmetatable({ title = "买笔" }, { __index = defaults })
print(item.owner)
if rawget(item, "owner") == nil then
  print("表里没有主人")
else
  print("写在自己身上")
end
```

自己的键优先。浇花若明确写了 done = true，即使默认是 false，读到的仍是 true。__index 根本不会被问到，因为缺失才问。这让「这一条特例」比「全体默认」更优先，符合纸面：画了圈的那一行不要被默认的空圈盖掉。下面打印自己的完成。

```lua run expect="自己的完成" title="已有的键不询问默认"
local defaults = { done = false }
local item = setmetatable({ title = "浇花", done = true }, { __index = defaults })
if item.done then
  print("自己的完成")
else
  print("落到默认")
end
```

写入默认是普通赋值。这一章没有 __newindex，所以 item.owner = "阿宁" 会在 item 自己身上新建键，默认表里的周衡不动。之后 rawget 能看见阿宁，另一条仍借到周衡。这是你想要的覆盖。若你改的是 defaults.owner，所有还没覆盖的条目会一起变成新主人，因为它们读的是同一张默认表，不是各自抄下来的副本。共享省下了每条都写主人的麻烦，也制造了连带修改。默认表应当当成稳定的底稿。要改全体，就明白地改底稿；要改一条，就写在那一条上。

```lua run expect="4" title="底稿一变，没覆盖的一起变"
local defaults = { priority = 1 }
local a = setmetatable({ title = "买笔" }, { __index = defaults })
local b = setmetatable({ title = "交表" }, { __index = defaults })
defaults.priority = 2
print(a.priority + b.priority)
```

2 加 2 是 4。若希望两条各有优先级，就在 a 和 b 上分别写入，不要改 defaults。写入之后再改 defaults，已经覆盖的那一条不再跟随。跟随与否取决于键还在不在自己身上，不取决于你当初从默认读到过什么。读不会把值抄回来。这和有些框架的「访问时冻结一份」不同。Lua 的 __index 每次缺失都再查一次。好处是底稿的修正立刻可见。坏处是你不能假设「第一次读到的 1 会留在对象里」。要留，就显式赋值。

默认值若是一张表，例如标签列表，共享会更危险。两条待办的 tags 若都从默认表借来同一张，往里面插入「急」会同时出现在两条上。字符串和数字没有这个问题，它们不可变，或者改的是绑定而不是内容。布尔值也安全。所以这一章的默认只用 done、owner、priority 这种不可再深入改写的值。真要每条有自己的标签表，就在创建时放一张新的 `{}`，不要放进 __index。

__index 也可以是函数，缺失时调用它来计算默认值。函数能看键的名字，甚至按标题生成一个默认优先级。我们不用函数形式，因为待办的默认是数据，不是计算。数据可以打印、可以在测试里改一个数字就看到 4。函数把规则藏进代码路径，默认优先级是多少得跑起来才知道。等规则真的依赖标题内容，再考虑函数。在那之前，多一种形式只会让 rawget 的对照更难讲。

没有元表时，缺失就是 nil。挂上只含 __index 的元表之后，缺失变成「再查一张表」。再查的那张表自己也可以有元表，于是形成一条链。链能用来做一层层的默认：全体待办、这一类、这一条。链一长，值到底从哪一层来，rawget 只回答「是不是自己的」，不回答来自哪一层。要回答，得沿着元表自己走。短课里链只留一层。一层已经够表达「纸上的空圈」。

getmetatable 可以把元表取回来。取回来就能改 __index，所有挂着它的待办立刻改道。这说明元表不是创建时的快照。若你把元表放进一个谁都能碰到的地方，任何代码都能改查找规则。模块那一章会把构造函数收进本地表，元表用局部变量挡住，外面只能要到已经挂好规则的条目，改不到规则本身。那是隐私，和闭包挡住清单是同一类选择。

false 作为默认值时，条件仍把它当成假。item.done 通过 __index 得到 false，`if item.done then` 走 else，印出未完成。这是对的。不要为了「默认值也算有值」去把未完成设成 0 或其他真值。0 会让 if 走进完成。未完成就用 false，并且接受它挡不住 `or "默认"` 这种写法——false 会触发 or 的右边。显示中文时用 if，或者用 `== false` 把借来的 false 和真正的 nil 分开。挂了元表之后，done 不该再是 nil，除非默认表里也没有。若 rawget 是 nil 而 item.done 是 false，你看到的就是「借来的未完成」。

```lua run expect="借来的未完成" title="默认的 false 仍是假"
local defaults = { done = false }
local item = setmetatable({ title = "回信" }, { __index = defaults })
if rawget(item, "done") == nil and item.done == false then
  print("借来的未完成")
else
  print("不是这一种")
end
```

元表不改变 `#`。序列的长度仍按边界找，不会因为 __index 在缺失的下标上提供了一个默认标题，就把洞填上。`#` 和 ipairs 使用的是原始访问，不触发 __index。你不能靠默认表去修补洞。洞仍然要避免，默认只修补名字字段。这是两种缺失：序列中间的 nil，和记录上的缺字段。同一种 nil，两套机制，只有第二套会来问 __index。混用会让人以为默认标题能把 `#` 变长。它不会。

setmetatable 的返回值就是那张被挂上规则的表，所以可以写成 local item = setmetatable({ title = "买笔" }, meta) 一行。元表本身也可以是局部变量，几条待办共享同一张 meta，而不是共享条目。共享 meta 和共享 defaults 是两层。改 meta 的 __index 指向另一张底稿，所有条目的查找方向一起变。改底稿里的字段，只有还没覆盖的条目变。两层都要有名字，打印时才说得清你动的是规则还是数据。匿名的元表写在调用里很短，短的代价是后来想给第二组待办换底稿时，你找不到那张元表。

没有 __newindex 时，给缺失的键赋值会写到自己身上，这是覆盖。若以后加上 __newindex，赋值可能被拦住，转写成别的存储，rawset 才能绕过。这一章不加那一项，就是为了让赋值的含义保持「写在这张表上」。读者不必同时记住两套绕过方法。rawget 对读取已经够用。写入用普通赋值，再用 rawget 证明键出现了。证明比再介绍一个 rawset 更贴这张纸：周衡在某一行上画了圈，圈就在那一行，不在规则表里。

默认表里不要放函数，除非你准备把方法也做成共享的。放一个函数值本身没有问题，它和数字一样被读出来。问题是调用时的自我。item.touch() 这种冒号语法会把 item 当作第一个参数传进去，点号调用则不会。默认表上的函数若假设第一个参数是条目，调用方式写错，标题就会变成 nil。方法是函数那一章和模块那一章的领域。元表这一章的 __index 只提供 done、owner、priority。不提供动作，调用就不会悄悄依赖冒号。动作仍写在普通函数里，参数显式把 item 传进去，传的是表，不是「对象」这个额外概念。

链路上的第二层默认会让值的来源更难讲。假设条目没有优先级，第一张默认表也没有，第二张才有。读到的数是对的，rawget 只告诉你不是自己的。要知道来自第二张，得取出元表，再看它的 __index 是不是还有元表。调试时把这三步打印出来可以，写进业务代码就会把每一条待办的读取都变成巡游。一层默认足够表达空圈。第二层留到真的出现「这一类待办」和「所有待办」两种底稿时再加。加的时候给两张底稿不同的主人名字，输出里就能看见当前落在哪一层。

元表不影响相等。两张内容相同、元表也相同的待办，== 仍是假，除非它们是同一个引用。Lua 不因为挂了 __index 就按字段比较。想按标题判断是不是同一件事，就比较 title 字段。这避免了「默认字段也参与相等」带来的意外：一条没写主人、一条写了周衡，若按全部可见字段比较，会因为默认主人看起来一样而被当成同一条。可见字段包含借来的值，存储字段不包含。相等应该看存储，或者只看你指定的键。指定标题，买笔和买笔是同一件事，即使一条的优先级是借来的 1，另一条自己写成 1。

把元表用于模块的函数表，可以让没写的动作落到一套基础动作上。待办的动作只有追加、计数和成行，继承它们会让调用点看不出函数到底定义在哪。缺函数时的 nil 调用会立刻报错，报错比静默落到一个过时的基础版本更好。所以这一章的技术不拿到模块上去用。技术能用，不代表这张纸需要它。需要的是缺省的完成标记和主人，那是数据，用 __index 的表形式刚好。

挂上元表之后，type 仍回答 table，不会多出一个叫对象的类型名。调试时打印类型，只能确认它还是表，确认不了默认值从哪一张底稿来。来源要靠 rawget 和普通读取对照。两种读取不同，说明规则在工作。两种读取相同，要么键写在自己身上，要么规则根本没挂上。字段名若写成少了下划线的 index，缺失仍是 nil，脚本往往继续跑。这种安静的失效比报错更依赖对照。对照就是同一条上两种读取各印一次，用中文说明哪一次是借来的。

几条待办可以在创建时就写入已经知道的字段，只把真正省略的留给底稿。创建时全抄一份，元表就没有意义，每条都是独立副本，改底稿不再影响任何人。全不抄，所有字段都共享，一条赋值之前大家都跟着底稿走。介于两者之间才是这章要的：标题必写在自己身上，完成标记可以省略。必写的那些不放进默认表，省略的那些不在构造时填 nil。填了 nil 等于没写，查找仍会落到默认，你以为自己显式清空了，其实没有。清空用 false 或其他明确的值。

## 小结

__index 只在键缺失时把查找带到另一张表。自己写过的键优先，rawget 能证明某个值是不是借来的。默认表是共享底稿，改底稿会连带所有没覆盖的待办；写到条目身上则只影响那一条，而且不会自动抄一份。默认的 false 在条件里仍为假。长度和 ipairs 不走 __index，所以元表填不满序列里的洞。
