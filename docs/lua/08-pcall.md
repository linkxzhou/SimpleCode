空标题不该变成一条待办。前面用 if 绕开它，调用方若忘记绕，空字符串仍会进表。把拒绝放进追加函数里，规则就跟函数走，不跟每一处循环走。拒绝需要一种能从深层返回的失败，而不是一个容易被忽略的返回码。error 抛出失败，正常的返回到此为止。若没有人接，整个脚本停下来，退出码不是 0，终端上是错误位置和消息。教学里希望这一块仍然成功结束，并把消息印成可以核对的字。pcall 负责接住。

pcall 调用一个函数。成功时，第一个结果是 true，后面是那个函数自己的返回值。失败时，第一个结果是 false，第二个是错误对象。错误对象通常是字符串。下面故意对空字符串抛出「缺标题」。error 的第二个参数用 0，表示不要在消息前面再加文件名和行号。行号会随课文改动而变，期望若写死行号，一插入一行注释就对不上。消息本身稳定。接住之后打印它。

```lua run expect="缺标题" title="接住故意的失败"
local function need_title(title)
  if type(title) ~= "string" or title == "" then
    error("缺标题", 0)
  end
  return title
end
local ok, result = pcall(need_title, "")
if ok then
  print("不该成功")
else
  print(result)
end
```

注意判断用的是 ok，不是 result 的真值。失败时 result 是非空字符串，字符串为真。你若写成 `if result then`，失败的消息也会走进成功那一支，然后被当成标题印出来，看起来像「接住了又没接住」。true 和 false 才是 pcall 的合同。消息留在第二个名字里，只在 ok 为 false 时阅读。

成功的路径要把 true 和标题一起看。只打印标题，会漏掉「第一个结果是 true」这件事。有人把 pcall 的结果当成标题本身，于是清单里出现一条叫 true 的待办，或者在连接时把布尔值转成文字。下面分开印。

```lua run expect="true" title="成功时先看见 true"
local function need_title(title)
  if type(title) ~= "string" or title == "" then
    error("缺标题", 0)
  end
  return title
end
local ok, result = pcall(need_title, "买笔")
print(ok)
print(result)
```

第二行是买笔。期望锁定 true，是为了盯住合同的第一项。你改函数让它抛错，第一行会变成 false，期望就失败，这是对的。若期望只写买笔，一个把买笔写进错误消息的失败也可能混过去。两个结果分工：第一个回答有没有抛，第二个才是标题或消息。

追加可以包在同一层保护里。失败时清单不应变长。pcall 接住之后，表的内容保持调用前的样子，因为出错发生在写入之前。若你先写入再检查，失败时条目已经在里面，接住错误也不会自动撤销。所以检查放在写入前。这不是事务，Lua 没有替你回滚表。顺序就是你的事务。

```lua run expect="1" title="先检查再写入"
local function add(list, title)
  if type(title) ~= "string" or title == "" then
    error("缺标题", 0)
  end
  list[#list + 1] = title
  return #list
end
local items = {}
local ok, n = pcall(add, items, "交表")
if ok then
  print(n)
else
  print(n)
end
print(#items)
```

成功时 n 是 1，长度也是 1。两行都是 1。若传入空串，ok 为 false，长度仍是 0，打印的是缺标题。你可以把这一块的参数改成空串再跑，对照两行。对照要在同一次修改里看，不要同时改检查条件和期望，否则你不知道是规则变了还是核对变了。

pcall 会接住保护函数里的任何错误，包括把 `#` 写成错的名字、把局部变量打错。那些错误的消息通常带有行号，看起来和「缺标题」不同，但若你的处理只看 ok，拼写错误和校验失败会走同一支。支路里若统一印「失败」，你就看不见是哪一种。处理时把 result 打出来。范围也要收小：pcall 只包住追加或只包住校验，不要把整份脚本包进去。整份都包住时，所有 bug 都变成一条温和的输出，退出码还是 0，测试以为通过了。温和的输出应当只留给你预期的那种失败。

assert 是一种会抛错的检查。`assert(title ~= "" , "缺标题")` 在条件为假时调用 error。它顺手，消息的位置信息是默认加上的。我们在例子里直接用 error 并传入 0，是为了让期望不必包含 `stdin:` 这种随运行变化的前缀。assert 的条件若写成 `assert(title)`，空字符串会通过，因为空字符串为真，nil 才会失败。又一次，真值比「有没有字」更宽。校验空标题要用 `title ~= ""`，再配上类型是字符串。assert 省不下这句比较。

错误对象不一定是字符串。error 可以抛出一张表，例如 `{ code = "empty" }`。pcall 会原样把这张表交到第二个结果里，并且因为不是字符串，不会去加位置前缀。结构化的错误便于区分缺标题和缺主人。代价是打印一张表只会得到类似 table: 0x... 的文字，地址每次进程都可能变，不能写进期望。要核对，就打印字段：`result.code`。这一课的消息用字符串，打印简单，字段留到错误种类真的多于一种时再做。

调用 pcall 的方式和调用普通函数一样，参数跟在函数后面：`pcall(add, items, "交表")`。不要写成 `pcall(add(items, "交表"))`。后者会先调用 add，失败在 pcall 开始之前就已经抛出，没有人接。这是最常见的一层括号之差。前者把函数和参数交给 pcall，由它来调用。匿名函数 `pcall(function() ... end)` 适合一段不止一次调用的逻辑。一段太长，就退回到「范围要小」的那条。

失败被接住之后，脚本可以选择补一条默认待办，也可以选择什么都不加。补默认会把「用户没写」伪装成「用户写了未命名」，和类型那一章反对的 or 默认是同一类粉饰。这里选择不加。打印消息，让周衡看见缺标题，然后清单保持原长。安静地补上，纸会越来越长，每一条都不是他写的。

pcall 的函数若再调用 pcall，失败会被内层接住，外层看到的是成功。内层若把失败吃掉并返回 nil，外层的 ok 是 true，第二个结果是 nil。调用方会以为追加成功且没有标题。吃掉错误必须有记录，例如返回 false 和消息，而不是返回 nil。记录要印出来。静默的内层 pcall 是这一章最不希望看到的结构：外面以为有保护，里面把保护变成了黑洞。一层就够。校验函数自己抛，最外层接一次。

error 抛出的字符串可以被接住后再 error 一次，把消息原样抛给更外层。这适合模块不想处理、只想加上自己的话的时候。加上话就拼接，不要把原消息丢掉。丢掉之后，最外层只看见模块名，看不见是缺标题还是缺主人。拼接用 ..，不要用 print 的多参数，否则制表符会进到错误对象里，下一层再打印时缝是看不见的。错误消息也是字符串，字节规则同样适用。中文消息的长度是字节，不要拿去和某个单字节的错误码数组下标混用。

成功时函数可以返回零个结果。pcall 仍返回 true。第二个名字会是 nil，因为没有结果可接。nil 在这里表示「没有额外信息」，不表示失败。失败与否只看第一个结果。若你的追加成功时不返回条数，调用方必须能接受第二个值是 nil，并且不去对它取长度。想让成功总是带着条数，就 return #list，哪怕是 0。0 是数，可以打印，也可以和「没返回」分开。没返回和返回 nil 在一个接收位置上看起来一样，都是 nil。要分开，就保证成功路径的返回个数固定。

故意失败的例子应当稳定。用一个固定的空字符串，而不是用随机数决定抛不抛。随机会让期望有时对上、有时对不上，核对就失去意义。教学脚本里的失败是设计出来的，和真正的意外相反。真正的意外来自写错的名字。设计出来的失败消息由你指定，意外的消息由解释器指定。处理时可以先看消息是不是你指定的那句。是，就按校验失败处理；不是，就不要把它翻译成「缺标题」，翻译会掩盖笔误。掩盖之后的清单是空的，你以为用户没写，其实函数名字写错了，一条都没机会加。

assert 的第一个参数若是一个函数调用，调用会先发生。assert(need_title("")) 会先抛，assert 看不到。这和 pcall(need_title("")) 是同一类括号问题。assert 不是接住错误的函数，它是条件为假时才抛的函数。条件本身抛了，传播出去的是条件的错误，不是 assert 的消息。想检验标题，把布尔表达式放进 assert，不要把会抛的函数放进 assert 再希望它改写消息。会抛的函数交给 pcall。

接住之后的清单可以继续用。失败没有把表毁掉，前面已经追加的买笔还在。这是顺序的好处：先成功的留下，后失败的不写入。若你在一次 pcall 里循环追加三行，第二行失败，第一行已经在表里，第三行没有执行。没有自动撤销第一行。要「三行要么都在要么都不在」，就先放进临时表，全部成功再搬到正式清单，或者失败时把正式清单清回原来的长度。清回去要自己写。pcall 不提供这张收据。收据是你在调用前记下的 #items。

错误消息里可以带上这次收到的标题，方便区分两笔不同的拒绝。空串的长度是 0，写进消息能证明拒绝的是空白而不是缺失。缺失的值没有长度，拼接之前必须先问类型。顺序反了，会在 nil 上取长度，抛出的是解释器那一句，你准备的「缺标题」根本没有机会执行。期望对不上时，先看是不是问类型的那一行写在了取长度之后。两句拒绝都给 error 传 0，行号才不会掺进要核对的文字。

接住失败之后若还要追加别的合法标题，用同一张表继续即可。前面失败的那次没有留下空洞，因为写入在抛出之前没有发生。后续成功的下标仍是连续的。不要因为看见过一次 false 就把整张表丢掉重来，除非业务要求「有一行非法则全部作废」。全部作废需要你自己清表，保护调用不会替你清。清表是一张新的空表赋回名字，不是把每个键设成 nil。逐个设成 nil 会在中途制造洞，长度立刻变得不可信。换一张新表最干净。

## 小结

error 用来拒绝空标题，pcall 把这次失败变成 false 加上消息，脚本得以继续并把「缺标题」印出来。成功时第一个结果是 true，后面才是函数的返回值。检查要写在改表之前，pcall 不会回滚已经写入的键。保护的范围只包住这段校验，断言空标题时不要依赖空字符串的真值。

## 练习

对一个空字符串调用会抛出「缺标题」的函数，用 pcall 接住并打印消息。消息不要带行号前缀。

::: answer 参考答案：打印缺标题
```lua run expect="缺标题" title="参考答案"
local function need_title(title)
  if title == "" then
    error("缺标题", 0)
  end
  return title
end
local ok, result = pcall(need_title, "")
if not ok then
  print(result)
end
```
