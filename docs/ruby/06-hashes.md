数组靠位置认元素，位置一插队，后面的下标全变。一本书的标题、页数和书架没有自然的先后，硬排成数组会让 `book[1]` 到底是页数还是书架变成口头约定。哈希是一组键到值的映射。键负责身份，值负责内容。这一章只建一本书，名字就叫 `book`。标题是字符串 `"ruby"`，页数是整数 `180`，书架是符号 `:west`。键本身也用符号：`:title`、`:pages`、`:shelf`。

花括号里的 `title: "ruby"` 是 `:title => "ruby"` 的简写。键必须是符号，简写才成立。字符串键不能写成 `title: ` 这种冒号贴在后面的形式，那种冒号是符号键的语法。老式的 `=>` 对任何键都适用，写 `"title" => "ruby"` 得到的是字符串键。两种写法可以混在一张表里，于是一张表里同时存在 `:title` 和 `"title"` 两个键，它们不相等，查找对不上。这是哈希最常见的静默错误：读到 `nil`，脚本继续跑，后面再对 `nil` 发消息才停。维护一份约定比记忆语法重要。这门课的约定是：代码里的字段名用符号，用户输入的原文用字符串。用户输入是开放集合，不适合事先变成源码符号；字段名是封闭集合，符号的身份稳定，写起来也短。

```ruby run expect="ruby" title="符号键读出三个字段"
book = { title: "ruby", pages: 180, shelf: :west }
puts book[:title]
puts book[:pages]
puts book[:shelf]
```

三行是 `ruby`、`180` 和 `west`。`puts` 打符号时不带冒号，所以书架看起来像普通单词。这不表示它被收成了字符串。值仍然是符号。要看见冒号，用 `p book[:shelf]`，检查形式是 `:west`。`puts` 对哈希整体不会拆成每个键一行。`puts book` 打出的是一整行检查形式，类似 `{:title=>"ruby", :pages=>180, :shelf=>:west}`。这和数组被拆行不同，不要用数组的经验来预测哈希的输出行数。确认键的样子时，`p` 更合适；向别人交标题文字时，取出 `book[:title]` 再 `puts`。

用字符串去取符号键，得到 `nil`，不是标题。`nil` 在条件里为假，所以 `book["title"] ? "有标题" : "没有"` 会说「没有」，即使标题明明在 `:title` 上。失败被真值吞掉了。`inspect` 能把这个 `nil` 显式打出来。页数用 `fetch` 去取，键在时结果和 `[]` 一样，是 `180`。两者的差别在键不在的时候，下一块再看。

```ruby run expect="nil" title="字符串键对不上"
book = { title: "ruby", pages: 180, shelf: :west }
puts book["title"].inspect
puts book.fetch(:pages)
```

`[]` 在键缺失时返回 `nil`，若你曾用 `[]=` 把某个键设成 `nil`，两种情况的读法相同。你无法从返回值知道键在不在。`fetch` 在键缺失时失败，异常类型是 `KeyError`，脚本会停，除非你接住它。也可以给 `fetch` 第二个参数当默认，或给它一个块，只在缺失时计算默认值。默认参数在键存在时不会求值吗？第二个参数总是会先求值。块则只在缺失时执行。默认值若很贵，或带副作用，用块。页数这种字段缺失应当算数据错误，不该默默变成 `0`，因为 `0` 页和「没有页数字段」会被后面的加法收成不同的故事。这一章用接住 `KeyError` 来把错误变成一句「没有作者」，作者键我们故意不放。

```ruby run expect="没有作者" title="fetch 缺失即失败"
book = { title: "ruby", pages: 180, shelf: :west }
begin
  puts book.fetch(:author)
rescue KeyError
  puts "没有作者"
end
```

`begin` 和 `rescue` 只包住这一次查找。不要把整本书的构建也包进去，否则写错字段名时你也会看到「没有作者」，排查范围被放大。异常是在说「这个键不该缺」。若键可以缺，用 `key?` 提问，`book.key?(:author)` 为 `false`，再决定打印什么。`key?` 问存在，不取出值，因此不受「值本身是 `nil`」的干扰。可以缺的字段用 `key?`，不该缺的字段用 `fetch`。`[]` 适合你确定键在、只是想写得短的时候。

页数要增加时，读出来加，再写回去。`book[:pages] = book[:pages] + 12` 得到 `192`。哈希不会因为值是整数就提供 `book[:pages] += 12` 以外的魔法，`+=` 能用，只是因为它是读、加、写回的糖。写回的是新的整数，键仍是 `:pages`。漏写左边，加法的结果丢掉，页数停留在 `180`。和整数那一章一样，运算不自动写回容器。容器只是多了一层槽。

```ruby run expect="192" title="页数写回同一键"
book = { title: "ruby", pages: 180, shelf: :west }
book[:pages] = book[:pages] + 12
puts book[:pages]
puts book[:title]
```

标题仍是 `ruby`。改一个键不影响另一个键。这是哈希相对数组的好处：你不用记得页数是第几号。代价是键写错时没有「越界」这种位置错误，只有缺失。写错成 `:page` 会新增一个键，旧的 `:pages` 还在，表里两套页数。`p book` 能看见多余的键。只 `puts book[:pages]` 会让你以为写回失败，其实写到了别的键上。改完不确定时，看整张表的检查形式。

默认哈希 `Hash.new(0)` 让缺失的键读出来是 `0`，常用于计数。这个 `0` 是读的时候给的，键并不因此存在。`counts[:ruby]` 第一次读到 `0`，`counts.key?(:ruby)` 仍可能为假，直到你赋值。用它来数书名出现次数是合适的，因为「没出现」和「出现零次」在计数里可以当成同一个数。用它来存页数不合适，缺失会被当成 `0` 页，`fetch` 那种失败也消失了。默认值是政策：读缺失时不要吵，还是要吵。一本书的目录选择吵，用普通哈希加 `fetch`。计数器选择不吵。

键的比较用 `eql?` 和哈希码，不靠真值。整数 `180` 若被误当成键，它不会和浮点 `180.0` 合成一个键。我们的键是符号，值才是 `180`。符号和同文字的字符串也不会合成一个键，这和 `==` 对两类对象直接返回假是一致的。不要在运行时把用户输入 `to_sym` 之后拿去当 `:title` 这种字段来查，除非你明确在做字段名解析，并且拒绝未知字段。用户输入进 `:title` 的值，键保持 `:title` 不变。

`each` 能遍历哈希，块收到键和值两个参数。`book.each { |key, value| ... }` 里，`key` 是符号。遍历顺序在当前的 Ruby 里是插入顺序。依赖顺序来排版可以，依赖顺序来当编号不可以，编号是数组的职责。不要为了顺序把这张表改回数组，又失去键。需要顺序又需要键时，保留哈希，另外用一个数组记下键的顺序。三字段的小表用插入顺序就够了。

`books` 若要从书单长成多本书，每一本是一个哈希，外层是数组。这一章先不建那个数组，免得一次引入两层容器。先让单本的三个键稳定。下一层数组只是把「取第几本」交回去。键的约定不会因为外层是数组就改变：每本仍用 `:title` 和 `:pages`。若有的本用字符串键，`map` 时会混进 `nil`。约定要在放进数组之前就统一。

`merge` 交出一张新表，不改原来的 `book`。`book.merge(pages: 200)` 的新表里页数是 `200`，旧表仍是 `180`。这和 `map` 交出新数组是同一类选择：默认不碰原来的结构。`merge!` 就地改。两张表有同一键时，参数那张的值赢。没有的键会加进去。你若用 `merge` 的结果却不接住，旧页数不会变，看起来像加法没生效。写回 `book = book.merge(...)` 才让名字指向新表。旧表若还有别的变量指着，那些变量仍看见 `180`。这是复制的意义。

```ruby run expect="180" title="merge 不改旧表"
book = { title: "ruby", pages: 180, shelf: :west }
newer = book.merge(pages: 200)
puts book[:pages]
puts newer[:pages]
```

`values_at` 按你给的键取出数组，顺序跟参数走，不跟插入顺序走。`book.values_at(:pages, :title)` 先是页数后是标题。缺键的位置是 `nil`，不会抛错。它适合一次取好几个字段再交给别的方法，不适合替代 `fetch` 的严格。取完得到的是数组，`puts` 会逐个元素换行。想保留结构就 `p`。键的顺序由调用决定，所以它能表达「打印顺序」，哈希本身的插入顺序仍留给遍历。

嵌套时，`book[:shelf]` 若从符号改成另一张表，例如 `{ id: :west, row: 2 }`，读取要用连续的 `[]`。中间任何一层是 `nil`，下一层就会失败。`dig` 在中间缺失时返回 `nil`，不抛错。方便和含糊再次绑在一起：`dig` 适合可选的嵌套，必填的路径用逐层 `fetch`，让缺的那一层报 `KeyError`。这一章的书架只是符号，用不到 `dig`。等字段长成树，再决定哪条路径可以缺。不要为了短，把必填路径写成 `dig`。

键可以是任何对 `eql?` 和哈希码有稳定表现的对象。把数组当键可以，但就地改那个数组之后，哈希可能找不到它。字符串键也有同样的问题，所以才有「放进表之后不要再改键」的约束。符号不能就地改内容，拿来当字段名少这一类事故。这是符号键的实际好处，不只是少打引号。值可以改，键不要改。页数写回是在换值，不是在改键对象。

值可以是 `nil`。`book[:author] = nil` 之后，键是存在的，`key?` 为真，`[]` 的返回值仍是 `nil`。这时 `[]` 完全不能区分「没有作者字段」和「作者字段是空」。`fetch` 能取到这个 `nil` 而不抛错，因为键在。`compact` 会交出一张去掉 `nil` 值的新表，原表还在。用它来清理可选字段可以，用它来删除「故意写成空」的作者则会丢信息。空作者若要和缺失区分，就保留 `nil` 值，读取用 `key?`。不要把 `compact` 当成标准的读路径。

```ruby run expect="true" title="值为 nil 的键仍在"
book = { title: "ruby", pages: 180, shelf: :west }
book[:author] = nil
puts book.key?(:author)
puts book[:author].inspect
puts book.fetch(:author).inspect
```

遍历时不要边遍历边删键。正在 `each` 的表上删除，可能跳过元素或直接失败，取决于删除的是不是当前键。需要过滤时，用 `select` 交出新表：`book.select { |key, value| key != :pages }`。哈希的 `select` 把键和值都交给块，返回的仍是哈希，不是数组。这和数组的 `select` 只交一个元素不同。块参数写成 `|key, value|`，少写一个的话值会被丢掉，条件若误用了值就会错。过滤页数这种结构，通常是在造一张给别人看的表，原书的页数还要留着。就地 `delete` 适合你确定这张表的生命周期只到这次请求结束。

数字当键时，`1` 和 `1.0` 不会并成一项，因为 `eql?` 看类。页数做值，不做键。若你用分数当键去数「有多少人得了这个分」，键用整数，先把输入用十进制规则转成整数再当键。浮点键会让看起来相等的分进不了同一个计数。计数表用 `Hash.new(0)` 合适，因为没出现过就是零次。书的字段表不要用这个默认。

`delete` 返回被删掉的值，键不存在时返回 `nil`，除非你给了块作为缺失时的计算。只看返回值，又会把「删掉了一个 `nil` 值」和「键本来没有」混在一起。删除作者字段之后若要确认，再问一次 `key?`。不要用删除的返回值当作唯一的成功标志。页数这种必填字段通常不删，只改值。

## 小结

`book` 用符号键存放标题、页数和书架。`title: "ruby"` 就是 `:title => "ruby"`。`book[:title]` 得到字符串，`book["title"]` 得到 `nil`，因为键的类不同。`puts` 打出的符号不带冒号；要看冒号和整张表，用 `p`。

`[]` 在缺失时返回 `nil`，和「值就是 `nil`」分不清。`fetch` 在缺失时抛出 `KeyError`。可以缺的字段用 `key?`，不该缺的用 `fetch`。页数增加必须写回 `:pages`。写错键名会多出一个键，旧键还在。默认哈希适合计数，不适合把缺页数伪装成 `0`。
