上一章的 `add` 对数量 0 选择安静返回。有些货行不该安静。单价是负数、数量是负数，都意味着这行字本身不能进账。继续加，合计会变小，纸上却像是卖出了货。巷口纸品把这种行当成失败：抛出 `Exception`，由打票的那一层接住，印出「失败」，并且不要把这一行加进合计。能用 `if` 看懂的普通分支，仍然用 `if`。异常留给「这张票不能接受」的那一种。

`throw new Exception("负数数量")` 立刻离开当前函数，往外找 `try`。`catch (Exception $e)` 接住它。接住之后，`$e` 里有消息。消息可以含路径或你临时写的英文，不适合做期望的全文。期望写成你自己 `echo` 的固定词「失败」。固定词不随文件路径变化。消息仍可在店员读终端时帮忙，只是核对不依赖它的整句。`try` 里面，抛出之后的语句不会执行。成功的 `echo` 若写在 `throw` 后面，失败时不会印出「好」。把成功的打印放在 `try` 的末尾，失败的打印放在 `catch` 里，两条路只走一条。

空的 `catch` 会把失败吃掉。合计没有增加，纸上也没有「失败」，调用者会以为这行已经入账。接住就一定要有可见的结果：打印固定词，或返回一个调用者必须查看的值。小票选择打印。不要用空的 `catch` 来压住警告。警告不是 `Exception`。把失败变成沉默，比让进程停掉更难查，因为退出码仍是 0。

PHP 把失败分成两条继承线。`Exception` 是你抛出的应用失败。`Error` 是引擎的失败，例如把对象当字符串印、把两个字符串相加、用 `intdiv` 去除以零。`catch (Exception $e)` 接不住 `DivisionByZeroError`。那个类型继承 `Error`，不继承 `Exception`。若你希望除以零也印「失败」，就要么在调用 `intdiv` 之前用 `if` 判断除数，自己 `throw new Exception`，要么额外写 `catch (Error $e)`。额外去接所有 `Error`，会把编程错误和业务失败混在同一个词里。铅笔的数量写错，和你把参数传反导致的类型错误，不该在纸上长得一样还让人无法分开。课程的业务失败只用 `Exception`。除数是否为零先用 `if ($n === 0)` 判断，为零就抛 `Exception` 或直接印「失败」。`intdiv` 只在除数已经非零时调用。这样 `DivisionByZeroError` 不会出现在正常的小票路径上。

能用 `if` 写清楚的，不必绕进 `try`。数量是不是负数，看一眼就知道。`if ($qty < 0) throw new Exception("负数数量");` 把判断和抛出放在一起，是「看完才拒绝」。若负数只是一种普通分类，例如退货单，那它不是失败，而是另一种单据。退货应当有自己的方法，而不是靠异常当成分支。异常会跳过中间的代码，跳过的代价在有多步更新时才显出来：你已经把品名追加进明细，然后单价检查失败抛出，明细里就留下一行没有金额的货。所以检查放在修改字段之前。先看数量和单价，都合法再 `$this->total += ...`。失败时字段保持原样，不需要回滚。这是小票类保持一个整数合计的好处。先改后检查，就要在 `catch` 里把刚才加的减回去，减错还会再错一次。

不要用异常的消息文本做分支。`if ($e->getMessage() === "负数数量")` 会在有人改了标点之后失效。需要区分几种失败时，用不同的类，例如自己写 `class BadLine extends Exception`。`catch (BadLine $e)` 只接坏行，其他 `Exception` 另接。这一章的失败只有一种，一个 `Exception` 就够。子类留到真的有两种处理的时候。多写的类在只有一种打印词时是噪音。

未接住的 `Exception` 会让进程失败，退出码不是 0，php-cgi 会打出一段带栈的 HTML。抽屉里的核对不会把这当成成功的小票。可运行的失败示例都自己接住。这不是为了把错误藏起来，是为了把「接住之后印什么」固定下来。真正忘记接住的情况，应当表现为进程失败，而不是一张写着栈追踪的顾客小票。栈追踪给写程序的人看。顾客那一层只看见「失败」。

`finally` 无论是否抛出都会执行。小票若打开了什么必须合上的东西，可以放在 `finally`。这一章没有打开文件，也没有网络连接，不必为了对称去写空的 `finally`。空的 `finally` 不改变结果，只增加一块看起来像清理的结构。没有资源时不写它。

下面三块沿用 `Receipt`。第一块抛出并接住。第二块在除数为零时先判断，再抛 `Exception`，避免引擎的 `DivisionByZeroError`。第三块是成功路径，除数非零，印出整数商，说明 `try` 不是每笔账的义务。

```php run expect="失败" title="负数数量不入账"
<?php
class Receipt {
  private $total;
  public function __construct() {
    $this->total = 0;
  }
  public function add($cents, $qty) {
    if ($qty < 0 || $cents < 0) {
      throw new Exception("负数");
    }
    $this->total += $cents * $qty;
  }
  public function cents() {
    return $this->total;
  }
}
$ticket = new Receipt();
try {
  $ticket->add(350, -1);
  echo "好\n";
} catch (Exception $e) {
  echo "失败\n";
}
echo $ticket->cents(), "\n";
```

纸上先是失败，然后是 0。`echo "好"` 没有执行。合计仍是 0，因为抛出发生在加法之前。第二行的 0 说明字段没有被负数污染。期望锁定「失败」。你要自己确认后面还有 0，而不是 350 或 -350。若有人把 `throw` 挪到加法后面，第二行会变成负数或少掉的金额，第一行仍是失败，子串核对会放过脏账。所以这一块要看两行。

```php run expect="失败" title="除数先判断再抛异常"
<?php
function boxes($pencils, $size) {
  if ($size === 0) {
    throw new Exception("零");
  }
  return intdiv($pencils, $size);
}
try {
  echo boxes(20, 0), "\n";
} catch (Exception $e) {
  echo "失败\n";
}
```

`size` 为 0 时不会调用 `intdiv`。若删掉 `if` 直接 `intdiv`，抛出的是 `DivisionByZeroError`，这个 `catch (Exception $e)` 接不住，进程失败，纸上没有「失败」两个字。先判断，是为了让业务上的「不能装盒」停留在 `Exception` 这条线上。盒的容量来自店员填写时，0 是填错，不是引擎坏了。

```php run expect="3" title="容量合法时直接出商"
<?php
function boxes($pencils, $size) {
  if ($size === 0) {
    throw new Exception("零");
  }
  return intdiv($pencils, $size);
}
echo boxes(20, 6), "\n";
```

容量 6 不需要 `try`。调用者知道这个数是字面量，不是外来的输入。字面量仍可能写错，写错时让进程失败，比每行都包一层 `try` 更容易看见。`try` 包住的是来自文本、可能非法的那一笔。这一块的 20 和 6 来自源码，直接印出 3。成功路径保持直，读起来就是盒数。

异常的构造可以只写消息。消息用短词，给读栈的人看。顾客路径不印 `$e->getMessage()`。若你把消息印出去，期望就要跟着消息的标点走，改一个字，核对就坏。固定词把两边解开：内部消息可以改得更清楚，纸上的失败标志保持两个字。

有人会用返回 `false` 表示失败，调用者忘记检查 `false`，就会把失败当成合法的盒数去打印。`echo false` 是空。纸上少了一行，进程仍成功。异常强制调用者表态：要么接住，要么让进程失败。这个强制是它相对返回码的好处。代价是控制流不再只向下读，`throw` 会跳到远处的 `catch`。小票的 `try` 因此贴着调用写，不要把 `catch` 放在文件的另一头。贴着写，跳转的距离就只有几行。

把这一章嵌回打印机。`add` 先检查负数，再改合计。打票的脚本对可能来自文本的那一次 `add` 使用 `try`，接住后印「失败」，并再印一次 `cents()` 证明没入账。容量、除法这类能先看除数的运算，用 `if` 把零挡在 `intdiv` 之外。引擎自己的 `Error` 不被 `catch (Exception $e)` 收走。下一章处理「一行文本」，文本不来自键盘，而来自一个已经放在字符串里的行。空行会走到和这一章相同的失败词。

异常还会改变你阅读小票脚本的方式。没有异常时，你从上往下读，每一行都可能执行。有了 `throw`，你要同时看见一条跳转：从抛出点到最近的、类型匹配的 `catch`。中间那些打印和赋值都被跳过。跳过是你想要的，因为坏行不该留下半行字。跳过也是风险，因为你放在中间的「记一笔日志」同样不会发生。日志若必须发生，放在 `catch` 里，或放在一定会走到的语句里。小票没有日志文件，就把那一句可见的「失败」放在 `catch` 里。它是给顾客和给核对看的日志。

自己定义的异常类要继承 `Exception`，不要继承 `Error`。继承 `Error` 会让业务失败看起来像引擎坏了，`catch (Exception $e)` 又接不住它，你等于把上一节刚分开的两条线重新拧上。继承 `Exception` 之后，原有的 `catch (Exception $e)` 仍然接得住，因为子类也是 `Exception`。这是先用基类的好处：以后把消息换成子类，调用处的 `catch` 不用当天就改。若调用处写的是 `catch (BadLine $e)`，别的异常就会漏出去。漏出去表现为进程失败。你要决定未知的异常是应当停掉整单，还是也印「失败」。停掉整单更安全，因为你没想过那种失败该怎样入账。印同一个词更简单，也更含糊。含糊的词在只有一种失败时够用。

`intdiv` 的除数检查要和类型检查放在一起看。除数是字符串 `"0"` 时，`=== 0` 不成立，函数会继续调用 `intdiv`。`intdiv` 对字符串会先做转换，`"0"` 变成 0，然后仍抛出 `DivisionByZeroError`。于是你以为写了检查，检查却因为类型没挡住。把参数先收成整数，或同时判断 `$size === 0 || $size === "0"`。更干净的是入口处只接受已经验证的整数，字符串留在调用 `boxes` 之前处理。函数的合同写「两个整数」，调用者就负责转换。合同写「什么都能传」，函数内部就要把各种零都挡完。小票的 `boxes` 选择整数合同，所以示例传入的是不带引号的 `0` 和 `6`。

消息字符串还要避免把顾客的品名原样塞进去再拿去比较。品名里若含有引号或换行，消息会变长，按全文比较的人会失配。固定词「失败」不含品名。品名留在异常消息里给写程序的人看时，可以拼进去，但纸上仍只印固定词。这样品名里的特殊字符影响不了核对。拼消息时用点号，不用加号。两个字符串相加是 `TypeError`，属于 `Error`，不是 `Exception`。若你在准备异常消息时用了加号，还没来得及 `throw new Exception`，进程就已经因类型错误停了，`catch (Exception $e)` 看不到它。消息的拼接是字符串那一章的规则，在失败路径上同样有效。

最后区分三种停法。语法错误在运行前就停，没有任何 `echo`。未接住的异常在运行中停，抛出点之前的 `echo` 还在纸上，之后的没有。接住的异常不停，`catch` 里的词会印出来，后面的语句继续。三种停法对应三种纸面。核对失败时先看是哪一种，再改代码。改期望只能应付第三种里你印错的词，应付不了前两种。

## 小结

`throw new Exception` 表示这张票拒绝这一行。`catch (Exception $e)` 接住之后印「失败」，不拿消息全文做期望。抛出要发生在修改合计之前。`catch (Exception $e)` 接不住 `DivisionByZeroError` 和其他 `Error`。除数为零时先用 `if` 判断。空的 `catch` 会让失败看起来像成功。字面量已经合法时，不必为了对称包上 `try`。
