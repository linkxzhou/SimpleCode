到上一章为止，每一条成功的插入、更新和删除都自己作数。SQLite 默认把单条语句包在一次自动提交里。语句结束，这句的效果就定了，后一句看得见，也撤不回前一句。卖出一册夜航、同时在账上记一笔负数，这两件事若分属两句自动提交，前一句成功、后一句失败时，库存已经少了，账上却没有那一笔。对账的人会以为书丢了。事务把若干写入收成一个命运：要么一起留下，要么一起回到开始之前。

BEGIN 关掉自动提交，直到 COMMIT 或 ROLLBACK。COMMIT 把这一组留下，同一份脚本后面的查询看得见。ROLLBACK 把这一组撤销，哪怕里面已经插入了三本书，撤销之后再数，也是 0。下面先做撤销，因为撤销比提交更需要证据。人容易相信「我插入了所以它在」，不容易相信「我撤销了所以它不在」。证据用计数，不用空白终端。

```sql run expect="0" title="插入过，又撤销了"
CREATE TABLE books(title TEXT, copies INTEGER);
BEGIN;
INSERT INTO books(title, copies) VALUES
  ('夜航', 3),
  ('河岸', 1),
  ('旧书店', 2);
ROLLBACK;
SELECT COUNT(*) FROM books;
```

建表在 BEGIN 之前，所以表还在，撤销的是插入，不是建表。有人把 ROLLBACK 理解成「脚本作废，什么都没发生」。不是。它撤的是这一次事务里的写入。事务外面的对象还在。也因此，你能在撤销之后对同一张空表再查询。若把 CREATE 放进事务里，撤销会把表一起拿掉，后面的查询会因为没有表而失败。失败就没有 0 这个格子。教学脚本把建表留在事务外，让 0 有地方可落。

提交是对照面。同样的三行，COMMIT 之后再数，是 3。这个 3 只在这一次连接里有效。下一次 Run 仍是空的内存库，不会因为你写过 COMMIT 就留下夜航。提交不是持久化到下次按钮。持久化那台机器这里不存在。提交的意义是：同一份脚本的后半段可以相信这些行已经定了，不会被一次还没决定的撤销抹掉；同时，你若在提交前查看，也能看见自己的草稿。自己的连接看得到未提交的行。这门课只有这一条连接，所以你看不见「别人看不看得见」的那种隔离。不要把这里的实验理解成多用户并发的证明。它只证明同一条脚本里的命运绑定。

```sql run expect="3" title="提交之后这三行还在"
CREATE TABLE books(title TEXT, copies INTEGER);
BEGIN;
INSERT INTO books(title, copies) VALUES
  ('夜航', 3),
  ('河岸', 1),
  ('旧书店', 2);
COMMIT;
SELECT COUNT(*) FROM books;
```

真正需要同生同死的是一来一回。假设把一册从夜航挪到河岸：夜航减 1，河岸加 1，总数仍是 6。两句更新放进同一个事务，提交后分别去看，夜航是 2，河岸是 2，总和是 6。总和没变，分布变了。若只做了第一句就停住，总和已经少 1，分布也只改了一半。事务保证你不会把这种半截留给后面的查询。

```sql run expect="2|2|6" title="挪一册，总数不变"
CREATE TABLE books(title TEXT, copies INTEGER);
INSERT INTO books(title, copies) VALUES
  ('夜航', 3),
  ('河岸', 1),
  ('旧书店', 2);
BEGIN;
UPDATE books SET copies = copies - 1 WHERE title = '夜航';
UPDATE books SET copies = copies + 1 WHERE title = '河岸';
COMMIT;
SELECT
  (SELECT copies FROM books WHERE title = '夜航')
  || '|' ||
  (SELECT copies FROM books WHERE title = '河岸')
  || '|' ||
  (SELECT SUM(copies) FROM books);
```

2|2|6 里的 6 是诚实的：三本原来就是 6 册，挪动不创造册数。旧书店仍是 2，藏在总和里。若你把第二句更新写错书名，提交仍会发生，两句都会留下，总和可能还是 6，可册数长在了错误的书上。事务保的是命运，不是业务正确。业务正确仍靠 WHERE。不要因为有了 BEGIN 就放松条件。BEGIN 不会读懂「挪一册」这个中文意图。

撤销这一挪动，应当回到 3、1、2。在提交之前 ROLLBACK，再查夜航，应当仍是 3。注意插入三本书发生在 BEGIN 之前，那些行已经自动提交了，撤销不会把它们删掉，只会放弃事务里的两次更新。这和第一份脚本不一样。第一份的插入在事务内，撤销后连行都没有。范围由 BEGIN 划定，不由你的主观「这一段都算」。写事务时先看 BEGIN 上面还有哪些句子已经自己作数了。

脚本若 BEGIN 了却既不 COMMIT 也不 ROLLBACK 就结束，连接关闭时，未提交的事务会被回滚。你在同一次输出里看不到这个「关闭之后」，因为进程已经没了，没有下一句查询可以证明那些行消失。下一次 Run 又是全新的空库，更不能用来证明「是事务回滚了」还是「本来就没有持久化」。所以这门课一律把 ROLLBACK 写成一句看得见的语句，紧跟着 SELECT。不把证据寄托在进程退出时的隐式回滚上。隐式行为存在，但核对用不上。

失败也会中断命运。若事务里某一句违反约束，那一句不生效，你还得决定事务怎么办。有的错误让事务进入必须回滚的状态，之后除了 ROLLBACK 什么写入都不再被接受。教学例子避开了这种失败，让退出码保持为 0。你在自己的脚本里若看见「事务被中止」一类的话，先回滚，再修句子，不要在同一个已死的事务里反复重试插入。重试只会得到新的拒绝。

嵌套在这门引擎里不是真的堆叠许多独立事务。BEGIN 里面再 BEGIN，不会给你两层可以分别提交的抽屉。需要在一个大事务里撤销一小段，用保存点。这三本书的挪动只有两句，一层就够。保存点是句子变长之后的工具，不是起步的仪式。我不在可运行的例子里套保存点，避免你以为每段 SQL 都该有三层边界才算完整。完整是边界刚好卡在「必须同生同死」的那一组句子上。多出来的边界是噪音。

读在事务里是什么效果，也要说清。BEGIN 之后、写入之前，查询看见的是事务开始时已经提交的行。写入之后，同一条连接看见自己的草稿。提交之后，草稿变成这张表的事实，供后面的语句使用。没有第二个人会在你 COMMIT 之前把这些草稿读走，因为没有第二个连接。等你离开这个抽屉，到一台真正同时有许多人的库上，隔离级别会变成新的题目。那一天你再读锁定和快照。今天只要把 0、3 和 2|2|6 看懂。

自动提交让单句的教学变得容易，后一句总能看见前一句。它也让两句之间没有刹车。刹车要显式地开始事务。我把建表放在刹车之外，是一个要单独记住的版式：表是容器，写入才是这一次的命运。容器若被撤销，后面的证明查询就没有桌子可放，你得不到那个 0。笔若被撤销，容器还在，计数可以落成 0。两种版式不要混用之后抱怨找不到表。你若确实希望建错的表也一起消失，就把建表放进事务，并且不要在回滚之后查询它。

提交之后再回滚，撤不掉已经留下的行。回滚只对当前打开的那一层有意义。它不是编辑器里可以连续按许多次的撤销。编辑器的撤销栈记得你的按键，事务只记得这一层还没提交的写入。终点之后的修改是新的命运，不再和已经提交的进货绑在一起。想反悔已经提交的挪动，只能再写一笔相反的业务，那是新的事务，也是新的事实，不是把旧事实从历史上抹掉。

自己读得到草稿，不要推广成「数据库都会把未提交的行给别人看」。这里读得到，是因为读和写是同一条连接。别的级别可以禁止别人看见草稿。合计在回滚之前能被打出来，靠的是同一条连接这份特权，不是一条普遍定律。特权让教学成为可能，也容易让人高估自己在多用户库上的可见性。

事务越长，在更忙的库上就越可能让别人等待。这里没有第二个连接，演示不了等待，我也不制造人为的等待。合适的长度就是不可分割的那几笔：挪一册的两次更新，或者插入后立刻决定撤销的那一组。把整个下午的交互都放在一个事务里，任何一个误点都会让你想把整下午一起扔掉。命运的宽度应当等于业务上不能只做一半的那一段，不多也不少。

只读的查询不必为了仪式而包进事务。数三本书有几册，一句 SELECT 就够。包进去也不会更正确，只会让读的人以为这里有写入要保护。保护是给多句写入的。单句查询没有「做了一半」的状态。把所有语句都包上 BEGIN，是一种看起来整齐的噪音，噪音会掩盖真正需要同生同死的那两句更新。整齐不是目标，边界刚好才是。

回滚不会把已经打印的输出从终端上擦掉。你若在回滚前打出了 6，回滚后打出了 0，两行都留在输出里。这不是事务失败，这是输出不参与回滚。输出是副作用，表才是事务的对象。读结果时按出现的顺序读：先看见的是草稿，后看见的是撤销之后的世界。不要因为两行矛盾就断定引擎错了。矛盾是你有意安排的证据。证据的力量恰好来自它们不一样。

约束失败若发生在事务中间，已经写进这一层的句子可能还悬着，也可能整层已经不能再继续。遇到这种情况，先回滚，让表回到 BEGIN 之前，再修数据。不要在失败之后接着 COMMIT，指望它替你保存「失败之前的那一半」。那一半若留下来，就是这一章努力避免的半截挪动。半截比完全失败更难发现，因为查询仍能看见一些合理的行，只是总数少了一册。少的那一册没有相反的一笔，账就静静地歪着。

提交成功之后，脚本后半可以把它当成普通的已写入数据来更新。那些更新又是新的自动提交，除非你再开一层。层与层之间不要假设还存在着「整个脚本是一个事务」。没有最外层的 BEGIN，就没有整个脚本的命运。每一段自己的 BEGIN 管自己的段。段与段之间，前一段已经不可撤销。设计脚本时把不可撤销的点写在你真的决定了的地方，而不是写在文件的自然段落后面。自然段落不是承诺。BEGIN 才是。

## 小结

BEGIN 把后面的写入绑成一个命运，COMMIT 让这一次脚本的后半看得见，ROLLBACK 让后半看得见「它们没了」。三本书插入后若整体撤销，计数是 0；提交则是 3。把一册从夜航挪到河岸，提交之后是 2、2，总和仍是 6。

提交不会让下一按 Run 还看见这些行。下一次仍是空库。隐式的关闭回滚也别拿来当证据，证据是显式 ROLLBACK 之后的查询。下一章把册数改写成一笔笔明细，在同一份脚本里建账、插入、求和、再撤销，让你看见账可以在打出来之后被同一份脚本抹掉。
