条件里的 2 一旦写死，它就只对今天这三本书诚实。夜航 3、河岸 1、旧书店 2，平均恰好是 2。你写 copies > 2，夜航留下，看起来像「高于平均」。明天河岸进货变成 10 册，平均挪走了，写死的 2 仍会把夜航留下，尽管夜航已经低于新的平均。高于平均这件事，右边的数应该从同一张表里算出来，而且跟左边的行用同一次运行里的数据。子查询就是把一个查询的答案交给另一个查询。

先算平均，再比。标量子查询放在比较的右边，括号里是一条应当只交出一个值的查询。AVG 正好交出一个值。整数的平均在这三本上是 2.0，夜航的 3 比它大，河岸和旧书店不比它大。旧书店等于平均，大于把它挡在外面。期望是夜航。不要写成大于等于，否则旧书店会混进来，你分不清自己比的是平均还是「达到平均」。

```sql run expect="夜航" title="高于平均的只有夜航"
CREATE TABLE books(title TEXT, copies INTEGER);
INSERT INTO books(title, copies) VALUES
  ('夜航', 3),
  ('河岸', 1),
  ('旧书店', 2);
SELECT title
FROM books
WHERE copies > (SELECT AVG(copies) FROM books);
```

把平均手写在注释里对照，可以；写进查询，就不可以。注释不会跟着进货变化，子查询会。这也是子查询比在程序里先查一次、再把数拼进下一条语句更稳的地方：中间没有第二次往返，也就没有人把旧的平均数粘进新的句子。在这个抽屉里本来也没有两次往返，整份脚本一次跑完。即便如此，仍不要先 SELECT 平均、肉眼读到 2、再写一个 2。肉眼是最容易把 2.0 看成「大概是 2」的设备。

子查询若放在 SELECT 的列表里，也会为每一行算一个值。问「比这本多的还有几本」，相关子查询引用外层这一行的册数。相关的意思是：里面的查询不能单独跑，它依赖外面正在看的那一行。夜航的 3 比另外两本都多，所以比它多的有 0 本。河岸的 1 比它多的有两本。这个数和连接能算出来的数可以相同，写法却把「对每一本分别提问」摆在字面上。

```sql run expect="夜航|0" title="有几本比这一本多"
CREATE TABLE books(title TEXT, copies INTEGER);
INSERT INTO books(title, copies) VALUES
  ('夜航', 3),
  ('河岸', 1),
  ('旧书店', 2);
SELECT title,
       (SELECT COUNT(*) FROM books AS other
        WHERE other.copies > books.copies) AS richer
FROM books
WHERE title = '夜航';
```

别名在这里不是装饰。里外都叫 books 的时候，列名会指错地方，里面的 copies 可能指到外面，条件变成自己和自己比，计数永远是 0 或者永远是全部，而且不报错。给里面起一个 other，条件写成 other.copies > books.copies，两本不同的书才真的在比。相关子查询写完之后，先挑一本你心算得清的书来核对。夜航是最清楚的一本：没有人比它多。

借出表回来一次，仍然是林和周借夜航、林借旧书店、河岸没有人借。这次不用连接，用相关子查询在 SELECT 列表里数借出。按身份排序，三行都会出现。河岸是 0。这个 0 是 COUNT 在零行上的结果，和空范围的 SUM 不同。计数零行得到 0，求和零行得到 NULL。两种空，两种函数，不要互相借用直觉。期望取旧书店|1，因为 1 比 0 更不容易被别的计数冒充，而旧书店恰好被林借了一次。

```sql run expect="旧书店|1" title="每本书各自数借出"
CREATE TABLE books(
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  copies INTEGER
);
INSERT INTO books(id, title, copies) VALUES
  (1, '夜航', 3),
  (2, '河岸', 1),
  (3, '旧书店', 2);
CREATE TABLE loans(book_id INTEGER, who TEXT);
INSERT INTO loans(book_id, who) VALUES
  (1, '林'),
  (1, '周'),
  (3, '林');
SELECT title,
       (SELECT COUNT(*) FROM loans
        WHERE loans.book_id = books.id) AS n
FROM books
WHERE title = '旧书店';
```

EXISTS 问的是「有没有至少一行」，不关心那一行的列。找被借走过的书，EXISTS 足够，而且里面选什么列都行，习惯上选一个常数。IN 则把内层的一列当成名单。两种写法在「没有 NULL」的这份借出数据上选出同样的书：夜航和旧书店。一旦名单里出现 NULL，IN 会重新掉进三值逻辑，未知让一些行既不被留下也不被明确拒绝，读起来像随机少行。EXISTS 不把 NULL 当成名单里的一个成员去比较，通常更好预测。这门课的借出没有空的身份，所以两种都能跑。我更愿意把 EXISTS 留给「有没有」，把 IN 留给「在不在一组已知的值里」。

标量子查询有一条我必须提前说得很难听的方言行为。标准希望右边的子查询若交出多行，就报错，因为「一个值」不成立。SQLite 常常不报错。它从那些行里取一行来用，语句退出码仍是 0。你写 copies = (SELECT copies FROM books)，右边其实有 3、1、2 三个数，引擎拿其中一个去比，结果可能只剩下夜航，看起来像查询成功而且很聪明。它不聪明。它只是拿了扫描先遇到的那个数。扫描顺序不是合同。数据一变，留下的书会变，而你以为规则没变。可运行的例子里我一律用 AVG、MAX、MIN 或 COUNT 把多行收成一个值，再放进标量的位置。你在旧代码里看见没有聚合的标量子查询，先假设它在抽签，再决定要不要改成聚合。

抽签之所以危险，是因为它在这三行上可能连续多次抽到同一个数，测试全绿。测试数据若总是按插入顺序扫描，抽到的永远是夜航的 3，高于或等于 3 的只有夜航，于是错误的查询拥有稳定的错误答案。稳定不是正确。把正确写进聚合函数，稳定性才属于你。

相关子查询的代价是每一行都可能再跑一遍里面的查询。三行无所谓。三千行再配一张没有索引的借出表，就会慢得让你怀疑连接写错了。这时连接加分组常常是同一种问题的更快写法，而且优化器对连接的准备比对「每一行一个小查询」的准备更充分。我不是在这一章禁止相关子查询。它在「对这一行提问」时最容易读懂。等读懂了、也慢了，再改成连接，并让两种写法在这三本书上交出同样的数字。数字不一致时，先怀疑相关条件把里外连错了，不要先怀疑数据库坏了。

子查询还可以出现在 FROM 里，给一块结果起名，再当作一张临时的表来过滤。例如先算出每个架子的和，再问哪个架子的和大于 3。架子是上一批数据里的甲和乙。这种写法和分组之后再套一层是一回事。层数多了，名字就要起得像业务，不要永远叫 t1、t2。t1 在三层之后没有人记得它是架子还是借出。

最后留一个否定的判断。子查询不是为了显示你能把 SQL 写成套娃。能用一个聚合回答的，不要套三层。这一章的平均只有一层，借出计数只有一层。层数是复杂度，不是水平。水平是你让右边的数跟着数据走，并且保证右边真的只有一个数。

子查询和连接常常能互相改写，但高于平均不能直接变成连接，因为平均是看完全表才有的一个数。你要先把平均做成一行，再让每一本书去和这一行比。那一行可以仍是比较右边的标量，也可以放进 FROM，起一个名字，主查询既过滤又把平均打出来。只比一次、不再展示时，我用右边的标量，短，而且 AVG 保证只有一个值。需要把平均和书名印在一起时，派生表更不容易让人把同一个子查询抄两遍，抄两遍就会有一天只改了其中一处。

相关子查询很容易写成意外的非相关。里面的条件若不再提到外面的列，它就变成一个独立的计数，每一行旁边都印着同一个数。夜航、河岸、旧书店看起来被同样地借过，像是连接条件写错了，其实是相关的那一根线断了。核对时挑两本你知道不一样的书。按现在的借出，夜航是两次，河岸是零次。两本一样，就回去看里面的 WHERE 还认不认识外面的身份。认不出，就不是在「对这一行提问」。

IN 的名单来自子查询时，空名单通常表示没有书被选中，这符合「没人借过」。名单里若混进空的身份，三值逻辑会让整份属于关系变得不确定，行可以消失得没有规律。借出的身份因此值得禁止为空。身份可以未知，这句话几乎没有好处，只会在名单里制造雾。雾不是可运行例子的一部分，是你加列时就要做的决定。决定晚了，查询会先「能跑」很久。

标量位置上的空也要单独看。全表还没有行时，平均是 NULL，册数大于 NULL 不会留下任何书，即便你随后插入了夜航。顺序在脚本里就是这样：先比后插，比的是空。先插后比，比的才是 2.0。子查询不会魔法般地看见写在它后面的插入。它看见的是它执行时已经在表里的行。这和事务里「自己能看见自己的草稿」不冲突。草稿也得先写进去。查询若放在插入之前，没有草稿可看。

相关子查询放在 SELECT 列表里，行被 WHERE 滤掉之后，里面的查询也不会为那一行运行。你只问旧书店，就不会为河岸再数一次借出。这是自然的，也提醒你：想核对河岸是 0，就要让河岸出现在外层的结果里。外层把它滤掉，你就失去了观察那个 0 的机会，只能以为「没打出来就是没有问题」。没有问题的证明是打出 0，不是沉默。沉默在这门课里已经有太多种意思。

一层子查询够用时，不要为了「先取出身份再取出书名」再套一层。身份在这三本书上就是 1、2、3，外层可以直接用。多一层就会多一个必须起名的派生表，名字若叫临时，读的人不知道它是平均、是借出还是书。名字应当说它是什么数。说不出来，往往是这一层并不需要存在。把不需要的层删掉，句子会短，短了之后相关的那一根线也更容易看见。看不见线的长句子，是抽签和真相关混在一起的温床。

## 小结

高于平均的门槛应当是 AVG 的子查询，不应当是写死的 2。在今天这批书上，只有夜航的 3 册跨过那条线。相关子查询让每一行带着自己的册数或身份再问一次，别名把里外分开，夜航比别人多出的本数是 0，旧书店的借出是 1。

多行却被放进标量位置时，SQLite 可能不报错，只悄悄取一行。那一行不是合同。要用聚合把多行收成一个值。零行的计数是 0，零行的求和是 NULL，两种子查询不要互相抄直觉。下一章处理「谁排在前面」。顺序在这之前都只是核对用的脚手架，现在要变成你对结果的承诺。

## 练习

查出册数等于全表最大册数的书名。应当是夜航。用 MAX 的子查询，不要把 3 写死。写死的 3 在有人把旧书店改成 4 之后会撒谎，子查询不会。

::: answer 册数最多的书
```sql run expect="夜航" title="最大来自表里"
CREATE TABLE books(title TEXT, copies INTEGER);
INSERT INTO books(title, copies) VALUES
  ('夜航', 3),
  ('河岸', 1),
  ('旧书店', 2);
SELECT title
FROM books
WHERE copies = (SELECT MAX(copies) FROM books);
```
:::

用 EXISTS 判断旧书店有没有借出。有则打出有，没有则打出无。按现在的借出，林借过，应当是有。CASE 的条件是 EXISTS 的真假，不要先数出来再和 0 比较，除非你确实需要次数。

::: answer 旧书店被借过吗
```sql run expect="有" title="存在即可"
CREATE TABLE books(
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  copies INTEGER
);
INSERT INTO books(id, title, copies) VALUES
  (1, '夜航', 3),
  (2, '河岸', 1),
  (3, '旧书店', 2);
CREATE TABLE loans(book_id INTEGER, who TEXT);
INSERT INTO loans(book_id, who) VALUES
  (1, '林'),
  (1, '周'),
  (3, '林');
SELECT CASE
         WHEN EXISTS (SELECT 1 FROM loans WHERE book_id = 3)
         THEN '有' ELSE '无'
       END;
```
:::
