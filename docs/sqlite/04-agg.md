过滤还是一行对一行。店长问的很多问题却不是一行：最少的那本有几册，最多的有几册，架子上一共有几册。这是把一袋行收成一个数。聚合函数做收成这件事。没有分组时，整张表是一袋。有分组时，每一袋交出一个数，于是结果又变成行，只不过行的身份换成了组的身份。

仍是那三个数。夜航 3，河岸 1，旧书店 2。你心算最小是 1，最大是 3，和是 6。查询把三个函数放在同一行，列表模式用竖线把它们拼起来。期望必须是 1|3|6 这一整段。竖线是默认分隔，不是我在字符串里另加的装饰，所以不要写成带空格的 1 | 3 | 6，那不是引擎交出来的样子。也不要依赖表头里的 MIN、MAX、SUM 这几个字，表头可以关掉，格子不会跟着改。

```sql run expect="1|3|6" title="最少、最多、一共"
CREATE TABLE books(title TEXT, copies INTEGER);
INSERT INTO books(title, copies) VALUES
  ('夜航', 3),
  ('河岸', 1),
  ('旧书店', 2);
SELECT MIN(copies), MAX(copies), SUM(copies) FROM books;
```

这一行之所以值得单独存在，是因为它把「聚合不是排序后取第一行」说死了。你当然可以按册数排序再取一头一尾，那是后一章的做法，要付出排序的代价，还要在并列时决定谁算第一。MIN 和 MAX 不关心谁是夜航，只关心数。SUM 把三本加在一起，不管它们在架子上的位置。三个函数一起写，是为了让你一次看见 1、3、6 的关系：最小、最大都来自这袋数，和也来自这袋数，它们不是三次互不相关的实验。

计数是另一种收成。COUNT(*) 数行，三本书就是 3。它和 SUM 回答的不是一类问题。和是 6 册，行是 3 行。把这两个数除一除，得到平均每本 2 册，那是 AVG 要做的事。AVG 给出的是实数，这三本恰好除尽，看起来像 2.0。除不尽时你会看到一条小数。需要整数平均时，回到上一章的整数除法，用 SUM 去除以 COUNT，而不是对 AVG 的结果睁一只眼闭一只眼。

空值会让这些函数分家。这一章的三行都有册数，所以 MIN、MAX、SUM 和你的心算一致。若某一行的册数是空，SUM 会跳过它，不把它当 0；COUNT(*) 仍数那一行，COUNT(copies) 不数。空袋上的 SUM 甚至不是 0，而是 NULL，因为没有数可加，和加出来等于零，是两种业务说法。这些差别我放到空值那一章用同一批书加一行样书来拆。现在不要用这三行的整齐去记住「聚合就是加总」这一句过分简单的话。整齐是我选的数据，不是函数的全部性格。

分组是把一袋切成几袋。给这三本书加一列书架，不改册数。夜航和河岸在甲，旧书店在乙。甲架的册数是 3 加 1 等于 4，乙架是 2。组的身份是书架，不是书。查询里除了聚合，只放分组的那一列。按书架名字排序，输出才稳定。乙的码点在甲前面，所以第一行是乙架。

```sql run expect="乙|2|1" title="按架子切开"
CREATE TABLE books(title TEXT, copies INTEGER, shelf TEXT);
INSERT INTO books(title, copies, shelf) VALUES
  ('夜航', 3, '甲'),
  ('河岸', 1, '甲'),
  ('旧书店', 2, '乙');
SELECT shelf, SUM(copies), COUNT(*)
FROM books
GROUP BY shelf
ORDER BY shelf;
```

乙|2|1 读作：乙架，册数和为 2，行数为 1。甲架那一行会跟着出现，和是 4，行数是 2。我把期望钉在乙这一行，是因为两个数字都小，不容易和「全体的总和 6」搞混。全体的总和仍在，你把分组去掉就会看见。分组没有丢掉书，它只是拒绝把不同架子的册数加进同一个格子。

这里有一条 SQLite 特有的纵容，我不打算当成可以写进报表的自由。标准希望你在 SELECT 里要么放分组列，要么放聚合。SQLite 默认允许你再放一个没分组的 title。甲架有两本书，引擎会从里面捡一本的书名交出来，不报错。捡到哪一本，不要写成合同。今天是夜航，明天可能仍是夜航，因为扫描顺序没变，可这不是承诺。报表上若印着「甲架的代表作是夜航」，而代表作只是捡来的，店长会拿它做决定。要代表作，就另写一个明确的规则，例如册数最大的那本，用后面的子查询或排序去取，不要用这种随便捡的列。我能跑的例子里不放这种列，就是为了不让期望依赖运气。散文里写出来，是为了让你在别人的旧脚本里认得它。

WHERE 和 HAVING 的差别是时机。WHERE 在分组前丢掉行。HAVING 在分组后丢掉组。若你只想要甲架，书的架子是行的属性，用 WHERE shelf = '甲'，然后不必分组也能求和。若你想要「册数和至少为 4 的架子」，这个 4 是组的属性，行上没有这列，只能 HAVING SUM(copies) >= 4。能用 WHERE 的时候我不用 HAVING。不是少写一个关键字的虚荣，是过滤越早，后面的聚合越不容易把不该进袋的行算进去。初学时两种写法经常凑出同一个数字，数据一多，时机的差别就变成两份对不上的日报。

第三份脚本先丢掉河岸，再对剩下的行做全体聚合，不用分组。条件是册数大于 1，留下夜航和旧书店，最小是 2，最大是 3，和是 5。这和第一份的 1|3|6 是同一批书的两种问法。河岸还在表里，只是没进这一袋。你若把 WHERE 写成 HAVING，在没有分组的查询里，HAVING 有时也能用，因为它把整张表看成已经聚好的一组。能用，但读起来像把过滤器放错了抽屉。行的条件放 WHERE。

```sql run expect="2|3|5" title="先拿掉河岸再加总"
CREATE TABLE books(title TEXT, copies INTEGER);
INSERT INTO books(title, copies) VALUES
  ('夜航', 3),
  ('河岸', 1),
  ('旧书店', 2);
SELECT MIN(copies), MAX(copies), SUM(copies)
FROM books
WHERE copies > 1;
```

2|3|5 和 1|3|6 差在河岸那 1 册。差本身就是这一章的教材：聚合回答的是「这一袋」，袋子由 WHERE 和 GROUP BY 决定。不写袋子，就默认整张表。默认很方便，也容易让人忘记自己正在把样书、残书、已下架的书都加进去。以后表变大，先写清袋子，再写函数。

DISTINCT 可以放进计数，回答「有几种」而不是「有几行」。三本书的书名都不重复，COUNT(DISTINCT title) 仍是 3，看不出差别。架子那一列才能看出：两行甲、一行乙，不同的架子只有 2。需要这个数时再写 DISTINCT，不要习惯性地给每个 COUNT 都戴上，它会掩盖「一行就是一件事」的那些统计，例如借出次数。借出还没进这一章。这里的行就是书。一本书一行，COUNT(*) 就是书的种数。哪一天你把每一次进货都插成一行，种数和行数就会分家，那时再请 DISTINCT 出场，不要提前。

平均值有一个温和的陷阱：它是实数，而且它悄悄跳过空值。跳过空值意味着「没填册数」不把平均拉低。若没填应当当成 0 册，你要先用替换把空变成 0，再平均，那是一个业务决定，不是函数默认的决定。默认是「未知不参加平均」。三本都有数的时候，默认和你的直觉重合，于是默认就藏起来了。藏起来的默认，就是以后对不上账时的第一疑点。

期望写成 1|3|6，也是在把分隔符当成教材。别的工具爱用逗号或制表符，久了你会以为分隔符是数据的一部分。这里的竖线来自列表模式的默认，批处理没有替你换成表格，也没有表头。若显示被改成一列一行，这段子串会消失，计算却可能仍是对的。课程把展示固定在默认上，三个函数才有稳定的外观。你要给别人读长句子时，可以在外面包一层拼接，那是展示；最小、最大和总和仍是那三个函数，不要为了好看改掉它们的含义。

分组的身份也可以是缺失。某一行没有填写架子，它不会混进甲，也不会混进乙，缺失自己成为一组。这一章没插入那样的行，是为了让全体的 1|3|6 先干净出现。你以后看见一个空名字的组，不要当成分组坏了。那是有行的值恰好是空。这一组里若册数也都是空，总和会是 NULL，组却存在。组在而数没有，和「这个架子从未出现」不是一句话。从未出现的丙架不会从单表分组里冒出来，因为没有行可以归到它名下。可能的架子若列在另一张表里，要先连接再分组，空架子才留得住。单表分组只报告发生过的值。

计数和总和对「根本没有行」的态度不同，分组把这件事放大成「某个名字根本没有组」。报表若必须列出全部架子，分组本身不够，你还需要一份完整的架子名单。三本书两只架子，名单的缺失还不刺眼。刺眼之前先记住：聚合描述的是有行的世界，不是你希望存在的世界。希望存在的那些零，要另找一张表来托住。

把三个函数放在同一行，还有一个阅读上的好处：你能看见它们共享同一只袋子。若分成三条查询，中间有人插入了第四本，三条结果可能来自不同的世界。在这个抽屉里虽然没有并发，写成一行仍然是好习惯，因为它声明「最小、最大、总和是同一次扫描意义上的三个数」。1 来自河岸，3 来自夜航，6 是三本一起。你对得上账，是因为数据小。数据大了，对账的方法仍是同一行里的三个格子，而不是三次运行拼起来的记忆。

分组之后的排序是对组排序，不是对书排序。按架子名字排，甲和乙的先后由编码决定，和哪本册数更多无关。若问题是「哪只架子更满」，应当按总和从高到低，而不是按架子的名字。名字排序适合目录，总和排序适合比较。两种都要写出来，不要假设分组的输出会按总和从大到小排列。它不会。没有排序的分组，谁在前仍是事故。乙架在前，只是因为这一次我按名字排了，而这个名字的码点恰好靠前。

HAVING 里也可以写计数。架子上的书少于两本就丢掉，乙架会被丢掉，甲架留下。这和 WHERE copies 不是一回事：WHERE 丢掉的是书，HAVING 丢掉的是架子。乙架上那本旧书店在分组前是完整的一行，它被丢掉是因为同伴太少，不是因为它自己的册数不合格。这个差别用两只架子就能演完。演的时候先心算甲是两行、乙是一行，再看结果里乙还在不在。还在，说明你把条件写到了行上；不在，说明你写到了组上。

## 小结

整张表是一袋的时候，夜航、河岸、旧书店的册数交出最小 1、最大 3、总和 6，三个格子由竖线连成 1|3|6。分组之后，袋子按书架切开，甲是两本共 4 册，乙是一本 2 册。SELECT 里不要顺手带上没有分组的书名，SQLite 会替你捡一本，报表不该靠捡。

行的条件用 WHERE，在进袋之前；组的条件用 HAVING，在出数之后。能早滤就早滤。空值会让总和、计数和平均各走各的，下一章先不处理空，先给这三本书配一张借出表，看一行书怎样配上多行借阅，配不上的河岸又会怎样从结果里消失。
