到目前为止，所有问题都问得了单张表。店里一旦出现「谁把书借走了」，硬把借阅人塞进 books 的某一列，会立刻不够用：夜航可以同时被两个人借，一个格子装不下两个人，除非你把名字拼成一段文本，然后再用子串去拆。拆文本是在逃避第二张表。第二张表才是这件事的形状。书仍是那三本，身份 1、2、3，册数仍是 3、1、2。新的只有借出。林借了夜航，周也借了夜航，林还借了旧书店。河岸没有人借。

借出表不复制书名。它记下书的身份和人的名字。书名只放在书的那张表里，这样改名时不必去借出记录里改许多行。身份对得上，就配成一行结果；对不上，就看你用的是哪一种连接。连接是按谓词配行，不是把两张表的列从腰上粘在一起。粘在一起是列的排列，配行是行的乘法加上条件。忘记条件，行数会变成两边行数的乘积，三本书乘三条借出会得到九行，每本书都好像被每个人借走了。那种写法老语法用逗号把表列在 FROM 里，条件补在 WHERE。漏了一个条件，不会有语法错误，只有一份荒唐的笛卡尔积。我不用逗号连接。把 JOIN 和 ON 写在一起，条件就有一个固定的家，漏了会在读的时候碍眼。

内连接只留下配得上的行。河岸的身份是 2，借出里没有 2，于是河岸不在结果中。这不一定是错。若问题是「哪些书被人借走过」，河岸本来就不该出现。错的是你没意识到它被丢掉了，还用这份结果去点库存。库存的问题要问书的表，不要问连接的结果。

```sql run expect="夜航|林" title="配得上的才留下"
CREATE TABLE books(
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  copies INTEGER
);
INSERT INTO books(id, title, copies) VALUES
  (1, '夜航', 3),
  (2, '河岸', 1),
  (3, '旧书店', 2);
CREATE TABLE loans(book_id INTEGER, who TEXT);
INSERT INTO loans(book_id, who) VALUES
  (1, '林'),
  (1, '周'),
  (3, '林');
SELECT books.title, loans.who
FROM books
JOIN loans ON loans.book_id = books.id
WHERE books.title = '夜航'
ORDER BY loans.who;
```

夜航配出两行，林和周。旧书店配出一行，林。期望钉在夜航|林，是两列都在的一个格子组合。排序让林排在周前面，这样子串的位置稳定。注意结果的行数已经不是书的行数。夜航一本变成了两行，因为借出有两行对着它。你若在这个结果上 COUNT(*)，数到的是借出记录的条数，不是书的种数。种数要把书的身份再分组，或者回到没有连接的那张表去数。连接改变了「一行代表什么」。这个改变比记住 JOIN 这个单词重要。

左连接以左边的书为全部班底，右边配不上就用空补上。河岸会回来，借阅人那一列是空。空不是空字符串，是 NULL。打印出来像空白，类型是 null。下面不直接打印那个空白，空白太容易和「没输出」混在一起。改成计数。对左连接的结果按书分组，COUNT(*) 数配出来的行，河岸即便没有借阅也有一行，所以是 1。COUNT(loans.who) 数借阅人这一列里非空的格子，河岸那一格是空，所以是 0。两个数并排，河岸|1|0。夜航是两行且两行都有人，会是夜航|2|2。旧书店是 1 和 1。差别只在河岸身上显出来，所以期望写河岸这一行。

```sql run expect="河岸|1|0" title="没人借也留在左边"
CREATE TABLE books(
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  copies INTEGER
);
INSERT INTO books(id, title, copies) VALUES
  (1, '夜航', 3),
  (2, '河岸', 1),
  (3, '旧书店', 2);
CREATE TABLE loans(book_id INTEGER, who TEXT);
INSERT INTO loans(book_id, who) VALUES
  (1, '林'),
  (1, '周'),
  (3, '林');
SELECT books.title, COUNT(*), COUNT(loans.who)
FROM books
LEFT JOIN loans ON loans.book_id = books.id
GROUP BY books.id
ORDER BY books.id;
```

若你只用 COUNT(*) 去回答「被借了几次」，河岸会显示 1，店长会以为有人借了它。错在函数，不在连接。左连接的价值是保住左边的每一本书，代价是配不上的行带着空。空让计数函数分家，这和整表上 COUNT(*) 与 COUNT(列) 的分家是同一件事，只是空的来源变成了「配不上」，不一定是你插入时就写了空。读连接上的聚合，先问空是从哪来的。

右连接和全外连接在别的方言里对称地存在。SQLite 没有右连接这个写法，你把表的位置换一下，左连接就够了。不要为了对称去找一个不存在的关键字。全外连接这里也不作为可运行的工具。这三本书的问题用左连接已经能说完：以书为准，还是以借出为准。以借出为准就是内连接，或者干脆从 loans 出发去连 books。从哪张表出发，是问题的主语，不是排版。

还有一种安静的错误：ON 写成了永远为真，或者写成了书名相等但两边都没有约束到身份。行会爆开。三行对三行你还能眼看出来九行不对，三百行对三百行就只能看总数发呆。写完连接先数行，再看内容。行数若等于两边行数的乘积，先怀疑条件没有真正限制任何东西。条件写在 WHERE 里而不是 ON 里，对内连接常常仍能得到同样的行，对左连接则会把「配不上」的那些行再滤掉，因为空和任何值的比较都不是真。左连接的条件放错地方，河岸会再次消失，你还以为自己写了左连接。ON 放配对条件，WHERE 放「配对完成之后还要的业务条件」，例如只要林借的。两者不要挤在一个子句里图省事。

身份是整数。有人用书名连接书名，小表上能跑，改名和重名会让它垮掉。这三本书的名字碰巧都不重，所以书名连接会得到和身份连接一样的结果，于是你觉得身份是多此一举。重名一旦出现，书名连接会把借出配到每一本同名书上。主键的意义在连接这一章才完全落地：它不是为了让你有个数可以打印，是为了让另一张表有一个不会漂的靶子。

外键约束本可以让借出里的身份必须真有这本书。SQLite 默认不打开这道门。不打开时，你插入一条 book_id 为 99 的借出，语句成功，连接时只是配不上。打开之后，同样的插入会失败。失败的脚本我不放进可运行的例子。可运行的这一份只插入 1 和 3，都是存在的书。你要知道默认是敞开的，所以「表能插进去」不等于「身份一定合法」。合法性若重要，要在脚本里明确打开那道开关，并准备好接受失败的退出码；在这门课的核对里，我用正确的身份绕开失败，把注意力留在配行上。

第三份只问林借走了哪些书，条件放在 WHERE，连接仍是内连接。林借了夜航和旧书店。按身份排序，先夜航后旧书店。期望用旧书店，避免和上一份夜航|林 重复得无法区分你到底跑了哪一段。

```sql run expect="旧书店" title="只要林借走的"
CREATE TABLE books(
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  copies INTEGER
);
INSERT INTO books(id, title, copies) VALUES
  (1, '夜航', 3),
  (2, '河岸', 1),
  (3, '旧书店', 2);
CREATE TABLE loans(book_id INTEGER, who TEXT);
INSERT INTO loans(book_id, who) VALUES
  (1, '林'),
  (1, '周'),
  (3, '林');
SELECT books.title
FROM books
JOIN loans ON loans.book_id = books.id
WHERE loans.who = '林'
ORDER BY books.id;
```

周只借了夜航，所以把人换成周，旧书店会从结果里消失。人是借出表的列，不是书的列。写 books.who 会直接报没有这列。列的归属在连接里必须写清楚，尤其两边若出现同名列。这一对表里，id 和 book_id 不同名，是故意的：同名会让人误以为自然就相等。不相等，除非你写下等号。自然连接按同名列自动配对，我不用它。自动配对在列改名时会悄悄改变配上谁，读脚本的人看不见那个等号，也就看不见风险。等号写出来，靶子就写出来了。

连接之前先问主语。主语是书，左边就是书的表，河岸才有机会在无人借阅时留下来。主语是借阅这件事，左边就该是借出表，没有借出的书不该出现。许多看起来像连接写错的结果，其实是主语选错了，函数再正确也在回答另一个问题。夜航被两个人借走：主语是书时，它是一行配一个次数；主语是借阅时，它是两行。界面要印哪一种，就从哪一种出发。连完之后再在外面折叠，折叠的规则也该写回 SQL，否则界面和查询各说各的话。

同名列加上表名，是句子的精度。这份数据里书名和借阅人不同名，省略前缀也能跑，于是省略看起来无害。等两边都有了你随手起的同名列，不写前缀会因为歧义而报错，这还算幸运，因为它响了。不响的是前缀写错，指到另一张表上恰好同名的列，配出一份像结果的错结果。三行的例子里我把表名写全，是让眼睛习惯精度。习惯省略的人，会在第一次真的歧义时不知道该给哪一边加前缀。

借出上的身份若重复很多，长久的库会想给那一列做索引，让连接不必每次扫描全部借出。三行看不出差别，也不该为了看不见的差别提前优化。谓词还没写对时，索引只会让错误的配对来得更快。先让河岸在该出现的查询里出现、在不该出现的查询里消失，再谈快慢。快慢不是这一章的正确性。正确性是身份对上了谁。

一对多是这份借出的形状：一本书对多条借出，一条借出只指向一本书。把形状记反，你会在书的表里为每个借阅人加一列，列永远不够。夜航已经需要两个人。第三个人来的时候，加列的方案就要改表。加行的方案只要再插入一条借出。所以第二张表不是为了显得正规，是为了让「再多一个人」变成插入而不是改结构。改结构在空库的脚本里不值钱，在有历史借出的库里很值钱。现在就用行来表达重复，是把值钱的习惯提前养成。

连接的结果还可以再过滤册数。只要被借过、并且册数至少为 2 的书，夜航和旧书店都在，河岸两边都不占。条件放在 WHERE，配对仍放在 ON。若你把册数条件误放进 ON，内连接上看起来常常一样，左连接上会不一样：配不上的河岸本来该留着，结果因为册数条件在配对时失败，又被扔掉。你以为左连接失效了，其实是条件站错了队。站队的规则很短：谁和谁是同一本，写在 ON；这本书还要满足的生意条件，写在 WHERE。

借出人不重复地数，要用另一种计数。林借了两本，若问有几个人借过店里的书，按行数会把林算两次。不同的人只有林和周，是二。这个数等你真的要「读者人数」时再写，不要和「借出条数」混用同一个词。条数是三，人数是二。两个中文在口语里都叫「多少借阅」，SQL 里必须分成两种函数用法。分不清的时候，先问自己丢掉重复之后，林还应该剩几次。应该剩一次，那就是人数；应该剩两次，那就是条数。

## 小结

借出是第二张表，书还是夜航、河岸、旧书店。内连接回答「配得上的借阅」，河岸因为没有借出而不在结果里。左连接回答「每一本书的借阅情况」，河岸留下，借阅人是空。在这个空上，COUNT(*) 是 1，COUNT(借阅人) 是 0。拿错函数，库存报表会多出一次不存在的借阅。

配对条件写在 ON 里，用身份而不用册数，也不用可能重名的书名去凑合。逗号把表排在一起很容易漏掉条件，漏掉就是行数相乘。下一章回到单张书表，改册数、删掉河岸，并且立刻查询，证明改的是存储，不是这一次投影的滤镜。
