字面量算得再准，也只活在那一条语句里。店要打烊之后还认得出存货，就得有一张表把书名和册数按行摆好。这里的「打烊之后」只到这次脚本结束为止，你已经知道下一次 Run 会把桌子擦掉。即便如此，表仍然有意义：它让后面的语句按名字取数，而不是把 3、1、2 再抄一遍。抄写会分叉。表里的行只有一份，过滤、汇总、修改都对着这一份。

建表是在给关系起名字，并列出列。我把表叫做 books，列叫做 title 和 copies。类型写上 TEXT 和 INTEGER，但你要立刻放弃一种从别的数据库带过来的期待：这些字不是监狱。SQLite 用的是亲和，一种「尽量存成这个样子」的偏好，不是「不符合就拒绝」的门卫。偏好对能转换的值会转换，对转换不了的值会照单全收。这就是为什么同一列里后来可能躺着两种类型。声明仍然要写。它是给人看的意图，也是后面约束可以附着的地方。不写声明，列一样能用，可读脚本的人不知道这列想装册数还是想装备注。

第一份脚本只放进夜航，而且按列名插入。列名写出来之后，值的顺序跟着列名走，不跟着建表时的顺序走。我故意把 copies 写在 title 前面。3 先进列名列表，夜航跟在后面，落进表里仍然是书名对书名、册数对册数。若你省略列名，值就按建表顺序对位，明天有人在中间加了一列，旧的插入会整行错位，而且常常不报错，只是书名栏里出现一个数字。那种错比语法错误贵得多。三行的教学表看不出代价，三十列的业务表会看出来。所以这门课的插入从第一行起就写列名。

```sql run expect="夜航|3" title="先放进夜航"
CREATE TABLE books(title TEXT, copies INTEGER);
INSERT INTO books(copies, title) VALUES (3, '夜航');
SELECT title, copies FROM books;
```

终端若在插入之后仍然空白，你没有失败。失败会有错误文本，退出码也不会是 0。空白表示这条语句没有结果集。紧跟的查询才是证据。证据要具体到格子：书名和册数都在，才算这行被放对了位置。只查计数，会把「插进了一行垃圾」也算成功。

第二份脚本把三本书一次写完。多行插入用逗号隔开每一组括号，组与组之间是同一条语句。夜航 3，河岸 1，旧书店 2。次序我按讲述的顺序来，不按册数排序。表不负责排序。你这一次看见的行顺序，可能碰巧是插入顺序，那是存储留下的痕迹，不是合同。合同要到排序那一章才签。这里核对河岸，用书名把行钉死，这样就算引擎哪天换了扫描顺序，期望还在。

```sql run expect="河岸|1" title="三本一次写完"
CREATE TABLE books(title TEXT, copies INTEGER);
INSERT INTO books(title, copies) VALUES
  ('夜航', 3),
  ('河岸', 1),
  ('旧书店', 2);
SELECT title, copies FROM books WHERE title = '河岸';
```

一次写多行和写三次单行，在这张没有额外触发器的表上结果一样。差别在失败的边界：一条语句里的多行是一起被处理的，中间某一行违反了约束，整条语句退回，不会留下「前两行已经进表」的半截。三次单行则是三次自动提交，第二行失败时第一行已经留下。这一章还没加会失败的约束，所以你看不到半截。等事务和约束出现时，请记得多行括号并不是为了少写两个字，它把若干值绑成一条语句。现在先用它把三本书当成一批存货放进去。

亲和需要一次亲眼看见，否则 INTEGER 会让你以为脏数据进不来。第三份脚本仍是这三列的表，但插入时做两件不合直觉的事。夜航的册数写成文本 '3'。河岸的册数写成文本 '一'，这个字不是数字。然后再插入真正的旧书店，册数是整数 2，用来证明同一张表可以混合你的正常写法和那些试探。查询不直接打出册数的显示文字，因为 '3' 被转换之后看起来和 3 一样，眼睛会被骗。打出类型名。夜航那一格的类型是 integer，说明文本 '3' 被亲和收成了整数。河岸那一格的类型是 text，说明「一」转换不成整数，于是以文本留下。列声明没有拒绝它。

```sql run expect="integer|text" title="亲和会收数字，不会拦汉字"
CREATE TABLE books(title TEXT, copies INTEGER);
INSERT INTO books(title, copies) VALUES ('夜航', '3');
INSERT INTO books(title, copies) VALUES ('河岸', '一');
SELECT
  (SELECT typeof(copies) FROM books WHERE title = '夜航')
  || '|' ||
  (SELECT typeof(copies) FROM books WHERE title = '河岸');
```

这就是我不把类型声明讲成校验的原因。校验若存在，应当失败得响。亲和失败得不响，它留下一个类型不同的值，以后的比较和求和会按另一套规则处理这个值。文本和整数比大小，结果可能让你以为河岸的册数很大或很小，取决于转换碰巧怎么走。正常的插入请写不带引号的整数。引号留给书名。如果你从一张外部清单把数字当文本读进来，先在进表之前想清楚要不要转换，不要等亲和替你做一半。

主键这一章开始承担一点责任，但我不把它说成性能魔法。id 是每一行的身份，整数主键在 SQLite 里还会和内部的 rowid 叠在一起，空着不写时会自己往下数。身份有什么用，要到借出表用书的身份去指向它时才完全显出来。现在先让三本书各自有 1、2、3 这三个身份，并且书名不再允许空着。空书名不是空字符串那一类「有个值，值是空的」，那是下一类问题；这里的 NOT NULL 是「这列必须有值」。下面的脚本全部供给了值，所以它能跑完。若你删掉某一行的书名再运行，会看到 NOT NULL 约束失败，语句停住，后面的查询可能不会执行。那种脚本不放进可运行的例子，因为退出码不再是 0，期望也就失去了着落。你只要知道门卫是约束，不是类型名。类型名 INTEGER 挡不住汉字「一」，NOT NULL 挡得住「这里什么都没写」。

```sql run expect="旧书店|3" title="给每一本一个身份"
CREATE TABLE books(
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  copies INTEGER
);
INSERT INTO books(id, title, copies) VALUES
  (1, '夜航', 3),
  (2, '河岸', 1),
  (3, '旧书店', 2);
SELECT title, id FROM books WHERE copies = 2;
```

旧书店的册数是 2，身份是 3。这两个数字不要互相替代。2 是有几本，3 是它是谁。后面的连接用身份，不用册数。用册数去连接是一种常见的偷懒：两本书碰巧都剩 2 册时，它们会被当成同一本。身份重了才会被主键拒绝。册数重了是生意，不是数据错误。

省略身份让引擎自己编号，也可以。插入时不写 id，第一行会得到 1。这很方便，也容易让人把「第一行」当成业务概念。编号是存储给你的，删除后再插入，旧的编号不一定复用，也不一定不复用，视你有没有提出更强的要求。这门课需要稳定身份时就亲手写下 1、2、3，不把「谁是第一本」交给自动编号的心情。

建表语句写错了想改，SQLite 允许你加列，却不鼓励你随意改列的含义。教学脚本比修改旧表更干净的办法，是整份重来：下次 Run 本来就是空的，你改正 CREATE，再插入。在长久的库上你没有这种奢侈，要写迁移。在这里，重跑就是迁移。不要为了模仿生产而在一份教学脚本里堆许多 ALTER。那会把读者的注意力从「行是什么」拉到「方言允许改哪些元数据」上。元数据的限制等你真的要改一张有数据的表时再查文档，不值得占掉存货这一章。

SELECT * 能把所有列打出来，写起来短。我仍然在核对用的查询里点名 title 和 copies。点名的好处是列的顺序由你决定，期望里的竖线左右是稳定的。星号的顺序跟着建表走，有人把 id 加到第一列，原来的「书名|册数」会变成「身份|书名|册数」，子串可能还在，也可能被新的列插到中间。期望若只写书名，星号无害；期望若写相邻的两列，星号就是一处未来的断裂。核对是一种写作，不是一种偷懒。

有人问，下次运行既然全空，为什么不把三本书留在宿主语言的列表里，省掉建表。因为这一门要练的是按名字取一组行。过滤、汇总、连接都是对关系说的。数据若留在外面，再逐条拼进语句，你会回到用引号把值嵌进文本的老路，而那条路在字面量一章刚刚被双引号绊过。表是边界：里面是值，外面是语句。夜航这两个字进了表，后面的条件只写列名，不必在每一句里再抄一遍书名。抄写看起来短，改一个字就要改许多句，三本书的教程还改得动，三十个条件就改不动了。

默认值可以写在列上。册数若声明成省略时为 0，你就是在店规里宣布「没写就算没有库存」。0 是数过的结果。样书那种还没数，不该被默认填上。这一章的插入把册数都写全了，默认值不会露面。抄到别人的建表语句时，看见默认就要停下来问：这个数是观察，还是替缺失做的填充。填充一旦进了行，后面的求和无法分辨它是不是人手填的。

普通表还有一个你没声明也会存在的内部编号。把整数主键写成完整的 INTEGER，这个主键就会和内部编号重合，旧书店的身份是 3 时，内部编号也是 3，不会出现两套身份。写成别的整数类型词，重合可能不发生，你于是有一个业务编号、一个存储编号，连接时接错一个，借出就指向陌生人。教学脚本把词写全，就是为了让这一套身份从第一天起只有一个意思。

## 小结

表把夜航、河岸、旧书店从一闪而过的字面量变成可以按名字反复读取的行。插入时写下列名，值就不会因为明天多了一列而悄悄错位。插入本身常常没有输出，查询才是证据。

类型声明表达意图，亲和却会把 '3' 收成整数，把「一」当成文本留下。真正会拒绝写入的是约束，例如主键和不允许空。身份和册数是两种数，旧书店的身份是 3、册数是 2。下一章不增加书，只在这三行上写条件，把不该留在柜台上的行滤掉。

## 练习

建一张只有书名和册数的表，列名列表里先写册数再写书名，插入旧书店 2 册。查出书名，确认错开的书写顺序没有把 2 塞进书名栏。

::: answer 列名决定对位
```sql run expect="旧书店" title="册数写在列名的前面"
CREATE TABLE books(title TEXT, copies INTEGER);
INSERT INTO books(copies, title) VALUES (2, '旧书店');
SELECT title FROM books;
```
:::

三本书都插入，身份手写为 1、2、3。查出册数大于 1 的有几行。夜航和旧书店应当留下，河岸不进这个计数。

::: answer 两本册数超过一
```sql run expect="2" title="大于一册的行数"
CREATE TABLE books(
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  copies INTEGER
);
INSERT INTO books(id, title, copies) VALUES
  (1, '夜航', 3),
  (2, '河岸', 1),
  (3, '旧书店', 2);
SELECT COUNT(*) FROM books WHERE copies > 1;
```
:::
