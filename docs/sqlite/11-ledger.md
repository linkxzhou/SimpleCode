存货表上的册数是一个现状。现状回答不了「这一册是什么时候进来的，卖掉的那一册有没有记上一笔」。把现状当成唯一的记录，更新会把历史盖掉。盖掉之后，总和仍能对上今天的架子，对不上昨天的进货单。账本反过来记。每一行是一笔，不改旧行。现状是 SUM 算出来的，不另存一个容易和明细打架的余额列。余额列看起来省一次求和，代价是每一笔写入都要记得去改它。忘记一次，余额和明细就永久分家，而你还不知道该信哪一个。信明细，让余额每次现算。三本书的规模根本不需要为这个求和担心。

明细的形状很瘦：哪本书，这一笔是多少。进货写成正数，售出写成负数。夜航进 3，河岸进 1，旧书店进 2，三笔都在事务里提交。求和得到 6，和当初那三本的册数一样。一样是对的，因为我们只是把现状拆成了三笔进货，还没有卖。按书名分组，夜航自己的和是 3。分组存在，是为了让「一共」和「某一本」都从同一批明细里长出来，而不是一本看余额、总共看别的表。

```sql run expect="6" title="三笔进货的和"
CREATE TABLE lines(title TEXT, n INTEGER);
BEGIN;
INSERT INTO lines(title, n) VALUES ('夜航', 3);
INSERT INTO lines(title, n) VALUES ('河岸', 1);
INSERT INTO lines(title, n) VALUES ('旧书店', 2);
COMMIT;
SELECT SUM(n) FROM lines;
```

售出不回去改那笔进货。夜航再插入一笔 -1。历史变成两行：3 和 -1。和是 2，正好等于上一章卖掉一册之后的现状。旧行还在，你可以看见进过 3。若当时用更新把 3 改成 2，进货这个事实就没了。负数看起来像脏数据，其实是方向。没有方向的账只能记录残差。检查约束可以禁止你把某一种业务写错符号，例如退货必须为负、进货必须为正，那是店规加严，不是明细这种形状本身的错误。这一份先不加那道门，让 -1 能够表达售出。

```sql run expect="2" title="售出是新的一笔"
CREATE TABLE lines(title TEXT, n INTEGER);
INSERT INTO lines(title, n) VALUES
  ('夜航', 3),
  ('河岸', 1),
  ('旧书店', 2);
INSERT INTO lines(title, n) VALUES ('夜航', -1);
SELECT SUM(n) FROM lines WHERE title = '夜航';
```

夜航的 2 不等于全店的和。全店是 5，因为只卖掉了一册，河岸和旧书店的进货还在。问全店还是问一本书，WHERE 要写清楚。不写 WHERE 的 SUM 是全店。写错书名的 SUM 可能是 NULL，因为没有行，空范围的和不是 0。账本上这个 NULL 尤其容易被读成「这本书的余额是空，所以是零」。上一章已经把这个坑挖开了。在账上再掉进去，就会把没进过货的书和进过又退光的书看成一样。退光是若干笔加起来等于 0，0 是数字。没进过是没有行，没有行的和是 NULL。COALESCE 可以在给店长的那一格上把 NULL 显示成 0，可清单本身不该因此删掉这个区别。

现在把建表、插入、求和、回滚收进同一份脚本。这是这一章要你亲手跑通的那一件事，不是三份脚本拼起来的想象。事务里插入三笔进货，先求出和，这个和应当是 6，说明草稿在提交前已经能被自己的连接看见。紧接着 ROLLBACK，不提交。再数行，应当是 0。再问总和是不是 NULL，应当是 1。三个结果都出现在同一次输出里：先是 6，然后是 0，然后是 1。期望抓 6 会太容易和别的数撞车，所以求和时给它一个前缀，让格子变成合计6。撤销之后的计数带上另一个前缀。两个前缀都在同一份输出里，才证明「先看见和，随后又抹掉」发生在同一次运行，而不是你回忆了两次按钮。

```sql run expect="合计6" title="先加总，再整笔撤销"
CREATE TABLE lines(title TEXT, n INTEGER);
BEGIN;
INSERT INTO lines(title, n) VALUES ('夜航', 3);
INSERT INTO lines(title, n) VALUES ('河岸', 1);
INSERT INTO lines(title, n) VALUES ('旧书店', 2);
SELECT '合计' || SUM(n) FROM lines;
ROLLBACK;
SELECT '剩下' || COUNT(*) FROM lines;
SELECT SUM(n) IS NULL FROM lines;
```

输出里还会有剩下0，以及最后的 1。我把期望放在合计6，是因为那是撤销之前的草稿总和，最能说明查询可以读未提交的自己的写入。剩下0 证明回滚写进了这张表的现状。最后的 1 证明空账的和不是数字 0。三个句子缺一，这个故事就变成普通的插入。你若把 ROLLBACK 写成 COMMIT，合计6 仍在，剩下0 会变成剩下3，期望里的合计6 还在，所以单靠这一个子串抓不住「你是不是真的撤销了」。练习会专门核对剩下0。正文这一份把撤销放在脚本中央，请你把输出读完整，不要只让眼睛停在期望四个字上。

为什么允许在回滚前先查询？因为事务不是一块不许看的黑箱。黑箱会逼人在提交之后才发现插错了书。先看合计，确认是 6，再决定提交还是撤销，这是事务对作者的用处。在这份教学脚本里，决定已经写死为撤销，好让结果可重复。在你自己的账上，决定可以来自合计是不是你预期的那个数。预期不对就回滚，表回到 0 行，没有半笔进货留下。这比自动提交安全，也比「先插入，再写一条反向插入去抵消」更干净。反向插入是业务上的退货。退货要留在账上。试验性的进货草稿不该伪装成退货。

再看一笔必须同生同死的双分录。从夜航挪一册给河岸，在明细里不是去改册数，而是两笔：夜航 -1，河岸 +1。两笔的和是 0，全店总和不变。它们必须在同一个事务里。只插入了夜航的 -1 就失败，账上会少一册。下面提交这对话，再看全店的和，应当仍是 6，因为三笔进货已经在事务外提交过了，挪动的两笔和为 0。

```sql run expect="6" title="挪动不改变全店的和"
CREATE TABLE lines(title TEXT, n INTEGER);
INSERT INTO lines(title, n) VALUES
  ('夜航', 3),
  ('河岸', 1),
  ('旧书店', 2);
BEGIN;
INSERT INTO lines(title, n) VALUES ('夜航', -1);
INSERT INTO lines(title, n) VALUES ('河岸', 1);
COMMIT;
SELECT SUM(n) FROM lines;
```

夜航的分户和变成 2，河岸变成 2，旧书店仍是 2。全店 6。这和更新现状表时看到的 2|2|6 是同一个生意，记录的方式不同。现状表丢掉了「曾经进过 3」；明细留着 3 和 -1。留着的代价是行数变多，现状必须算。我接受这个代价。账的职责是让一笔无法被悄悄改写，不是让某一格永远等于架子上的册数。架子上的册数是算出来的视图，不是另一份可以手改的真相。

这门课走到这里，前面的判断都在这份账上有一个位置。每次运行是空的，所以脚本从建表开始，不连接上次的文件。字面量那一章的整数规则仍然管着 -1 和 3，它们是整数，不是文本。过滤用来切出某一本书的分户。聚合用来求 6。连接在这张瘦表上可以暂时不用，若你另有一张只存书名的目录，再用身份连回去，避免明细里的书名和目录里的书名各改各的。空值那一章解释了为什么没进过货的书不能显示成和退光一样的 0，除非你明确替换。子查询可以找出「分户和大于平均」的书，而不把平均写死。排序决定清单上谁在前。事务决定挪动的两笔会不会只留下一半。没有一个关键字是为了凑章节目录才出现的。

不要给这份账加 JSON 列来存放「任意附加信息」。附加信息若值得查询，就值得成为列或成为另一张表。也不要 ATTACH 一个下次还在的文件来假装这个抽屉有记忆。记忆若需要，是你把同一份脚本一次跑完，在同一次输出里把合计和撤销都打出来。输出才是这次运行留给你的东西。表不是。

人名若出现在账上，例如林付款、周退款，那是另一列，不是另一套书。书仍是这三本。按人名汇总是 GROUP BY，按书名汇总也是。两个维度不要揉进一个文本字段再去 LIKE。揉字段的冲动，在借出那一章已经拒绝过一次，账上再拒绝一次。

分户和全店用的是同一个求和，差别只在条件。有人给每本书存一个余额，再存一个全店余额，漏记一次之后三个数各说各话，你不知道该信哪一个。现算没有第二份可漏的数。行数大了会慢，慢的时候给书名准备索引，或者把已经结清的月份做成汇总，那是速度上的设计，不是把模型改回「余额才是真相」。真相仍是一笔笔明细。汇总表若存在，它必须能被明细重新算出来，算出来对不上时，改汇总，不改历史。

前缀是展示，不是一笔账。我把合计和数字黏在一起，是为了让期望拥有独一无二的子串，免得单独一个 6 在输出里到处都能撞上。账的列只有书名和这一笔的数。不要为了好查而把「合计」插入表中。那一行会被下一次求和再次加进去，全店的和就虚高。展示留在查询的表达式里。表里只留发生过的进出。

回滚前的合计和回滚后的行数出现在同一次输出里，是这份空库能给你的最强证明：脚本的前半和后半看见不同的世界，运行却是同一次。库若不是空的，行数不是零可能因为旧数据还在，你分不清回滚没生效，还是上一份脚本的残留还在。残留在这个抽屉里不存在。空因此到最后一章仍是证据的条件，不是开篇用过就可以忘掉的开场。

## 小结

余额不是存出来的，是三笔进货加起来的 6，是夜航的 3 再加一笔 -1 之后的 2。旧行不涂改，退回和售出都是新行。同一份脚本可以先打出合计6，再 ROLLBACK，让行数回到 0，让空表上的和变回 NULL。草稿看得见，不代表草稿必须留下。

挪一册是夜航的 -1 加上河岸的 +1，两笔一个事务，全店的和仍是 6。下一次 Run 不会记得这份账。要记得的是写法：空库、自足的脚本、用查询证明、用事务绑定命运、用明细而不是用覆盖来记账。整数除法、双引号、空值比较这些安静的规则，还会在你离开这三本书之后继续生效。
