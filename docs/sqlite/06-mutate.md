过滤和连接都只决定这一次看见哪些行。打烊结账时，夜航卖掉一册，存储里的 3 必须变成 2，否则下一次查询还会把卖掉的那册卖一遍。在这个抽屉里并没有真正的「下一次」，同一份脚本后半段的查询就是下一次。UPDATE 改已有的格子，DELETE 拿掉整行。两者都不像 SELECT 那样交回一张结果表。批处理里它们通常没有可核对的输出。证明改过了，只能再查。

先看见改之前的夜航，免得你把插入时写错的数当成更新的结果。三本书照旧。查询只取夜航的册数，格子是 3。这一份什么都不改。它存在，是为了让后面的 2 有一个对照物。对照物必须来自同一批插入，而不是来自记忆。

```sql run expect="3" title="改之前夜航还有三册"
CREATE TABLE books(title TEXT PRIMARY KEY, copies INTEGER);
INSERT INTO books(title, copies) VALUES
  ('夜航', 3),
  ('河岸', 1),
  ('旧书店', 2);
SELECT copies FROM books WHERE title = '夜航';
```

书名当主键，是因为这一章按书名改、按书名删，不引入借出。书名重了会被拒绝。三本书不重，所以主键不妨碍插入。册数仍然不是身份。

第二份把夜航的册数减 1。SET 里写 copies = copies - 1，不要写 copies = 2，除非你的业务就是「盘点后改为绝对数量」。减 1 表达的是卖掉一册，和当前值有关。绝对赋值表达的是「不管原来几册，现在就是这些」。两种句子在当前数据上都能把 3 变成 2，意思却不同。若有人已经把夜航改成过 4，绝对赋值会把那次盘点盖掉，减法不会。教学数据只有一份，更要在句子里留下意图。WHERE 把目标钉在书名上。没有 WHERE 的更新会改每一行，三本书都变成各自减 1，河岸变成 0，旧书店变成 1。引擎不会问你「确定吗」。批处理也没有确认提示。确定是你的 WHERE。

```sql run expect="2" title="卖掉一册之后"
CREATE TABLE books(title TEXT PRIMARY KEY, copies INTEGER);
INSERT INTO books(title, copies) VALUES
  ('夜航', 3),
  ('河岸', 1),
  ('旧书店', 2);
UPDATE books SET copies = copies - 1 WHERE title = '夜航';
SELECT copies FROM books WHERE title = '夜航';
```

查出 2，才算卖掉了。若你忘记写更新，查出的仍是 3，期望对不上，这正是我们想要的警报。不要把期望改成 3 来迁就一份没更新的脚本。也不要只看退出码。退出码只说明语句没有失败，不说明改到了你想改的那一行。WHERE 写成一个谁都不等于的书名，更新成功，影响零行，查询仍给出原来的 3。成功和生效不是一个词。

想在更新之前知道会碰着谁，先把同一个 WHERE 放进 SELECT。选出的行就是将被改的行。这一章的条件很短，你觉得多此一举。条件一旦变成「书名模糊匹配并且册数低于某个数」，先查一次能救下整架书。我把这个顺序当成习惯，而不是当成一条只有生产环境才配使用的手续。习惯在三行的表上养成，才有机会在三百行的表上生效。

删除比更新更没有回收站。第三份脚本先卖掉夜航的一册，再把册数小于 2 的行删掉。此时河岸仍是 1，会被删掉；夜航已经是 2，留下；旧书店本来就是 2，留下。查询把剩下的行按书名排序打出来。书名的码点顺序里，旧书店在夜航前面还是后面，我不拿来当唯一证据，所以期望同时写出书名和册数，并分两行出现在输出里。子串夜航|2 必须在，子串旧书店|2 也必须在。我把期望设成夜航|2，练习里再核对旧书店还在，避免一个期望承担太多而让你分不清是排序变了还是删除错了。

```sql run expect="夜航|2" title="删掉不足两册的"
CREATE TABLE books(title TEXT PRIMARY KEY, copies INTEGER);
INSERT INTO books(title, copies) VALUES
  ('夜航', 3),
  ('河岸', 1),
  ('旧书店', 2);
UPDATE books SET copies = copies - 1 WHERE title = '夜航';
DELETE FROM books WHERE copies < 2;
SELECT title, copies FROM books WHERE title = '夜航';
```

河岸不在了。要证明它不在，不能靠「输出里我没看见」这种眼力，尤其当结果有很多行。用计数问书名等于河岸的行，应当是 0。下面这份把卖出、删除和两种证明放在一起：夜航的册数，以及河岸的行数。两个数用竖线连成 2|0。

```sql run expect="2|0" title="夜航还在，河岸没有了"
CREATE TABLE books(title TEXT PRIMARY KEY, copies INTEGER);
INSERT INTO books(title, copies) VALUES
  ('夜航', 3),
  ('河岸', 1),
  ('旧书店', 2);
UPDATE books SET copies = copies - 1 WHERE title = '夜航';
DELETE FROM books WHERE copies < 2;
SELECT
  (SELECT copies FROM books WHERE title = '夜航')
  || '|' ||
  (SELECT COUNT(*) FROM books WHERE title = '河岸');
```

2|0 是这一章的句号。2 证明更新写进了存储，0 证明删除写进了存储。两个子查询都读的是删除之后的表。若你把证明误放在删除之前，河岸的计数会是 1，期望会失败，你就知道顺序是语义的一部分。

changes 这个函数能告诉你上一条写入语句碰了几行。删掉河岸之后它是 1。它是连接上的计数器，不是表里的一行，脚本再往下读别的查询，你要赶在下一条写入之前把它读出来，否则计数器会被新的写入盖掉。我不以它作为唯一证据。唯一证据仍然是表里的行。计数器回答「刚才那一句力度有多大」，查询回答「现在世界上还剩什么」。力度大而世界没变，说明你改的是另一张表，或者条件在你读计数器之前又被下一句改了回去。

没有 WHERE 的删除会倒空整张表，而且成功。重建三本书要再插入。在空库的教学脚本里，倒空像是可以重来的，你于是对这条句子失去恐惧。恐惧应该留着。同一句拿到持久的库上，就是一次事故。写删除时先写 WHERE，哪怕条件是一个你刚刚查过的主键。先写 DELETE FROM books 再打算补条件，是一个危险的编辑顺序，因为中途运行就会先倒空。先写 SELECT，把 WHERE 调对，再把 SELECT 换成 DELETE。替换时别把 WHERE 弄丢。

更新可以把册数改成负数。没有额外约束时，负数会被接受，总和会变小，甚至变成你看着不像库存的数。若业务上册数不能为负，要在建表时写上检查约束，例如 copies >= 0。违反时语句失败，退出码不是 0，原来的值保持不变。这种失败适合在持久库上当最后一道门，教学脚本里我让数据保持非负，不靠失败来制造期望。你应当知道门在哪里：不在类型名 INTEGER 上，整数包含负数；门在你明确写下的检查上。

更新和删除都落在自动提交里。每一句成功，就真的留下了，直到脚本结束、内存消失。如果你希望「卖掉一册」和「记一笔账」要么同时留下要么同时没有，单句的自动提交太碎。那是事务的题目。这一章故意让每一句自己作数，好让你看见 2 和 0 是已经生效的事实，不是还悬在空中的草稿。草稿的撤销下一章还不会讲，空值要先讲，因为删除和更新都不会把「未知」变成「零」，它们只会改你点名的那些已经知道的格子。

SET 可以一次改多列。若表上还有架子，你可以在减册数的同时把夜航挪到另一架，一句话，仍然只碰 WHERE 选中的行。可运行的例子没做这个动作，是为了让期望只承担册数。两处变化捆在同一个子串里，失败时你分不清是册数错了还是架子错了。你自己的业务里，一次改多列很自然，前提是这些列确实属于同一次成交。不属于的拆开。拆开之后，某一句失败，你至少知道哪一半已经自己提交了。

用删除再插入来冒充更新，是一条绕路。删掉夜航，再插入一本册数为 2 的夜航，主键要求你必须先删后插。中间若已有借出指向原来的身份，先删会碰到约束，后插又可能得到新的身份。册数变了，书不该因此变成另一本。所以用更新：身份留下，格子改掉。借出里的那个身份仍然指向夜航，而不是指向一个被删掉又重生的陌生人。绕路在没有第二张表时看不出害处，这也是害处要到连接之后才显形的原因。现在表还只有一张，就先把「改格子」和「换行」分成两种句子。

删除在这条批处理路径上不交回一张可供期望比对的表。有的接口会把影响行数返回给调用方，这里要自己去读上一句的回声，而且要立刻读，下一句写入会把回声盖掉。我更信任删除之后的计数。计数读的是还剩下的世界，回声读的是一句的力度。力度可以为 1，而世界没变成你要的样子，说明条件碰着了行，却不是那本你心里想的书。两个证据一起看，才不会把「动过」误认为「动对」。

更新可以带条件表达式，让不同的行走不同的新值。例如册数大于 1 的减一册，等于 1 的不动。这比先查出名单再逐本更新更接近集合的想法。危险也在这里：一句就改完，你没有逐本确认的间隙。间隙要在写入之前用同一条件查询来制造。先看哪些行的册数大于 1，确认是夜航和旧书店，再执行更新。确认完再改，比改完再后悔便宜。后悔在自动提交之后只能再写一句相反的更新，而相反的更新要你记得原来的数。原来的数若没被查询打出来，你就只记得一个模糊的「好像是三册」。

主键让按书名更新最多碰着一行。这是书名当主键的好处，也是它的局限：书名一改，身份就改了。若借出表记的是书名而不是数字身份，改名会让旧的借出全部对不上。所以更早的那一章用数字身份连接。这一章为了句子短，用书名当主键，请不要把这个短带到有借出的脚本里。有借出时，更新书名可以，更新身份要极端谨慎。身份是靶子。靶子动了，所有箭都要跟着动，那就是一次事务里的许多句，而不是一次轻松的 SET。

零行更新不算错误。书名写成「夜航 」带一个空格，更新成功，随后查询仍是 3。期望若写着 2，你会以为引擎没执行更新。它执行了，只是没碰着行。把更新前后的值都打出来，才能区分「没执行」和「执行在了空处」。空处是条件的问题，不是 SET 的算术问题。算术在这句里只是减一，减一很难写错，写错的通常是 WHERE 里的书名。

## 小结

夜航从 3 册变成 2 册，是 UPDATE 写进了表，靠随后的查询才看得见。册数小于 2 的河岸被 DELETE 拿掉，再数它的行，得到 0。没有结果集的写入以沉默表示自己没崩，不以沉默表示自己改对了地方。

同一个 WHERE 先用来查询，再用来写入。没有 WHERE 就是全表。册数能否为负由检查约束决定，不由整数类型决定。下一章让一本样书的册数空着，你会看到等号对空无能为力，计数的两种写法开始分家，而一个谁都不匹配的总和甚至不是零。

## 练习

把旧书店的册数改成 4，不要改另外两本。查出旧书店的册数。插入时它仍是 2，4 必须来自更新，这样你才是在练习 SET，而不是在练习换一个插入字面量。

::: answer 旧书店改为四册
```sql run expect="4" title="只动这一本"
CREATE TABLE books(title TEXT PRIMARY KEY, copies INTEGER);
INSERT INTO books(title, copies) VALUES
  ('夜航', 3),
  ('河岸', 1),
  ('旧书店', 2);
UPDATE books SET copies = 4 WHERE title = '旧书店';
SELECT copies FROM books WHERE title = '旧书店';
```
:::

删掉夜航，然后数还剩几行。河岸和旧书店应当留下，计数是 2。用书名相等来删，不要用册数，免得把别的书一起删掉。

::: answer 删掉夜航
```sql run expect="2" title="剩下两行"
CREATE TABLE books(title TEXT PRIMARY KEY, copies INTEGER);
INSERT INTO books(title, copies) VALUES
  ('夜航', 3),
  ('河岸', 1),
  ('旧书店', 2);
DELETE FROM books WHERE title = '夜航';
SELECT COUNT(*) FROM books;
```
:::
