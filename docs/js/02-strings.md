阅读清单上的标题是字符串。页数有时从输入框来，也是字符串，哪怕它看起来像数字。JavaScript 用同一套值来装这两种文本，不会因为内容「长得像数」就自动把变量的种类改掉。种类只在某个运算符需要时临时转换。这一章把标题当作字符串来处理，再让空字符串和 `0` 撞上 `==`，看转换在比较里做了什么。

字符串是按 UTF-16 码元存的序列，不是按你眼睛里的「一个字」存的。`"边城"` 的 `length` 是 `2`，因为这两个汉字各占一个码元。有的表情符号占两个码元，`length` 会是 `2`，而你觉得那是一个符号。阅读清单的书名都是常见汉字，`length` 和字数碰巧一致，不要把这个碰巧写成规则。取第一个码元用 `title[0]`，得到 `"边"`。这是一个新的字符串，不是把原标题切掉一角。

字符串不能就地修改。没有方法能把 `"边城"` 这个值的第一个字换成别的字。你能做的是算出一个新字符串，再决定让哪个名字指向它。`title + "·沈从文"` 得到更长的新值，原来的 `title` 若没有被改绑，就还是 `"边城"`。这和上一章的数字加法是同一类契约：运算符交回新值。数组那一章会遇到相反的契约，`push` 改的是原来的那个值。

```js run expect="边城" title="拼接得到新字符串"
const title = "边城";
const longer = title + "·沈从文";
console.log(title.length);
console.log(title[0]);
console.log(title);
console.log(longer);
```

四行是 `2`、`边`、`边城`、`边城·沈从文`。模板字符串做的是同一件事，只是把空位留在句子里：`` `《${title}》` `` 得到 `"《边城》"`。模板没有魔法，空位里的值会被转成字符串再嵌进去。若空位里是 `null`，你会得到 `"《null》"` 这几个字母。那通常不是书名。嵌之前先用上一章的规则确认值是字符串。

加号一边是字符串时，另一边也会被转成字符串，运算变成拼接。`"120" + 1` 是 `"1201"`，不是 `121`。页数字段若还是文本，拿去和 `1` 相加会悄悄变长，而不是多一页。`Number("120") + 1` 才是 `121`。转换要写出来，是因为失败时你看得见：`Number("很多")` 得到 `NaN`，随后的加法也是 `NaN`，而不是一个看起来像页数的字符串。显式转换把「这格到底是不是数」变成一步单独的决定。

```js run expect="1201" title="加号碰到文本就拼接"
const raw = "120";
console.log(raw + 1);
console.log(Number(raw) + 1);
console.log(Number.isNaN(Number("很多")));
```

比较运算符里有一套更隐蔽的转换。`==` 在两边种类不同时，会按抽象相等的规则把它们往一处拉。空字符串被转成数字时是 `0`，所以 `"" == 0` 为真。`===` 不转换，种类不同直接为假，所以 `"" === 0` 为假。同一份页数字段，宽松相等会说「空白等于零页」，严格相等会说「文本不是数字」。阅读清单上空白通常表示还没填，零页表示填了零。把它们说成相等，筛选时会把未填的书当成已经读完零页。

```js run expect="false" title="空串与零"
const pages = "";
console.log(pages == 0);
console.log(pages === 0);
console.log(Number(pages));
```

三行是 `true`、`false`、`0`。第三行解释了第一行为什么成立：`Number("")` 就是 `0`，`==` 走了这条转换。信息「这原来是空文本」在比较之后就没了。`===` 把信息留住，因为它拒绝跨种类比较。代价是你不能写 `pages === 0` 来同时接住数字零和文本 `"0"`。文本零要先 `Number`，再和数字比。多写一步，换来的是空白不会混进来：`Number("") === 0` 仍然为真，所以转换之后你还是要单独拒绝空字符串。顺序应该是：先看是不是空文本，再转换，再比较。不要指望一个 `==` 帮你做完三件事。

`"0"` 更刁钻。`"0" == 0` 为真，`"0" === 0` 为假，`"0" == false` 也为真，因为 `false` 先被看成 `0`。可是在条件里，`"0"` 又算真，下一章会看见。三个判断，三种态度，都指向同一个两个字符的值。若页数字段里躺着文本 `"0"`，宽松相等说它是零，条件语句说它存在，严格相等说它不是数字 `0`。只有最后一种适合拿来做「这是数字零吗」的结论。前两种各有历史原因：`==` 来自早期脚本想把表单里的文本和数字比得轻松一些，条件真值则来自「空文本应该像没有」的习惯。轻松的代价是 `"0"`、`0`、`false` 和 `""` 在不同运算符下结成不同的亲戚。

空白字符也会被 `Number` 收成 `0`。`" " == 0` 为真。只检查 `length === 0` 挡不住一个空格。清单若来自手工输入，页数格里一个空格很常见。先 `trim` 再判断空，再 `Number`，比直接 `== 0` 长，但每一步的失败都还知道原因。`trim` 交回新字符串，不改原来的值，这和拼接一样。

```js run expect="true" title="空格也会被看成零"
const raw = " ";
const trimmed = raw.trim();
console.log(raw == 0);
console.log(trimmed === "");
console.log(Number(raw) === 0);
```

书名本身很少和 `0` 去比。真正容易写错的是把标题和页数放在同一个表达式里。`title + pages` 在 `pages` 为数字 `120` 时得到 `"边城120"`，中间没有分隔。这不一定是错，但你要知道加号已经不做加法了。想要固定格式，用模板，并自己放分隔：`` `${title}/${pages}` `` 得到 `"边城/120"`。格式是显示，不是把两个值合并成一个新类型。原来的 `title` 和 `pages` 都还在。

不可变带来一个取舍。每次拼接都可能复制整段文字。在这一章的短标题上，复制便宜得不值一提。若你在循环里用 `+` 把几千个书名粘成一段，就会反复复制越来越长的前缀。数组那一章的 `push` 再 `join` 通常更合适：先收集片段，最后拼一次。现在标题只有两三本，两种写法的输出一样。知道代价，是为了以后清单变长时不把「字符串很简单」记成「循环里可以随便加」。

索引超出范围得到 `undefined`，不是空字符串，也不会抛错。`title[9]` 在 `"边城"` 上是 `undefined`。把它和 `""` 用 `===` 比较为假。若你写 `title[9] == ""` 呢？`undefined == ""` 为假，因为宽松相等并不把 `undefined` 收成空串。它只和 `null` 彼此相认。所以「取不到字」和「取到空串」仍然不同。不要用 `|| ""` 去掩盖，除非你确实想把缺字显示成空白。掩盖之后，调用方分不清是标题太短，还是标题里真有空字。

引号可以嵌套。书名里若有双引号，外层用单引号，或者反过来。模板里用反引号。这三种都是字符串值，种类相同，只是字面量语法不同。`typeof` 一律是 `"string"`。没有「字符」这一个单独的种类，一个字也是长度为 1 的字符串。因此不存在字符和字符串相加的另一套规则，全部走同一条拼接或比较。

码元和字位不是一回事。`"边城"[0]` 取到的是一个码元，对这两个汉字刚好是一个字。若标题里夹了需要两个码元的符号，`[0]` 可能只拿到一半，打印出来像一个残缺的问号或一个孤立的代理项。`codePointAt` 按码位读取，能把那一对码元看成一个点。阅读清单的书名不放这种符号，所以下标和字数暂时一致。一旦允许读者自己起名，就要改用认识码位的方式，或者干脆不要按下标切书名。切书名来做缩写，本身就容易切在字的中间。显示缩写更稳妥的办法是按字数上限在完整码位上停止，而不是按 `length` 砍一刀。

`slice` 交回新字符串，不改原标题。`slice(0, 1)` 对 `"边城"` 得到 `"边"`，结束下标不包含在内。`substring` 也会交换写反的两端，`slice` 则把反着的区间收成空串。两套方法都留着，是历史包袱。新写的代码固定用 `slice`，和数组的 `slice` 记成同一个「结束不包含」的习惯。不要用 `substr`，它的第二个数是长度，和 `slice` 的结束下标容易看错，而且已经不推荐。

比较书名时，`===` 看的是码元序列是否相同，不看你觉得这两个字是不是同一个字的不同写法。有的汉字可以用合成字符写成看起来一样的序列，`===` 会说它们不同。规范化函数能把它们折成同一种写法再比。折叠会丢失「原文到底用了哪种编码」的信息。清单若要求字节级的忠实，就不要先规范化；若要求搜索时「看起来一样就算找到」，就在搜索前规范化一份副本，原标题仍保存。本课的三本书名没有这种歧义，直接 `===`。

`localeCompare` 按语言习惯排序，能让拼音或笔画顺序更接近读者的预期，也可能因为运行环境的语言设置而不同。这个抽屉不把排序结果写进期望，就是为了不依赖那份设置。要稳定的顺序，用放入顺序或明确的页数比较。字符串的字典序对汉字并不等于笔画序，它比较的是码元数值。用默认排序给书架排队，读者会觉得乱，而测试可能仍然通过，因为你没有断言顺序的含义。

重复拼接的成本来自不可变。循环里 `text = text + title` 每次都复制已经拼好的前缀。几十本书无感，几千条导入记录就会明显变慢。先把片段放进数组再一次 `join`，复制发生在最后。数组那一章会用这份清单演示 `push`，这里先记住：字符串的「简单加号」在循环里并不简单。单次标题拼接则没有这个顾虑，为了省一次分配去绕路，代码会更难读，不值得。

搜索书名时，`includes` 看的是连续码元，不是模糊的「像」。`"城南旧事".includes("旧")` 为真。它区分大小写，汉字没有大小写，英文作者名则有。`toLowerCase` 会交回新字符串，只在你明确要忽略大小写时使用。不要对书名先折叠再存回原字段，否则原始写法丢失。显示可以折叠，存储保持原文。空串是任何字符串的子串，`includes("")` 总为真，用它判断「有没有关键词」会把空关键词说成命中每一本。关键词先检查长度，再搜索。

## 小结

字符串按码元计长，运算产生新值，原值保持不动。加号只要看见文本就拼接，页数要先 `Number` 再做算术，转换失败会变成 `NaN`，用 `Number.isNaN` 认出来。

`"" == 0` 为真，是因为空串转成数字是 `0`；`"" === 0` 为假。`"0"` 和 `false`、空格和 `0` 也会在 `==` 下相遇。严格相等保留「这是文本还是数字」。阅读清单上的空白页数应先拒绝空文本，再转换，而不是交给 `==`。下一章把这些值放进 `if`：空串为假，文本 `"0"` 为真，数字 `0` 为假，三个结果会和本章的比较表对不上，那是真值判断的另一套规则。
