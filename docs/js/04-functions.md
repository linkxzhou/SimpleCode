函数是一段可以稍后调用的代码，也是一个值。你可以把函数绑到名字上，可以把它放进数组，也可以从另一个函数里交回来。阅读清单需要的不是再写一遍循环，而是一个「往清单里加一本，并告诉我这是第几本」的动作。这个动作若要记住已经加过多少本，记忆不能只放在调用时的参数里，否则每次调用都得把旧数字传回来。把数字放在外层函数的本地变量里，让交回来的内层函数去改它，这就是闭包。

调用内层函数时，它仍能看见创建它的那一次外层调用里的 `count`。外层函数已经返回了，按「函数结束变量就消失」的直觉，`count` 应该没了。闭包把这个直觉改掉：只要内层函数还活着，它用到的外层变量就跟着活。好处是计数器不用做成全局名字。代价是那个变量会比你想象的更久，若它指着一份很大的清单，清单就回收不掉。计数器这种小数字没有这个问题。若你闭包了一整份不会再读的书目缓存，内存会一直被占着。

```js run expect="2:围城" title="内层函数记住本数"
function openShelf() {
  let count = 0;
  return function (title) {
    count = count + 1;
    return count + ":" + title;
  };
}
const add = openShelf();
console.log(add("边城"));
console.log(add("围城"));
```

两行是 `1:边城` 和 `2:围城`。`openShelf` 每调用一次就有自己的 `count`。再调用一次 `openShelf` 得到的是另一个函数，另一份从零开始的记忆。两个加法器不会共用本数，除非它们是同一次 `openShelf` 交回来的同一个函数。这是取舍：闭包默认私有，你不能从外面直接改 `count`，调试时也不容易看见它。想看见，就让内层函数把数字放进返回值，像上面那样。不要为了调试把 `count` 改成全局，全局会让所有清单共用一个数，第二章才分开的那些书会混在一起。

参数是调用时的值。传入字符串，函数拿到的是那个字符串。传入对象，函数拿到的是指向同一个对象的名字。改对象的属性，调用方看得到；改参数名字的指向，调用方看不到。这和第一章的改绑是同一条规则，只是名字写在参数位置上。返回值是新的值，调用方要自己接住。`add("边城")` 若没有放进 `console.log` 或别的名字，本数仍然增加了，因为增加发生在调用内部，但那一行文字被丢掉了。副作用和返回值可以同时存在。计数器两者都有：它改了 `count`，也交回了一句说明。

现在把一本书写成带方法的对象。方法就是放在属性里的函数。调用写成 `book.label()` 时，点号前面的对象会变成这次调用的接收者，函数里面的 `this` 指向它。于是 `this.title` 就是这本书的标题。这套规则看的是调用的写法，不是函数写在哪一个对象字面量里。

```js run expect="没有接收者" title="拆开方法再调用"
"use strict";
function demo() {
  const book = {
    title: "边城",
    label: function () {
      return this.title;
    }
  };
  console.log(book.label());
  const pulled = book.label;
  try {
    console.log(pulled());
  } catch (err) {
    console.log("没有接收者");
  }
}
demo();
```

第一行是 `边城`，因为调用带有接收者。第二行是 `没有接收者`。在严格模式里，单独调用 `pulled()` 时 `this` 是 `undefined`，读 `this.title` 会抛 `TypeError`。本章的例子写了 `"use strict"`，这样不会悄悄把 `this` 指到全局对象上。非严格模式的全局 `this` 会让你读到别人的 `title`，或者读到 `undefined` 还不报错，两种都比抛错更难查。严格模式把「忘了接收者」变成一次失败。代价是旧代码若依赖全局 `this`，打开严格模式就会坏。新写的清单用严格模式。

箭头函数没有自己的 `this`。它记住的是定义时所在的那个函数的 `this`，一层层向外，直到有普通函数为止。写在对象字面量里的箭头，外层往往是全局或模块，不是这本书。所以箭头不适合当方法。它适合写在方法内部，用来把「这本书」带进一层更里面的函数，比如带进一次筛选的回调。普通函数当回调时，调用方怎么调用，`this` 就是什么；数组的 `map` 调用回调时不会把书本当接收者传进去。箭头因为不改写 `this`，反而能看见外层方法里的那本书。

```js run expect="箭头没有书" title="箭头不拿调用时的接收者"
"use strict";
function demo() {
  const book = {
    title: "围城",
    method: function () {
      return this.title;
    },
    arrow: () => "箭头没有书"
  };
  const nested = {
    title: "城南旧事",
    wrap: function () {
      const inner = () => this.title;
      return inner();
    }
  };
  console.log(book.method());
  console.log(book.arrow());
  console.log(nested.wrap());
}
demo();
```

三行是 `围城`、`箭头没有书`、`城南旧事`。第三行说明箭头用在方法里面是有用的：`wrap` 是普通函数，`this` 是 `nested`，`inner` 是箭头，它把这个 `this` 带走，即使 `inner` 的调用写法没有点号。若把 `inner` 写成普通函数再立刻调用，严格模式下它没有接收者，又会抛错。选择箭头还是普通函数，问的是：这次调用的接收者重要，还是外层的接收者重要。方法的最外层要接收者，用普通函数。往回调里传递「当前这本书」，用箭头。

`this` 不可靠的另一种说法是：你无法从函数的定义看出调用时的接收者，除非函数是箭头。阅读清单的 `label` 若被放进一个「稍后统一打印」的数组，再被数组循环调用，接收者就丢了。修法有三种。调用时写回 `book.label()`。或者用 `bind` 做出一个接收者已经固定的函数：`book.label.bind(book)`。或者一开始就在构造这本书的闭包里记住 `title`，让函数不靠 `this`。`bind` 交回新函数，不改原来的方法。闭包的办法少一个隐式参数，调试时参数都在名字上，但你就不再能把同一个函数体共享给许多书，除非标题是参数。类那一章会把方法放在原型上共享，那时 `this` 再次变成「当前这一本」。现在先接受：共享函数体的代价是用 `this` 区分实例，而 `this` 由调用点决定。

默认参数在调用方没传那个位置时才填上。`function add(title, pages = 0)` 允许只传标题，页数按零。默认值在调用时计算，不是在定义时只算一次。若默认值是一个表达式，每次缺省调用都会重新算。这和某些语言「默认列表只造一次」不同，JavaScript 的默认值通常更安全。不要用默认参数去填一个对象然后在函数里修改它并指望它当缓存，每次缺省都是新对象，缓存不会留下；你若把对象在函数外面造好再当默认值的引用，那就是共享，修改会留下来。页数的默认用数字 `0` 即可。

函数声明会被提升到所在作用域的顶部，函数表达式不会。`const add = function () {}` 在这一行之前不能调用。声明写法 `function add() {}` 可以。提升让短脚本里的顺序不那么挑剔，也让「名字从哪一行开始可用」变得不那么看得见。本课的例子把函数写在调用之前，两种写法都能跑，不靠提升来组织阅读清单。

参数个数可以不固定。剩余参数 `...titles` 把多出来的书名收成一个真数组，可以 `map`，也可以 `push`。它和旧的 `arguments` 不一样。`arguments` 像数组但不是数组，没有 `map`，而且在非箭头函数里才有。箭头函数没有 `arguments`，也没有自己的 `this`。新写的可变参数用剩余语法，放在参数列表最后。默认值参数若和剩余参数一起出现，剩余参数收的是默认值填完之后仍多出来的那些。阅读清单的 `add` 通常一次一本，剩余参数适合一次性导入多本：函数内部用循环去数，闭包里的 `count` 仍然按本增加。

`call` 和 `apply` 能在调用时指定 `this`。`pulled.call(book)` 等价于把接收者补回去。`apply` 的参数是数组。`bind` 则提前交回一个新函数。三者都是在补调用点丢失的接收者。能在调用点写成 `book.label()` 就不要绕。只有函数已经被别人的循环拿去、你改不了那个循环时，才 `bind`。补救放在交出去的那一刻，而不是在每次失败后再包一层 `try`。`try` 会把「没有接收者」和其他类型错误混在一起。

递归可以走一条很短的清单：处理第一本，再处理剩下的数组。对三本书，递归清楚，也费栈。JavaScript 引擎不保证尾调用消除，所以不要用递归数几千页。页码和本数用循环。递归适合树形的目录，例如一章里面还有节。本课的清单是平的数组，循环是更诚实的写法。用递归只为了「看起来像函数式」，会在深度上来的时候先爆栈，而不是先得到更清楚的书名。

函数名字和函数值可以分开。`const label = function show() {}` 里，外部叫 `label`，内部自己递归时可以叫 `show`。若你不需要内部名字，表达式可以匿名。栈上匿名函数会显示成 `(anonymous)`，查错时少一个线索。给清单操起一个名字，例如 `function unfinished`，栈会告诉你是筛选在抛，而不是一片匿名回调。箭头函数在栈上更短，适合一行的换算，不适合占满屏幕的流程。流程用有名字的函数声明，换算用箭头，这个分工比「全部箭头」或「全部声明」更易读。

纯函数是一种约束，不是语法。传入标题，返回带书名号的新字符串，不改外面的数组，这就纯。计数器不纯，因为它记住并修改 `count`。两种都需要。显示格式做成纯函数，方便你换一个标题就知道输出会怎么变。本数做成闭包，是因为调用方不想每次传递旧数字。不要把格式函数写成顺便 `push` 的不纯函数，否则「我只是想看看书名号」会改掉清单。副作用集中在 `add` 一类名字上，读名字就能猜到它会改东西。

回调的同步与否要在名字里看得出来。数组的 `map` 会立刻把回调跑完，再交回新数组，这里没有「稍后」。Promise 的 `then` 才是稍后。把同一个箭头既传给 `map` 又传给 `then`，两边的 `this` 和执行时机都不同。清单的格式化只交给 `map`。需要排队的打印留到微任务那一章。不要在 `map` 的回调里再去登记微任务并指望 `map` 的返回值里已经有那些结果。`map` 返回时，微任务还没跑，数组里若是 Promise，你拿到的是一排尚未展开的承诺，不是书名。展开它们是后一章的事，而且要明确地等。

## 小结

内层函数可以记住外层的 `count`，每次 `openShelf()` 有一份自己的记忆。返回值要接住，副作用才会和你看见的文字一致。方法调用 `book.label()` 把这本书当作 `this`；把方法拆成单独的名字再调用，严格模式下没有接收者，访问 `this.title` 会失败。

箭头函数带走定义处的 `this`，适合放在方法内部，不适合当作需要接收者的方法本身。`bind` 可以固定接收者，闭包可以让函数根本不看 `this`。下一章回到清单的存放：同一个数组上，`push` 会改原清单，`map` 会交回一份新清单。函数只是决定你用哪一种。

## 练习

1. 写 `makeCounter`，从 `0` 开始，返回的函数每调用一次就把数字加一并返回。连续调用三次，打印第三次回的数字，应能找到 `3`。前两次也打印出来。

::: answer 参考答案
```js run expect="3" title="参考答案"
function makeCounter() {
  let n = 0;
  return function () {
    n = n + 1;
    return n;
  };
}
const next = makeCounter();
console.log(next());
console.log(next());
console.log(next());
```
:::

2. 在严格模式下做一本书，标题 `"城南旧事"`，方法 `label` 返回 `this.title`。先用方法调用打印标题，再把方法取出来用 `bind` 绑回这本书并调用，两次都应打出标题。

::: answer 参考答案
```js run expect="城南旧事" title="参考答案"
"use strict";
const book = {
  title: "城南旧事",
  label: function () {
    return this.title;
  }
};
console.log(book.label());
const pulled = book.label.bind(book);
console.log(pulled());
```
