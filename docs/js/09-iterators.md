数组把阅读清单一次放完。三本书时这没有成本。若清单是「从第 1 页数到第 400 页」，先造一个长度为 400 的数组再取前两页，就做了用不到的分配。生成器把函数变成可以暂停的过程：执行到 `yield` 就把一个值交出去，下次再从那一行往后走。你要下一本时才计算下一本。状态留在生成器对象里，而不是留在一个已经填满的数组里。

`function*` 声明生成器函数。调用它不跑函数体，只交回一个生成器对象。真正往前走要靠 `next`。`next` 的返回值是一个普通对象，有 `value` 和 `done`。`done` 为假时，`value` 是这次 `yield` 交出的东西。函数体走完之后，`done` 为真，`value` 是 `undefined`，除非函数 `return` 了一个值。`for...of` 只用 `done` 为假的那些 `value`，`return` 的值不会出现在循环里。这个差别容易让人以为返回值丢了。不是丢了，是迭代协议把「序列的元素」和「结束时的附加结果」分开了。

```js run expect="true" title="next 逐本交出标题"
function* titles() {
  yield "边城";
  yield "围城";
  yield "城南旧事";
}
const it = titles();
console.log(it.next().value);
console.log(it.next().value);
console.log(it.next().value);
console.log(String(it.next().done));
```

四行是三本书名和 `true`。三次 `yield` 之后再 `next`，函数已经结束。生成器不会回到开头。再调用 `titles()` 才会得到一个新的、从头开始的生成器。同一个对象走两次 `for...of`，第二次是空的。这是取舍：暂停的状态只有一份，不会意外地每次循环都重头算；你若需要重头算，必须再调用生成器函数。数组则可以反复 `for...of`，因为它的状态就是那些已经放好的元素，不存在「走到头」之后内容消失。生成器走到头，内容不会保存在别处，除非你自己推到数组里。

```js run expect="0" title="同一个生成器不能重放"
function* once() {
  yield "边城";
}
const it = once();
const first = [];
for (const title of it) first.push(title);
const second = [];
for (const title of it) second.push(title);
console.log(first.join(","));
console.log(String(second.length));
```

第一行是 `边城`，第二行是 `0`。`for...of` 内部就是在调用迭代器的 `next`，直到 `done`。数组有迭代器，生成器自己就是迭代器。所以消费数组的循环也能消费生成器。回调式的 `map` 不能直接接收生成器函数，你要先把它展开，例如用展开语法把生成器倒进数组。一展开，懒的好处就没了，四百页会一次都算出来。只取前两页时，不要展开，用两次 `next`，或者在循环里 `break`。

`break` 会停止循环，生成器可能还停在中间。若函数体里 `yield` 之后还有必须做的收尾，只 `break` 不会自动跑到函数末尾。`for...of` 在提前退出时会去调用迭代器的 `return`，生成器因此有机会执行 `finally`。这一章的例子不打开外部资源，所以不靠这个收尾。知道有这条路径，是为了以后不要在生成器里做一半的事情却没有 `finally`。没有资源时，保持函数体只有 `yield`，提前停止就只是少要了几本。

页码可以用循环里的 `yield`，而不是先填数组。

```js run expect="6" title="需要时才产生下一个页码"
function* upTo(n) {
  let i = 1;
  while (i <= n) {
    yield i;
    i = i + 1;
  }
}
let sum = 0;
let taken = 0;
for (const page of upTo(100)) {
  sum = sum + page;
  taken = taken + 1;
  if (taken === 3) break;
}
console.log(sum);
```

`upTo(100)` 并没有造出 100 个数。循环取了 1、2、3 就 `break`，和是 `6`。若写成先 `Array` 填满再求和，结果一样，分配不一样。三页的差别可以忽略。判断在于：上限来自数据，可能很大，而你只显示前几本。生成器把「上限」写成循环条件，把「要多少」留给消费方。两者分开之后，生产方不用知道界面只显示三行。

代价是随机访问变贵。数组的第 50 本是 `shelf[49]`。生成器要先 `next` 四十九次丢掉，才能看见第 50 个 `yield`。阅读顺序本来就是从头走，生成器合适。要跳着读、要排序、要知道 `length`，还是先收成数组。`length` 在生成器上没有意义，因为剩下的个数可能取决于还没发生的计算。不要给生成器假装一个长度，除非你确实知道。

生成器函数里的 `yield` 也可以接收值。`const x = yield title` 会在下次 `next(某个值)` 时把那个值赋给 `x`。这把生成器变成双向的暂停点。阅读清单目前只需要往外交标题，不需要调用方在暂停时塞回指令。双向更强，也更难读：函数体的进度依赖于别人下一次 `next` 的参数。本课的 `next` 都不传参。能用单向交完，就不要做成对话。

无限的生成器是合法的，例如每次 `yield` 下一本推荐、永不 `done`。消费方必须 `break` 或只调用有限次 `next`。没有刹车的 `for...of` 会占住引擎，和死循环一样。本章所有生成器的 `yield` 次数都有上限。不要为了「演示无限」写一个不结束的循环。

和闭包比，生成器也是记住进度。闭包记住的是变量，每次调用走完整个函数。生成器记住的是停在哪一个 `yield`。计数器用闭包更合适，因为它没有「序列」的意思。页码用生成器更合适，因为调用方要的是下一个，不是一个会加一的函数偶尔被拿来当序列。若你把 `upTo` 写成闭包返回的 `nextPage`，也能用，只是 `for...of` 不认识它，除非你再包一层迭代器。生成器把「可被 for 消费」这件事情放进了语法。

展开和剩余参数认识可迭代对象。`const all = [...upTo(3)]` 得到 `[1, 2, 3]`。这在上限很小的时候是清楚的写法，用来把懒序列收成数组再 `map`。收成数组之后就可以有多份消费者，各走各的下标，互不影响。生成器本身做不到多份消费者共享同一次进度还各自独立，除非你为每个消费者重新调用 `upTo`。重新调用会重算。若重算很贵，先收成数组，接受那一块内存。贵和省是这次数据量上的判断，不是生成器在道德上更高尚。

迭代协议不神秘。一个对象若有 `next` 方法，每次交回 `{ value, done }`，它就是迭代器。生成器是语言帮你把函数体编成这种对象。你也可以手写一个对象来交书名，效果和 `function*` 相同，只是要把「现在交到第几本」存在自己的字段里。手写时字段看得见，生成器把字段藏在暂停的函数里。看得见的计数器更容易在调试时打印，藏起来的暂停点更接近「从这行继续」的阅读方式。三本书两种都能写。当暂停点散落在几层条件里时，生成器比手写状态机短。当状态只有一个整数时，普通闭包计数器更短。不要为了用上 `yield` 而把计数器改写成生成器。

可迭代对象比迭代器多一步。`for...of` 会先找 `Symbol.iterator`，调用它得到迭代器，再反复 `next`。数组的这个方法每次交回一个新迭代器，所以数组可以同时被两处遍历。生成器函数自己被调用时就得到迭代器，它的 `Symbol.iterator` 通常返回自己。因此生成器一次只能服务一个消费者。想让两处各自走一遍书名，就调用两次生成器函数，或者先展开成数组。展开是把懒计算做成快照。快照之后，原生成器若已经走了一部分，展开的是剩下的部分，不是从头。这个顺序很容易看错。需要完整快照时，对一个新的生成器展开。

`yield*` 可以把另一个可迭代对象的元素逐个交出去。一个生成器负责三本书名，另一个 `yield*` 它再追加一本，消费方看见四本。这样组合比先拼数组再生成更懒，只要消费方提前停止，后面的追加可以不发生。组合的代价是暂停点跨了两个函数，栈上要多看一层。层数一多，不如把标题数组交给一个简单的 `for...of`。懒是手段，不是目的。

生成器里抛出的错误会从 `next` 的调用点冒出来，而不是从创建生成器的那一行。`for...of` 没有自己的 `catch` 时，错误继续往外。若某一本的页数非法，你想跳过它而不是停掉整个遍历，就在生成器内部接住，或者在循环里接住每一次 `next`。接在内部，消费方不知道有过失败。接在外部，消费方能记下坏的那本。导入清单时，外部接住更合适，因为坏行是数据的一部分，不是生成器写错了。生成器写错则应该让它抛，不要在内部把编程错误变成「跳过一本」。

提前结束时，`for...of` 会尝试调用迭代器的 `return`。生成器收到这个信号，就跑 `finally` 并不再 `yield`。手写迭代器若忽略 `return`，提前 `break` 不会有任何收尾。没有文件要关时，忽略也没损失。有计数要提交时，把提交放进 `finally` 或 `return`。不要放在生成器函数最后一行却指望 `break` 还能走到那里。最后一行只在消费方走完时才执行。这个差别是生成器最容易写错的地方：把清理放在末尾，然后用 `break` 只取前三本，清理没有发生，你却以为函数「结束了所以一定会清理」。结束有两种，走完和打断，只有 `finally` 两种都覆盖。

无限序列必须带一个消费方的上限。参数 `n` 就是上限。不要在生成器内部写死一个很大的数字来假装安全，那个数字仍然可能被一次展开成巨大数组。上限放在离 `for...of` 最近的地方，读循环的人看得见这次只要三本。生产方只负责「下一本是什么」，不负责猜界面要多少。

把生成器传进只接受数组的函数之前要展开，这会失去懒。若那个函数只是为了取前三个元素，就不要先展开整段。改函数去接受可迭代对象，内部自己 `for...of` 并提前停止，生成器就能保持懒。接受的类型变宽之后，数组仍然能用，因为数组可迭代。这是一个方向上的兼容：从数组放宽到可迭代，调用方的数组不用改。反方向则要求每个人都先展开。新写的「只走一遍」的函数，参数用可迭代的消费方式，而不是要求 `length` 和下标。需要 `length` 的函数才要求数组。清单的合计需要全部页数，用数组合适；只要下一本标题的预览，用生成器合适。

## 小结

`function*` 的调用产生生成器，`yield` 暂停并交出一个值，`next` 恢复。`for...of` 会把序列走完，提前 `break` 就停。同一个生成器走完后是空的，再要一遍就再调用函数。

懒的序列适合「只要前几页」。需要下标、长度和重复遍历时，把结果收成数组。不要写没有上限的 `yield` 循环。下一章的顺序问题不在生成器里，而在已经完成的 Promise：微任务会排在当前这段同步代码之后，并且按排队的次序走完，不靠定时器。
