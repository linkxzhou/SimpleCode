前面的订单都在 `main` 一条路径上算完。计价若要交给另一段同时进行的代码，这段代码就是一个 goroutine。goroutine 和 `main` 之间用通道传递结果。这一章传递的数是确定的：先传 42，再传两杯茶的 3600。不使用 `time.Sleep`。睡觉是在猜对方什么时候算完，通道的接收才是在等那个数本身。

通道是带类型的队列。`make(chan int, 1)` 造出一条能传递整数、容量为 1 的通道。容量 1 表示里面可以先放进一个整数，即便当时还没有人在接收。放进第二个就会等待，直到有人取走第一个。容量为 0 的通道则要求发送和接收双方同时就绪，对不上就等待。容量 1 让发送方可以把一个结果放下就离开，接收方稍后来取。订单的计价结果只有一个整数时，一格缓冲正好。

下面这一块在 goroutine 里发送 42，在 `main` 里接收并打印。`<-ch` 会等到有值可读。值来自那一次发送，所以打印一定是 42。调度器可以先跑发送，也可以先跑到接收然后堵住，等发送发生再继续。两种调度的可见结果相同。缓冲让发送在接收还没开始时也能完成，goroutine 不会卡在发送上。`main` 仍然必须接收，否则 42 只是躺在通道里，终端什么都没有。

```go run expect="42" title="缓冲一格交回 42"
package main

import "fmt"

func main() {
	ch := make(chan int, 1)
	go func() {
		ch <- 42
	}()
	fmt.Println(<-ch)
}
```

42 在这里是一个约定好的标记，用来证明通道交回的是发送的那个数，不是零值，也不是随机数。下一笔换成金额，规则相同。goroutine 里计算 `2 * 1800`，发送 3600。`main` 接收后打印。输出是 3600。计算放在 goroutine 里，打印放在 `main` 里，中间只通过通道交接。没有共享的 `qty` 变量被两边同时写。不共享可变变量，就不必上锁。通道把「交接」变成唯一的接触点。

```go run expect="3600" title="金额从通道回来"
package main

import "fmt"

func main() {
	ch := make(chan int, 1)
	go func() {
		ch <- 2 * 1800
	}()
	fmt.Println(<-ch)
}
```

也可以不另起 goroutine，在 `main` 里对容量为 1 的通道先发送再接收。发送不会堵住，因为还有一格空着。接收立刻得到刚刚放下的 1800。这一块用来看清缓冲本身：没有第二段代码，通道仍然能暂存一个单价。暂存不是目的，目的是让发送和接收在时间上可以错开一步。错开一步之内，结果仍是确定的。

```go run expect="1800" title="先放进缓冲再取"
package main

import "fmt"

func main() {
	ch := make(chan int, 1)
	ch <- 1800
	fmt.Println(<-ch)
}
```

`time.Sleep` 解决不了等待。它让当前 goroutine 停一段时钟时间，然后继续。时钟和「计价有没有做完」没有关系。停得太短，另一段还没发送，你若去读一个还没人发送的无缓冲通道，就会一直堵着；你若去读共享变量，可能读到零值，把没算完的订单当成 0 分。停得太长，终端里的 3600 来得及出现，可是慢机器或解释器忙的时候，同样的时长又不够。测试因此会时过时不过。时长也没有写进类型，读代码的人看不出这里在等金额。接收表达式 `<-ch` 把等待的对象写在源码里：等的是一个 `int`。

下面这段只展示睡觉的长相，不运行。它用时钟去赌打印已经发生。赌赢了终端里有 42，赌输了什么都没有。课程不把这种赌放进可运行块。

```go norun title="不要靠睡觉等结果"
package main

import (
	"fmt"
	"time"
)

func main() {
	go func() {
		fmt.Println(42)
	}()
	time.Sleep(time.Millisecond)
}
```

这段还有第二层问题。goroutine 里的 `Println` 和 `main` 的结束在抢时间。`main` 返回时，进程结束，还没来得及打印的 goroutine 会被直接丢掉。`Sleep` 是在推迟 `main` 的返回，希望打印碰运气发生在返回之前。通道接收把 `main` 的返回拴在「值已经拿到」之后。拿到再 `Println`，打印的是本 goroutine 里的事，不依赖别的 goroutine 还能活多久。

接收也要有人发送，否则 `<-ch` 会一直等。一直等的程序在抽屉里表现为 Run 不返回。写可运行块时，每一条接收都对应一次确定会到达的发送，发送的个数不要超过缓冲加上接收的能力。容量为 1 时，goroutine 里连续发送两次，而 `main` 只接收一次，第一次发送可以进入缓冲，第二次发送会堵住。`main` 取走第一次之后如果直接返回，第二次还堵在 goroutine 里，进程随 `main` 结束，第二个数消失。输出也许仍是第一个数，可是你已经在依赖「进程退出会杀掉堵塞的发送」。计价只发送一次，`main` 只接收一次，两边对齐。

多个结果要用循环接收，或者换一条能传递切片的通道，一次把整张订单的金额切片送过来。不要开几个 goroutine 分别打印，再指望终端里的行序固定。调度器不保证打印的先后。通道若按你发送的顺序接收，顺序由发送次序决定，这才是确定的。这一章因此只让一个 goroutine 发送一个整数，`main` 打印那一次接收。茶和包子若要并行计价，应各自发送到同一条通道，`main` 接收两次，并且期望不要依赖哪一笔先到，除非你在发送的值里带上名字，接收够两笔再按名字汇总。汇总的打印放在两笔都到齐之后。

共享映射仍要小心。两个 goroutine 同时写 `price["tea"]` 会竞争，正式的竞争检测器会报，解释器不一定每次都表现成崩溃。这一章不共享映射。单价在 goroutine 内部是局部变量，只有结果整数穿过通道。需要共享表时，用互斥锁把写入包起来，或者规定只有一个 goroutine 负责写表，别的只通过通道把「请写入」的请求送过去。单一写入者比到处上锁更容易看出次序。

`defer` 在每个 goroutine 里各算各的。`main` 里的 defer 不会在子 goroutine 退出时运行。子 goroutine 要关闭自己的资源，就在自己的函数里 defer。这一章的 goroutine 没有资源要关，函数体只有一次发送。

[Go by Example](https://gobyexample.com/) 的 goroutine 和 channel 页使用类似的发送与接收。[Learn Go with Tests](https://quii.gitbook.io/learn-go-with-tests) 讨论并发时强调确定的失败和确定的完成。这里的完成就是接收到 42 或 3600。

缓冲大小是一种容量契约。1 表示「允许一笔结果先做完，调用者还没来取」。0 表示「必须当面交接」。更大的缓冲表示「允许堆积」。堆积能让计价的 goroutine 暂时不等待 `main`，`main` 却要记得把堆积的数都取走。取不完，数据留在通道里，进程结束就丢了。订单合计若只关心最终一个整数，就在 goroutine 里加完再发送一次，缓冲为 1 足够。不要为每一杯茶发送一次再把缓冲开得很大，指望 `main` 慢慢加。那样发送次数变成协议的一部分，漏一次接收就会堵死。

关闭通道是另一种信号。发送方 `close(ch)` 之后，接收方的 `for n := range ch` 会在取完已发送的值后结束。关闭不是结束进程，是告诉接收方没有更多的整数了。接收方不要 `close`，关闭两次会 panic。这一章的例子只有一次发送、一次接收，不需要关闭，函数结束就够了。等发送次数要到运行时才知道，再让发送方关闭，接收方用 `range`。`range` 的次数由发送方决定，输出若依赖次序，发送方就要按确定的次序发送。

`select` 能在多个通道里等最先就绪的那个。两笔订单两条通道时，`select` 哪一条先到就取哪一条，先到的次序不固定。合计可以相加，因为加法不关心次序。打印名字则会时而茶先、时而包子先。期望字符串不要写成固定的两行名字。要么只打印合计，要么把结果收齐后按名称排序再打印。排序发生在 `main`，发生在两笔都收到之后。`select` 本身不提供排序。

锁和通道不要包住同一块数据。已经用通道把整数交出来了，就不要再让 goroutine 写 `main` 里的 `sum`。两边同时写 `sum` 是数据竞争，结果可能少加一笔。通道的接收在 `main` 里做加法，写 `sum` 的只有 `main`。这条纪律比记住锁的用法更能让 3600 稳定。锁留给真正共享的结构，比如一张必须就地更新的映射，而且那张映射不要再通过通道共享它的内部切片。

解释器上的调度比编译后的程序更串行一些，有时会让错误的 `Sleep` 也「碰巧」打出 42。碰巧不是课程要的证据。证据是接收表达式和发送的值相同，反复运行仍是同一个数字。42 和 3600 都满足这一点。你把发送改成 `2 * 600`，输出就变成 1200，不需要调整任何等待时间。等待时间若也要跟着改，说明你在调时钟，不是在传结果。

通道里的值是复制进去的。发送一个 `int`，接收方得到的是同一个数的副本，两边之后各改各的局部变量，不会互相影响。发送结构体也是复制整份订单。大订单频繁发送会有拷贝成本，那时再考虑发送指针。指针能少拷贝，也让接收方有能力改到发送方还握着的那一笔。金额这种整数用值发送，42 和 3600 都是副本，接收方打印不会改到发送方。课程因此不把 `*Order` 放进通道。

`main` 作为接收方，还有一个职责是不要提前返回。接收语句放在打印之前，打印放在所有需要的接收之后。中间不要插入会 `return` 的错误分支却忘了还有 goroutine 在发送。若计价可能失败，让通道传递结果结构，或者另用一条错误通道，并保证两条里有一条一定会送来消息。没人发送的接收会让 Run 停住。停住和打印出错误文本不同。错误文本是你设计的输出，停住是协议缺了半边。

缓冲为 1 时，发送方放下 42 就可以去做别的事，接收方还没取也没关系，只要不再发送第二个。本章的发送方没有别的事，发送之后 goroutine 就结束。`main` 取到 42 再打印。这条时间线里没有第三个数会插进来，所以终端里的数字就是通道里的那个副本。

打印放在接收之后，接收的结果只打印一次。再打印一次 `<-ch` 会再等一个值，而发送只有一次，第二次接收不会返回。42 因此只出现在一次 `Println` 里。期望写成 42，不会被第二行干扰。

## 小结

`make(chan int, 1)` 可以暂存一个整数。goroutine 发送，`main` 接收，打印出来的就是发送的那个数。`time.Sleep` 只是在赌时钟，赌的不是结果。接收和发送要成对，进程才不会停在无人应答的等待上。下一章用一个简单的泛型函数同时取出商品名和单价。
