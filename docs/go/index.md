这家店只卖两样东西。茶一杯 1800 分，包子一个 600 分。分是人民币的最小单位，1800 分就是 18 元。后面每一章都还用这笔账，因为换一套商品会把注意力从语言机制上挪走。这一章先不声明结构体，不切片，不报错，只把两杯茶的金额算出来，并弄清这段源码是谁在读。

点 Run 之后，抽屉把你眼前这一份源码交给 Yaegi 0.16 解释执行。这里没有 `go build`，没有链接器，也没有生成一个可以拷走的二进制。解释器读完这一份文件，找到 `package main` 里的 `func main`，从那里开始。编译成机器码的那条路在这个抽屉外面。你在自己的机器上可以用编译器做同样的算术，课程里的按钮不走那条路。所以这一章讨论的失败，是解释器拒绝这份文件，或者解释器跑完了但终端里的数字不是 3600。两条路的修法不一样。

`package main` 在 Go 里表示这是一个程序，而不是一个库。库的包名通常和目录同名，给别的程序导入。程序必须有一个 `main` 包，并且在这个包里有一个没有参数、没有返回值的 `main` 函数。解释器沿用这条入口约定。你把包名写成 `order`，就算里面有一个看起来像入口的函数，这个抽屉也不会把它当成程序去调用，终端往往是空的。空终端很像「金额是 0」，其实是入口没被找到，乘法根本没有发生。把包名改回 `main`，再写上 `func main`，两杯茶的 3600 才会有机会出现。

整个程序只能是这一份文件。没有第二个 `.go`，也没有你自己的模块路径可以另存。标准库可以导入，`fmt` 就是这样进来的。你自己写的 `shop/order` 这种路径，解释器找不到对应的源码，导入会失败。多包、`go.mod`、工作区，都留给真有目录的工程。在这里，辅助函数写在 `main` 上面或下面，同一个文件里就够了。下面这段只是长相，它不能运行，因为那个导入在抽屉里没有落点。

```go norun title="别的包不在这一份文件里"
package main

import "shop/order"

func main() {
	order.Print()
}
```

导入了却不用，正式的编译器会拒绝这份文件。Go 把没被读到的导入当成错误，是为了让依赖清单和真正执行的代码保持同一份。留着一个「以后可能要」的 `errors`，读者会以为这一章已经在处理失败，其实一个字符都没交给那个包。这个解释器对个别未使用导入比较宽容，课程仍然不留。原因是同一份文件拿到 `go test` 或 `go build` 上会停住，而那才是你离开抽屉之后的习惯。每个可运行块只导入它调用到的包。

`fmt.Println` 是金额离开进程的方式。它在参数之间补空格，在末尾补换行。期望写成输出里能看见的那一串数字。换行多出来时，数字本身还在，所以期望盯住 3600，而不是盯住行数。若你什么都没打印，终端空白，空白是「没有把结果交出去」，要和「结果是 0」分开。0 会以字符 `0` 出现。空白连这个字符都没有。

先把两杯茶乘开。件数和单价都写在 `main` 里面，用短声明给出名字。短声明是下一章的主题，这里先用它把 2 和 1800 绑住，好让乘法的两个因子可以被指出来。没有这些名字，`fmt.Println(2 * 1800)` 也能得到同一个数，但后面你没法先打印件数再打印金额，而不把数字再抄一遍。抄写会漂移：一处改成一杯，另一处还是两杯，终端里的句子就不再描述同一笔订单。

```go run expect="3600" title="两杯茶"
package main

import "fmt"

func main() {
	qty := 2
	cents := 1800
	fmt.Println(qty * cents)
}
```

3600 可以心算复核：1800 加 1800 是 3600。若终端里是 1800，优先怀疑件数还是 1，而不是怀疑乘法会随机少乘一次。若终端里是 18，那是把元当成了分，少了两位。这门课把单价固定成整数分，就是为了让这种少两位在源码里显形，而不是藏在二进制浮点的舍入里。18.00 元用 `float64` 也能写出来，可是 0.1 这类十进制在二进制里是循环小数，三笔小额加起来可能差一分数。茶和包子的标价都是整分，整数乘法把「差一分」留到你真的要做折扣时再处理。折扣是后面的话题，这一章连除法都不做。

下一步把商品名和件数放在同一次打印里。名字是字符串 `"tea"`，件数是整数 2。`Println` 会在它们中间放一个空格。这一行的任务是确认字符串和整数可以一起离开进程，金额那一列先不混进来。茶的英文名是为了让期望稳定，中文商品名在源码里完全合法，终端也会按 UTF-8 显示。课程在可运行块里用短的英文标记，讨论用中文，是为了让期望字符串短、可核对。你把 `"tea"` 换成 `"茶"` 时，规则没有任何变化，变的只是输出里的字节。

```go run expect="tea 2" title="名称和件数"
package main

import "fmt"

func main() {
	name := "tea"
	qty := 2
	fmt.Println(name, qty)
}
```

第三次把名称、件数、单价按这个次序排开。三个值，一次调用。次序是你写在参数列表里的次序，解释器不会按「金额应该放在最后」这种习惯替你重排。若你把单价放在件数前面，终端会变成 `tea 1800 2`，读起来像单价是 1800 杯。这种错能跑完，退出也正常，所以看输出时要看完整的一行，对照参数的位置。

```go run expect="tea 2 1800" title="一行订单"
package main

import "fmt"

func main() {
	name := "tea"
	qty := 2
	cents := 1800
	fmt.Println(name, qty, cents)
}
```

`fmt.Printf` 可以用格式串控制字形，这一章先不用。`Println` 的默认格式对整数和字符串已经够用，而且少了一个「格式和参数对不上」的来源。等订单字段变多，需要固定列宽时再引入格式串。现在多一个工具，只会让 3600 的来源变模糊。

每一块都是一份新的程序。上一块里的 `qty` 不会活到下一块。这是抽屉的运行方式：每次 Run 都重新解释你点的那一块，块与块之间没有共享的内存。所以还要用到的数字会再写一遍。重复是为了让某一块能单独运行，不是 Go 规定两个文件之间必须失忆。你在自己的工程里当然会把订单类型放在一处，让多个函数看见它。那个工程有多文件，这个抽屉没有。

函数可以写在 `main` 旁边，只要还在同一个 `package main` 里。解释器会先读完整份文件，再调用 `main`，所以辅助函数放在 `main` 下面也找得到。这一章故意不抽函数，是为了让 3600 的来源在一个函数体里就能看完。下一章才会讨论声明的位置：哪些名字用 `var`，哪些名字用 `:=`，以及为什么同一个名字不能在同一块里用短声明再声明一次。

标准库里和这一章有关的，几乎只有 `fmt`。`fmt` 负责把值变成文字。它不负责校验件数是不是正的。两杯写成 -2，乘法会给出负数，`Println` 照样打印。负数金额在账上是一种意思，在这一章只是「解释器不会替你挡」。挡住非法件数，需要你自己写判断，并把原因交回去。那是错误那一章的事。现在先接受：入口对了，打印发生了，数字就是表达式的值。

还有一个和入口有关的取舍。有人希望解释器像脚本语言一样，从第一行开始执行，不必写 `package` 和 `main`。Go 拒绝这种便利，是因为同一门语言要同时写程序和库。入口若可以省略，一个被当成库导入的文件就说不清「这些顶层语句算不算已经执行」。把入口写死成 `main` 函数，库就可以安全地只提供函数和类型，导入它不会自动跑一段订单逻辑。你付出的是每个示例都要写那两行样板。换来的是：看到 `package main` 就知道这是一次运行，看到别的包名就知道这是一份供人调用的代码。

样板也有成本。教学块因此看起来比脚本长。读的时候先跳过这两行，把注意力放在 `main` 里面的名字和打印上。改的时候不要删这两行来「变短」。删掉之后按钮仍可能正常结束，终端却是空的，你会对着空白怀疑乘法。先看包名和函数名，再看数字。

金额用分还有一层和显示有关的理由。终端里的 3600 是四位数字，18 元若写成 18.00 会带小数点。小数点让人觉得精确，整数分让人觉得「还要自己除以 100 才是元」。这门课选择后者。元和分的换算放在给人看的最后一步，计算过程保持整数。你若在练习里打印元，用整数除法得到 36，余数用另一个整数表示角分。不要为了显示引入浮点，再把浮点乘回分。来回转换正是一分钱对不上的来源。

订单这一章只描述一杯茶的标价和两杯的合计。包子的 600 分先放在叙述里，代码里下一章再用它做第二个变量。同时引入两个商品，会把「名字怎么声明」和「两个金额怎么加」缠在一起。先让一种商品走通入口。第二种商品用来在后面说明：再声明一个同名变量会失败，把第二种商品放进另一个名字才是声明。

把这一章收成一张可以对照的清单。源码是一份文件。包名是 `main`。入口是 `func main`。输出用 `fmt`，导入就使用。金额是整数分。两杯茶是 3600。终端空白时，先看入口在不在，再看有没有把结果打印出来。终端里的数字和心算不一致时，对件数和单价，乘法本身在解释器和编译器里是同一张表。

按钮旁边如果还有一块只能阅读的源码，它用来展示抽屉做不到的导入。阅读块不会被解释，所以里面那句 `order.Print` 不会真的去找店名。把它改成可运行之前，先删掉那个不存在的导入，把要做的事写进当前文件的 `main`。混用两种块是为了让「做不到」有一个看得见的长相，同时让做得到的三笔账都能单独点 Run。

订单号这一章也先不引入。两杯茶还没有编号，因为编号会引出「零值的编号算不算有效」这种问题。先把入口和金额单位钉死。编号、件数是否允许为零、改件数会不会改到副本，都放在它们自己的章节里，每一章只加一种机制。这样终端里的 3600 始终能追溯到 2 和 1800，而不是追溯到一整页新概念。

[Go by Example](https://gobyexample.com/) 的目录能帮你对照语法名字。[Learn Go with Tests](https://quii.gitbook.io/learn-go-with-tests) 用测试来讲同一门语言。两边都不是可改编文本。这里的茶、包子和 3600 是单独写的，后面每一章都从这笔订单往下长。

## 小结

抽屉用解释器运行一份文件，不在这里 `go build`。程序仍然要 `package main` 和 `func main`，否则终端是空的，空不是金额 0。茶 1800 分，两杯 3600，用整数记住。自己的其他包不能导入。下一章看这些名字是怎么声明的，以及为什么 `qty := 2` 之后不能再写一次 `qty := 3`。

## 练习

只卖一个包子。单价 600 分，件数 1。打印合计。期望里要能看见 600。

::: answer 参考答案：一个包子
```go run expect="600" title="参考答案"
package main

import "fmt"

func main() {
	qty := 1
	cents := 600
	fmt.Println(qty * cents)
}
```
:::

把茶的名称、件数 2、单价 1800 打印成一行，中间用 `Println` 的默认空格。不要打印合计，这道题只核对三个原始字段的次序。

::: answer 参考答案：三个字段
```go run expect="tea 2 1800" title="参考答案"
package main

import "fmt"

func main() {
	fmt.Println("tea", 2, 1800)
}
```
:::
