上一章的一笔 `Order` 是一杯茶或一个包子。柜台一天不会只有一笔，单价表也不会只有一个数字。这一章用切片存放多笔金额，用映射存放商品名到单价。茶仍是 1800 分，包子仍是 600 分。新的问题是：这两种容器的零值能不能立刻使用，以及往一张还不存在的映射里写 `"tea"` 会发生什么。

切片是一段数组的视图。它自己带着指针、长度和容量。你看到的 `[]int` 是视图，不是固定长度的数组。映射是键到值的表。声明 `var price map[string]int` 时，`price` 的零值是 nil。nil 映射可以读，读不到的键得到值类型的零值，整数就是 0。nil 映射不能写。执行 `price["tea"] = 1800` 时，运行时发现没有底层表可以放这个键，于是 panic。panic 不是返回一个错误值，是当前这段调用栈往外炸。若没有人接住，进程以失败结束，1800 不会进任何表。

`make` 负责把表造出来。`make(map[string]int)` 返回一个空的、非 nil 的映射，可以写入。`make([]int, 0, 2)` 返回一个长度为 0、容量为 2 的切片，底层数组已经留了两个整数的位置。长度是现在有几个元素，容量是在重新分配之前能放几个。字面量 `map[string]int{"tea": 1800}` 也会造出非 nil 的映射，适合键和值在写源码时就知道的情况。`make` 适合一开始是空的、稍后在循环里填的表。两种都避免了 nil 写入。

先走安全的一条。造出单价表，写入茶和包子，再读出来相加。1800 加 600 是 2400。读取用 `price["tea"]`，键存在时得到写入的整数。这一块的输出是两者之和，用来确认两次写入都落在同一张表上。

```go run expect="2400" title="make 之后才能写入"
package main

import "fmt"

func main() {
	price := make(map[string]int)
	price["tea"] = 1800
	price["bun"] = 600
	fmt.Println(price["tea"] + price["bun"])
}
```

映射的遍历次序是故意打乱的。即便你先插入茶再插入包子，`for k, v := range price` 也不保证茶先出现。这是语言为了避免程序依赖哈希次序而做的选择。好处是你不会在某一版运行时碰巧按插入序打印，换一台机器就翻脸。坏处是单价表不能直接当成菜单的显示顺序。显示顺序若要紧，就另用切片保存名字，映射只负责按名字查价。这一章的可运行块用具体的键去读，不遍历，所以 2400 是确定的。

切片这边用 `make` 指定容量。先放 1800，再放 600。长度变成 2，容量仍是 2，因为两次 `append` 都没超出预留。打印第一个元素、长度和容量：`1800 2 2`。容量写进期望，是因为 `make` 的第三个参数把容量钉死了。若你改用 `[]int{}` 再 `append`，容量按运行时的增长策略变，可能是 2 也可能更大，期望就不该写死容量。教学块把容量写出来，就是为了让 `make` 的第三个参数有可见的后果。

```go run expect="1800 2 2" title="预留两个位置"
package main

import "fmt"

func main() {
	lines := make([]int, 0, 2)
	lines = append(lines, 1800)
	lines = append(lines, 600)
	fmt.Println(lines[0], len(lines), cap(lines))
}
```

`append` 可能返回一个新的切片头。当容量够用时，它往往还指向原来的数组，只是长度加一。当容量不够时，它分配一块更大的数组，把旧元素拷过去，再写入新元素。所以 `append` 的结果必须赋回去：`lines = append(lines, 1800)`。不赋值，你手里的 `lines` 可能还是旧的头，长度没变，新元素写进了一块你再也看不到的内存。这和上一章丢掉函数返回值是同一类疏忽。切片的头是一个小结构，按值传递。函数里 `append` 之后若不把新头返回给调用者，调用者的长度不会变。底层数组在容量够的时候可能已经被写过了，于是出现「长度没变，但某个共享数组的下一格被改了」这种更难读的情况。把返回值赋回来，头和内容重新对齐。

nil 切片和 nil 映射不一样。`var lines []int` 是 nil，长度和容量都是 0。对它 `append` 是合法的，`append` 会分配第一块数组并返回非 nil 的头。下面这一块从 nil 切片开始，追加 1800，打印长度和第一个元素，得到 `1 1800`。所以「切片和映射都要 make」这句话要收窄。映射的写入需要一张已经存在的表，`make` 或字面量都能给。切片的 `append` 可以自己从 nil 开始分配。`make` 对切片的价值是你想预先定长度，或者像上面那样预先定容量，避免反复分配。不是因为 nil 切片不能用。

```go run expect="1 1800" title="nil 切片可以追加"
package main

import "fmt"

func main() {
	var lines []int
	lines = append(lines, 1800)
	fmt.Println(len(lines), lines[0])
}
```

nil 映射的写入会 panic。这一行为可以用 `defer` 和 `recover` 接住，从而在终端里看见一个确定的词，而不是让整个解释过程直接倒下。`defer` 注册一个函数，在 `main` 退出前运行。函数里调用 `recover`。若刚才发生了 panic，`recover` 返回那个恐慌值，不是 nil。我们打印 `panic`。若没有恐慌，`recover` 返回 nil，什么都不印。写入放在注册 `defer` 之后。一旦写入炸掉，后面的 `fmt.Print("wrote")` 不会执行。所以成功的输出只有 `panic` 这五个字母，不会带着 `wrote`。

```go run expect="panic" title="nil 映射写入会恐慌"
package main

import "fmt"

func main() {
	defer func() {
		if recover() != nil {
			fmt.Print("panic")
		}
	}()
	var price map[string]int
	price["tea"] = 1800
	fmt.Print("wrote")
}
```

这段能稳定出现 `panic`，是因为写入和 `recover` 发生在同一个 `main` 里，恐慌没有跨到别的协程。`recover` 只接住当前协程上的恐慌。用它来把教学示例的失败变成一行输出是合适的。用它来吞掉柜台程序里的所有失败通常不合适：恐慌被吃掉之后，程序继续，单价表却仍然是 nil，下一笔写入还会再炸。接住之后若要继续做生意，应该改用 `make` 造一张表，而不是假装写入已经成功。这一块故意不补 `make`，就是为了让输出停在 `panic` 上。正式的订单路径用前面那块 `make`。

读一个不存在的键不会 panic。`price := make(map[string]int)` 之后读 `"bread"`，得到 0。0 和「表里真的写了免费」无法区分。映射因此提供两个返回值的读法：`cents, ok := price["bread"]`。`ok` 为 false 时，这个键没出现过，0 只是零值。`ok` 为 true 时，0 才是有人写入的价格。单价表里不要让「没这个商品」和「这个商品卖 0 分」共用一个信号。茶和包子都是正数，暂时看不出这个问题。一旦出现赠品，两个返回值就有用了。

切片的下标越界也会 panic。长度是 1 时访问 `lines[1]`，和 nil 映射的写入一样是运行时失败。`append` 会增长长度，下标访问不会。先看 `len`，再按下标取。容量不是你可以合法下标的范围。容量里还没经 `append` 或切片表达式纳入长度的部分，下标碰到就会炸。`make([]int, 2)` 和 `make([]int, 0, 2)` 的差别就在这里：前者长度已经是 2，两个格子是 0，可以下标；后者长度是 0，只能先 `append`。

把订单结构体放进切片是自然的下一步。`orders := make([]Order, 0, 2)`，然后 `append` 茶和包子两笔。这一章的可运行块用 `[]int` 放金额，是为了让期望保持短数字。结构体切片的机制相同：nil 的 `[]Order` 也能 `append`，`make` 用来预留。映射若要从商品名找到整笔订单，同样要先 `make(map[string]Order)` 或写出字面量，再赋值。把 `Order` 放进映射时，取出来的是副本。改副本的件数不会写回映射，除非你把改过的结构体再赋回同一个键。这和上一章的复制是同一条规则，只是副本来自映射的取值，而不是来自 `b := a`。

[Go by Example](https://gobyexample.com/) 的切片和映射页讲了 `make` 和 `append`。[Learn Go with Tests](https://quii.gitbook.io/learn-go-with-tests) 用切片装一组需要断言的例子。这里的 2400 是两样商品的单价和，`panic` 是对 nil 映射写入的那个词。

切片表达式能取一段而不复制元素。`lines[0:1]` 和原切片共享底层数组，改其中一格，另一边看得见。这和结构体的整份复制不同。金额切片若被两个变量切出重叠的视图，改一处会改到另一处的合计。需要各自独立时，用 `append([]int(nil), lines...)` 做一份新的拷贝，再交给日志。拷贝的成本和元素个数成正比。两三个单价可以拷。一天几千笔时再考虑要不要共享视图。

映射的键必须能比较。字符串可以，整数可以，切片不可以。不要把一整个订单切片当成键。商品名当键是合适的，因为名称用 `==` 比较，相等就是同一个商品。大小写不同的 `"Tea"` 和 `"tea"` 是两个键。课程统一用小写，避免同一杯茶占两行单价。若菜单需要显示「茶」，显示名放在值里或另一张表里，键仍用稳定的 `tea`。

`delete(price, "bun")` 会删掉包子。删一个不存在的键是空操作，不会 panic。这和写入 nil 映射相反：删除对 nil 映射也是空操作，读取 nil 映射得到零值，只有写入会炸。三个操作不要记成「nil 映射完全不能用」。不能用的是赋值。删除和读取有定义。即便如此，单价表仍应在写入之前 `make`。一张明确造好的空表，和一张 nil 表，在「有没有这个键」上一样，在「能不能标价」上不一样。让表从造成的那一刻起就能写，后面的代码就不必每写一次都先判断 nil。

预留容量是性能上的选择，也是期望上的选择。知道今天最多两样商品，`make([]int, 0, 2)` 一次分配就够。不知道笔数时，从 nil 切片 `append`，让运行时按倍数增长。增长会拷贝旧元素，笔数少时无感。教学块写出容量，是为了让第三个参数出现在输出里。业务代码若没有测量过分配，不必为了「看起来专业」到处写容量。先把 nil 映射的写入避开，这比调容量重要。

把订单切片和单价映射放在同一次结账里时，先造映射，再造切片。顺序写在 `main` 的前几行，读的人先看见容器已经存在。然后循环切片，用商品名去映射里取单价。取的时候用两个返回值。没有这个名字就跳过或返回错误，不要把 0 分乘上件数当成一笔真实的茶。映射在循环期间不要再写入，以免你一边遍历一边改表。Go 允许在某些条件下改映射，但遍历中插入会让人说不清这一轮会不会看见新键。教学例子把写入放在遍历之前，2400 只来自两次明确的赋值。

容量和长度再对着订单说一次。`make([]Order, 2)` 得到两张零值订单，长度已经是 2，可以直接改 `orders[0].Qty`。`make([]Order, 0, 2)` 得到空切片，必须 `append` 才能有第一张单。前者适合「我知道有两笔，先占位」。后者适合「我还不知道有没有，来一笔加一笔」。占位的零值订单会被 `Total` 拒绝，所以占位之后要立刻填件数和单价，不能把零值留到结账。空切片则根本没有那张会被拒绝的单，直到 `append`。选哪一种，看零值会不会混进合计。

## 小结

`make` 造出可写的映射，也用来给切片预留长度或容量。字面量同样能造出非 nil 的容器。nil 切片可以 `append`，nil 映射一写就 panic。读缺失的键得到零值，要用第二个布尔分清「没有」和「真的是 0」。下一章用一个小接口描述「能报出金额」，茶和包子各自实现它。
