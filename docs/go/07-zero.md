声明那一章见过整数 0、空串和 false。结构体那一章见过复制。切片那一章见过 nil。这一章把它们收成一句：零值是可用的起点，不是「这里没有东西」的空洞。一张 `var o Order` 的订单，名称是空串，件数是 0，单价是 0。你可以读它，可以把它交给只读的方法，可以得到金额 0。它不是 null。语言没有让结构体变成「不存在」。

这是 Go 对默认状态的选择。每个类型都有一个不需要额外初始化的值，声明之后立刻合法。好处是你少写一遍构造函数，切片、结构体、布尔、整数都遵守同一句话。代价是「未设置」和「设置为零」在值类型上看起来一样。订单件数为 0，可能是客人还没说数量，也可能是一张被明确清空的单。若业务要区分这两种，零值本身不够，要加字段或改用指针。不要为了模拟 null 去禁止零值。先问清 0 在这张单上是不是一种合法的业务状态。

空订单的金额方法可以照常工作。`Line` 用值接收者，件数乘单价，都是 0，结果是 0。打印 0。这个 0 是算出来的，说明方法没有要求调用者先 `new` 一下。若 `Line` 在内部假设名称非空，它就会在零值上失败，零值就不再可用。写方法时让零值走得通，哪怕走通的结果是 0。需要拒绝空单时，用上一章的 `error` 返回 `"qty"`，那是业务规则，不是类型系统缺少 null。

```go run expect="0" title="零值订单的金额"
package main

import "fmt"

type Order struct {
	Name  string
	Qty   int
	Cents int
}

func (o Order) Line() int {
	return o.Qty * o.Cents
}

func main() {
	var o Order
	fmt.Println(o.Line())
}
```

指针的零值才是「没有订单」。`var p *Order` 等于 nil。它不指向一张字段为零的订单，它根本不指向。读取 `p == nil` 可以得到 true，并且这个判断本身不崩溃。崩溃发生在你顺着 nil 去取字段的时候。所以「可能还没下单」用指针，使用前先判断。判断通过再读 `Qty`。下面这一块在 nil 时打印 `nil`，不访问字段。

```go run expect="nil" title="指针可以缺席"
package main

import "fmt"

type Order struct {
	Qty int
}

func main() {
	var p *Order
	if p == nil {
		fmt.Print("nil")
	}
}
```

有人会写 `if p == nil { p = &Order{} }`，把缺席变成一张零值订单，然后再填茶的单价。这也合理：边界上用 nil 表示还没开始，开始之后就保证指针非 nil，后面的代码可以大胆访问字段。转换放在一处。到处都写 `if p != nil` 说明指针的缺席渗透进了所有逻辑。柜台的主路径应该握着一张真实的订单，nil 只出现在「还没分配」的那个变量上。

nil 切片再次和 nil 映射对照。`var lines []int` 的长度是 0，`append` 合法。`var price map[string]int` 可以和 nil 比较，一写就 panic。零值「可用」因此不是「所有操作都可用」。可用的是那些不需要底层结构就已经有定义的操作：切片的长度、切片的追加、结构体字段的读取、映射的缺失键读取。不可用的是那些必须有底层结构的写入：映射赋值、向 nil 指针取字段、向 nil 通道发送。通道的 nil 发送会永远堵住，这一章不把发送写进可运行块，免得 Run 停住。只打印通道是不是 nil。

```go run expect="true 0" title="通道缺席切片为空"
package main

import "fmt"

func main() {
	var ch chan int
	var lines []int
	fmt.Println(ch == nil, len(lines))
}
```

`true 0` 里的 true 是通道的缺席，0 是切片的长度。两者都是零值，打印出来的含义不同。读终端时要对照类型。布尔 true 在这里表示「是 nil」，不是表示「付款成功」。上一章的 `paid` 零值是 false。同一个「零」在布尔上是 false，在指针和通道上是 nil，在切片上是长度 0 的 nil 切片。记零值就是记每个类型的这个默认点。

字符串的零值是空串，空串可以和 `"tea"` 拼接，得到 `"tea"`。可以取长度，得到 0。不必先让它指向一块缓冲区。这使订单名称可以先留空，等客人开口再赋值。空串参与拼接不会 panic。若你把名称换成指针 `*string`，才能表达「名称这个字段还没提供」，但每一次打印都要判 nil。多数订单用空串就够了：打印出来什么都没有，界面上显示空白，程序不崩溃。

布尔的零值 false 适合「还没付款」。付款是一个会从 false 变成 true 的标记，默认未付，符合零值。不适合用布尔零值表达的，是三态：未知、已付、未付。两态的布尔没有「未知」。未知要用另一个类型，或者用指针。小店的练习只有未付和已付，false 和 true 够用。不要为了看起来像数据库的 NULL 把每个布尔都换成指针。

把零值订单填成茶，是赋值而不是「激活」。`o.Name = "tea"`，`o.Qty = 2`，`o.Cents = 1800` 之后，`Line` 返回 3600。填之前的 0 和填之后的 3600 是同一个变量的两个时刻。不需要先销毁一个 null 再构造对象。这也是值类型的好处：生命周期就是变量的作用域，没有单独的分配步骤。需要在很多地方共享同一笔、并且共享修改时，再取地址，变成指针。共享是额外的决定，不是默认。

方法写在值上时，nil 指针仍可能被调用，只要你是通过接口或直接对指针调用、而方法体不访问字段。这种调用很容易让人以为 nil 也「可用」。一旦方法体写下 `o.Qty`，nil 接收者就会 panic。金额方法会访问字段，因此只对真正的 `Order` 值调用，像第一块那样。不要把 `(*Order)(nil)` 放进接口再调用 `Line`。

零值还影响比较。两张什么都没填的订单，`==` 为真。它们相等，因为字段都相等，不是因为它们共用一个身份。柜台若用零值订单当映射的键，所有空单会落在同一个键上，互相覆盖。空单不适合当键。等它有了名称和件数，再拿去当键，或者干脆用一个整数订单号当键。订单号的零值 0 通常留出来表示「还没编号」，真正的号从 1 开始。这样 0 又变成了有含义的哨兵，和「未填」重新对齐。哨兵是约定，不是语言强制的。你要在计价函数里拒绝编号 0，就像拒绝件数 0。

[Go by Example](https://gobyexample.com/) 在各种类型的页里都会碰到零值。[Learn Go with Tests](https://quii.gitbook.io/learn-go-with-tests) 依赖零值让测试里的空结构体有确定行为。这里的确定行为是金额 0，以及指针打印出 `nil`。

切片、映射、指针、通道、函数、接口，这六样的零值都是 nil。它们的 nil 含义各不相同，却共享「还没有指向具体东西」这一句。函数变量是 nil 时调用会 panic。接口是 nil 时调用会 panic。通道是 nil 时发送和接收会永久等待。映射是 nil 时写入会 panic。指针是 nil 时取字段会 panic。切片是 nil 时长度为零，追加却合法。六句话不能合成一句「nil 都不能用」。订单代码里最常碰到的是结构体值、切片和映射。结构体值没有 nil。切片的 nil 可以当空的订单列表。映射的 nil 不能当空的单价表，空的单价表要用 `make`。

把「有用的零值」用在延迟初始化上。`var price map[string]int` 先留着，第一次写入前若发现是 nil 再 `make`。这样没有订单的路径不会分配表。代价是每一处写入都要记得检查，漏一处就 panic。小店的单价表在进程开始就 `make`，写入点不必重复检查，分配的那一张空表小到可以忽略。延迟初始化适合很少用到的大结构。茶和包子的表用不到这个技巧。知道技巧，是为了读别人的代码时认出 `if m == nil { m = make(...) }` 在防什么。

零值也让测试好写。一个空的 `Order` 不用构造函数就能当输入，`Line` 应返回 0。一个 nil 切片当订单列表，长度是 0，合计是 0，循环一次都不进。这些输入不用模拟「未初始化的垃圾内存」。语言保证它们是零。测试因此只断言业务：空单的金额是 0，而不是断言内存被清过。

整数溢出会绕回，零值讨论到这里要补一句。件数和单价都是 `int`，两杯茶远离溢出。若有人把分写成很大的整数再相乘，结果可能变成负数，而 `err` 仍是 nil。零值不是溢出。溢出是运算的回绕。需要时改用 `int64`，并在相乘前看件数是否超过某个上限，超过就返回错误。这一章的 0 来自未赋值，不是来自绕回。看到负数金额时，先看有没有人写了负的单价，再怀疑溢出。课程里的数字都很小，负数只来自你明确写上的符号。

把零值订单交给 `fmt.Println` 会打印出一对花括号和零。那种字形依赖 `fmt` 的默认格式，字段一增加，字形就变。课程改打印 `o.Qty` 这种单个整数，就是为了让零值的证据是字符 `0`，而不是一串格式。你在调试时可以临时打印整笔订单，看完删掉，不要把整笔的默认格式写进期望。

空串名称和 0 单价同时出现时，小票上像一行空白。界面可以显示「未填写」，判断条件写在界面旁边：`o.Name == ""`。不要用 `len(o.Name) == 0` 以外的技巧去猜。空串的长度就是 0，两者等价。名称若允许用空格表示「还没想好」，那和空串不同，长度不是 0。课程不把空格当成名称。茶就是 `tea`，没填就是空串。

指针切片 `[]*Order` 的元素可以是 nil，长度却不是 0。`make([]*Order, 2)` 得到两个 nil 指针。这比 `var o Order` 更危险，因为容器看起来有两笔，每一笔其实缺席。循环时要先判断元素是不是 nil，再访问字段。需要固定两笔时，用 `[]Order` 的值切片，元素一定是结构体。需要稀疏的缺席时，才用指针，并在文档里写明 nil 表示这一格没有订单。

布尔零值 false 放在 `paid` 上，表示默认未付款。一张零值订单因此同时是「没名称、没件数、没单价、没付款」。四个维度一起为零，正好是一张还没开始的单。开始填写时逐项赋值，不必一次性用构造函数把四个维度都变成「非零才算活」。付款可以仍是 false，而茶的件数已经是 2。零值允许这种部分填写。部分填写的金额仍然要被 `Total` 检查，未付款不妨碍先把金额算出来给客人看。

把零值说成「可用」，包括把它传给函数。`func show(o Order)` 接受零值订单不会崩溃，函数里读到的件数是 0。调用者不必先 `new`。需要拒绝空单的函数应返回 `error`，而不是在类型系统里取消零值。取消不了，语言没有给结构体一个额外的空状态。

## 小结

`var o Order` 是一张可以算金额的空单，结果是 0。`var p *Order` 是没有单，使用前要判断 nil。nil 切片有长度 0 且能追加，nil 映射和 nil 通道不能拿来发送或写入。下一章用嵌入把商品放进订单，而不是做一层父类。
