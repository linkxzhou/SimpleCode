窗台上有一支便宜的温度计。某个下午它被记了五次：18、21、36、22、19，单位都是摄氏。36 那一次不是房间忽然变成了桑拿，是阳光直接打在金属头上。后面每一章都还用这五个数，因为换一套数据会把注意力从语言机制上挪走。这一章先不分支、不循环、不申请内存，只把它们加起来，并弄清这次加法要经过谁的眼睛。

点 Run 之后并不是有一个解释器从第一行开始念。源码先被 clang 编译成目标文件，再链接成 wasm，然后那个 wasm 才作为新进程执行。编译或链接的退出码不是 0 时，进程根本不会走到 `printf`。终端里出现的是诊断，不是你以为已经算好的 116。所以「输出不对」要先分成两类：程序没诞生，以及程序诞生了但印出来的不是那个数。改期望文字救不了第一类。

这条编译命令是直接把 `-cc1` 和 `-Werror` 交给 clang 8，目标三元组写成 `wasm32-unkown-wasi`。拼写看起来像少了一个字母，它却是这份运行时实际在用的名字。不要为了教程去改它，改了就对不上级别已经放进抽屉的编译器和 sysroot。`-Werror` 的含义很窄，也很硬：凡是这份前端默认会发出的警告，都变成错误，错误让这一阶段失败。格式串和实参对不上、`main` 的返回类型不是 `int`、在 `if` 的条件里写赋值、从函数里返回局部变量的地址，都落在默认会响的那一组里。它们响的时候，后面的链接和运行都不会开始。

未使用的局部变量要单独说，免得把口号说得比编译器更满。clang 8 里 `-Wunused-variable` 默认不开启，而这里又没有走会替你加上 `-Wall` 的驱动程序，所以「声明了 `int spare = 36` 却从不读它」在这个抽屉里未必让编译失败。课程仍然不留下这种名字。原因有两层。一层是移植：同一份文件拿到打开 `-Wall -Werror` 的 clang 上会停住，而那才是多数人自己机器上的习惯。另一层是这五个读数本身。你若算出了和却没把它交给 `printf` 或下一个表达式，终端里的空白并不证明房间是 0 度，只证明这次测量在源码里丢了。编译器的沉默不是保留它的理由。

`main` 必须返回 `int`。写成 `void main(void)` 时，`-Wmain-return-type` 会在 `-Werror` 下直接失败。返回的那个整数是进程的退出状态。抽屉用它区分「跑完了」和「中途放弃」。我们在末尾写 `return 0`，不是因为 C99 对 `main` 有一个特殊规定、允许从末尾掉下去时相当于返回 0。那个特殊规定只覆盖 `main`。你在别的函数里让控制走到右花括号外面，结果不是 0，而是未定义行为，clang 也会对非 `void` 函数少了 `return` 发出诊断。养成一种写法，比记住哪一个函数享有豁免更不容易在第八章的失败分支里漏掉状态。

参数列表写成 `(void)` 而不是 `()`。在 C 里，空括号是旧式声明，意思是「参数先不说」，不是「没有参数」。`(void)` 才是没有参数。这支温度计的程序不从命令行读位置参数，抽屉也不会替你塞 `argv`。把「没有参数」写死，以后若有人误写成 `main(18)` 这种调用，编译器才有资格说话。

整个程序只能是一个源文件。没有第二个 `.c`，也没有你自己的头文件可以另存。`#include <stdio.h>` 展开的是 sysroot 里的标准头，不是项目里的另一个翻译单元。想把「求平均」放进 `avg.c` 再链接，这条流水线做不到：它固定编译 `/program` 这一个入口。头文件护符、`extern` 跨文件声明，都留给真有多文件的工程。在这里把函数写在 `main` 上面同一个文件里就够了。

也没有线程，没有网络。不要包含 `pthread.h` 再创建一条去读温度的线程，这份 WASI 预览和链接参数里没有可用的线程实现。不要包含套接字相关的头去连接一台气象服务器，运行时没有网络出口。做不到的事用不能运行的块记一笔，免得后面某一章为了凑例子去改编译参数。输入如果需要，来自标准输入；这一章的三个例子连标准输入都不用，五个数写在源码里。

`printf` 是这五个数离开进程的方式。格式串里的 `\n` 要自己写。返回值我们这一章不检查，因为这三个例子只印常量表达式，失败的方式几乎只剩下标准输出本身坏了，而那不是温度计算的问题。从读入和写文件的那几章起，返回值会变成控制流的一部分。期望是输出的子串：印出 `116` 时，后面跟着换行也好，前面偶尔多一行说明也好，只要这三位数字还在。不要为了多出来的空行去改期望。

下面先把五个字面量加在一起。没有变量，是为了让你看见 116 来自加法，不来自某个上次运行留下的全局状态。每次 Run 都是新进程，全局变量不会活到下一次点击。

```c run expect="116" title="五次加总"
#include <stdio.h>
int main(void) {
  printf("%d\n", 18 + 21 + 36 + 22 + 19);
  return 0;
}
```

116 可以心算复核：18 加 21 是 39，加 36 是 75，加 22 是 97，加 19 是 116。若终端里是 80，优先怀疑漏写了 36，而不是怀疑 `printf` 会随机少加一次。36 是这组数据里唯一的异常点，后面用它做阈值，正是因为它离其余四次那么远。把它漏掉，平均值会显得房间一直很凉快，判断就整个偏了。

下一步把和放进名字。名字的价值不是短，五个加数并不长，价值是后面你可以先打印和，再打印别的，而不必把同一串加法复制两遍。复制会漂移：其中一处改成去掉阳光读数，另一处忘了改，两个数就不再描述同一次下午。

```c run expect="116" title="和有名字"
#include <stdio.h>
int main(void) {
  int sum = 18 + 21 + 36 + 22 + 19;
  printf("%d\n", sum);
  return 0;
}
```

`sum` 被读了，所以它不是前面说的那种丢掉的测量。若你在调试时又声明一个 `int count = 5` 却不打印、不参与运算，就把它删掉，不要注释掉留在块里充门面。注释掉的代码不会警告，但会让下一章的读者以为次数已经放在变量里。

第三次只拿出阳光那一次。它仍然是 36，和 116 是同一组数，不是新传感器。把异常点单独印出来，是为了确认格式串 `%d` 配的是整数，而不是配一段中文说明。说明文字要用 `%s`，而且参数必须是字符串。这一区分在下一章会变成编译错误的主要来源，这里先把两种格式都走对一次。

```c run expect="36" title="阳光那一次"
#include <stdio.h>
int main(void) {
  int sun = 36;
  printf("%d\n", sun);
  return 0;
}
```

```c norun title="这份运行时做不到的"
#include <stdio.h>
int main(void) {
  /* 不要写第二个源文件再链接。
     不要 pthread_create，也不要连接网络。
     void main(void) 会在 -Werror 下失败。 */
  return 0;
}
```

只读的那一块故意不能运行。它旁边的话是限制，不是待办。把 `pthread_create` 或第二份源文件的声明抄进能运行的例子，不会得到一个更完整的温度计，只会得到一份在这个目标上过不了编译或链接的文件。

再看一个容易误判的成功。下面这段若删掉 `printf` 那一行，`sum` 仍然算了 116，进程仍然可以 `return 0`。退出码是 0，终端是空的。空终端不是「房间温度为零」，是你没把结果送出进程。`-Werror` 不会替你发现这件事，因为 `sum` 如果完全不出现在任何表达式里才会涉及未使用变量，而只要它出现在一条被优化掉之前仍算「使用」的语句里，讨论就变味了。可靠的做法是：你要交给读者的每一个数，都出现在 `printf` 的参数里，或出现在决定打印什么的条件里。

五个数都是 `int` 能装下的。这一章不讨论整数除法，因为 116 除以 5 的商并不是 23.2，那是类型章的主题。若现在就把 `sum / 5` 印出来并写成「下午的平均温度」，你会在还没弄清类型之前先对家人撒一个偏凉的谎。先记住和是 116，次数是 5，异常点是 36。

编译失败时怎么读。诊断的第一行通常带有源码位置和警告的名字，例如格式类或 `main` 的返回类型。先看名字，再看它指着的那一个参数。不要同时改格式串、改数值、改返回值。一次只动诊断指着的地方，再用工具栏的 Run 看新结果。点代码块上的 Run 会把编辑器里的草稿盖回文档中的示例，适合重来；工具栏的 Run 才保留你的修改。

这套流程也解释了为什么示例都写得这么完整：每个可运行块都有自己的 `#include` 和 `main`，因为每个块都会被单独抽出来编译，而不是拼进一个大工程。你在块的外面写的散文不会被编译。你在块里面写的注释会被编译器跳过，但汉字注释没有问题，源码按字节保存，clang 接受 UTF-8。

取舍放在这里说清楚。把警告当成错误，会让教学示例变笨：你不能留一个「先声明以后再用」的变量穿过好几次编辑。好处是失败发生在有行号的时候，而不是发生在你把 36 误印成地址、屏幕上出现一串毫无关系的整数的时候。C 的 `printf` 在很多编译器上对格式错误沉默，然后按错误的宽度去读栈或寄存器。这个抽屉选择提前失败。提前失败的代价是你要学会读诊断；收益是五个温度不会在一种「看起来跑完了」的状态下被印成别的东西。

单文件也是取舍。真实的传感器固件会把驱动、滤波、通信分成多个翻译单元，否则一个文件会长到无法审查。这里的目标是看清语言，不是模拟固件的目录。把模块化的愿望压到一个文件里，函数仍然可以有边界，边界靠静态函数和参数，不靠链接器。等你离开抽屉，再把这些函数搬进各自的文件，那时候没有 `-cc1` 这条固定参数，构建脚本才是你的责任。

进程模型同样是取舍。每次运行都清空，调试时不会被昨天写到一半的全局数组污染，这是优点。缺点是你不能在这一章把 116 写进文件，指望下一章打开它。文件那一章会说明，即便写了，也只在同一次进程里可见。跨章节的记忆只能写在散文和源码的字面量里，所以这五个数要反复出现，不能换。

## 小结

这一章之后，先看退出发生在哪一阶段。编译诊断意味着 `printf` 没有执行，去改格式、`main` 的返回类型或那条不该出现的赋值，而不是去改期望子串。`main` 写成返回 `int` 的 `main(void)`，并用 `return 0` 把正常结束写在源码里。做不到的线程、网络和多文件不要塞进可运行块。

未使用的局部变量在这份 `-cc1 -Werror` 上不一定响，但仍然不要留。你要交付的数是 116 和那个单独的 36，它们必须被打印。下一章关心的是格式串为什么会在编译期就拒绝错误的参数，以及多一个、少一个参数时诊断怎么说。五个读数继续用这一组。

## 练习

只打印阳光读数和第一次读数的差。36 减 18，结果应当是 18。不要另起一组温度，也不要打印解释性的句子，这样期望子串不会和说明文字缠在一起。差本身用减法表达式或一个 `int` 都可以，但这个 `int` 必须出现在 `printf` 里。

::: answer 参考答案：温差
```c run expect="18" title="参考答案"
#include <stdio.h>
int main(void) {
  int early = 18;
  int sun = 36;
  printf("%d\n", sun - early);
  return 0;
}
```
:::

打印最后一次读数与阳光读数的和，也就是 19 加 36。这道题用来确认你写的是加法而不是把两个数拼成字符串。若格式用错，编译会停住，终端里不会有 55。

::: answer 参考答案：两端相加
```c run expect="55" title="参考答案"
#include <stdio.h>
int main(void) {
  printf("%d\n", 19 + 36);
  return 0;
}
```
