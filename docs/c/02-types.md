格式串配平之后，116 已经能稳定地离开进程。接下来的问题是：这五次读数的「平均」到底是哪一种运算。18、21、36、22、19 的和是 116，次数是 5。若按日常的温度报告，你会想要 23.2。C 不会从 116 和 5 这两个 `int` 里替你变出小数。两个整数相除，结果仍是整数，小数部分被丢掉。丢掉的方向在现行标准里是向零截断，所以 116 / 5 得到 23，不是 24，也不是 23.2。

这不是缺陷，是两种指令。整数除法在处理器上产出商和余数，C 的 `/` 在操作数都是整数时选择商。浮点除法是另一套运算，结果是近似的实数。语言没有理由在你没要小数的时候偷偷做浮点：整数除法更快，结果可重复，也符合「类型决定运算」这条主线。代价是物理量的平均值很容易被算凉。23 比四次正常读数里的三次都高，却仍然把阳光那一次的热量抹掉了一大截。你拿 23 去跟阈值 30 比较，会觉得下午从未越线；拿 23.2 比较，结论一样，但你不该用错误的数碰巧得到正确的结论。先把两个商都印出来，让它们在终端里分开站着。

```c run expect="23" title="整数商"
#include <stdio.h>
int main(void) {
  int sum = 18 + 21 + 36 + 22 + 19;
  int n = 5;
  printf("%d\n", sum / n);
  return 0;
}
```

`sum` 和 `n` 都是 `int`，`sum / n` 的类型就是 `int`。把这个结果交给 `%d` 是对的。若你以为自己已经得到了 23.2，只是打印时少了小数，那是把格式和运算搞反了。`%.1f` 不能从整数表达式里挖出被丢掉的 0.2，因为 0.2 在除法完成时已经不在结果里。余数还在，用 `%` 可以拿到：116 % 5 是 1。余数说明截断确实发生了，但余数不是小数部分的写法。1 除以 5 才是 0.2，那又是一次新的除法，并且至少有一个操作数得是浮点。

把其中一个操作数写成浮点字面量，运算就换成浮点除法。116.0 的类型是 `double`，5 会被转换成 `double`，然后再除。`printf` 的 `%f` 期望 `double`。`float` 传进可变参数时会提升成 `double`，所以教学例子直接用 `double` 字面量，少一次心智转换。

```c run expect="23.2" title="浮点商"
#include <stdio.h>
int main(void) {
  int sum = 18 + 21 + 36 + 22 + 19;
  printf("%.1f\n", sum / 5.0);
  return 0;
}
```

`sum / 5.0` 不是 `sum / 5` 的打印变体。`5.0` 改变了运算种类。`%.1f` 只负责把结果修约到一位小数。23.2 在二进制浮点里并不能精确表示，但这一位小数的修约恰好写回 23.2，所以终端上的字形是稳定的。不要据此认为所有的一位小数都「刚好」。若你以后把阈值写成 `0.1` 累加十次，误差会露面。温度这组数碰巧友好，不能当成浮点永远精确的证据。

取舍是：整条流水线保持 `int`，用十分之一度为单位存储，18.0 存成 180，36 存成 360，平均时仍用整数除法，最后再决定怎么显示。这样没有二进制小数误差，比较和排序也简单。代价是你必须自己记住缩放，一旦有人把 360 当成摄氏去跟 30 比较，阳光读数会变成荒谬的高温。另一条路是尽早用 `double` 保存摄氏，显示自然，代价是相等比较不可靠，也不该用 `==` 判断「是不是 23.2」。这组教材选择在示例里两种都印，让截断可见，而不是替你选一种存储。

宽度是另一件必须在这个目标上看见的事。抽屉把程序编译成 wasm32，数据模型是 ILP32：`int`、`long` 和指针都是 4 字节，`long long` 是 8 字节，`short` 是 2，`char` 是 1，`float` 是 4，`double` 是 8。从 64 位 Linux 过来的人会以为 `long` 比 `int` 宽，能当「更安全的整数」来装平均值。在这里不能。`long` 装不下 `int` 装不下的和。五个温度的和远小于 20 亿，用 `int` 足够；换 `long` 不增加范围，只增加你对 `%ld` 的依赖。若真要更宽的整数，用 `long long`，格式用 `%lld`。格式和宽度必须一起改，只改其中一个，`-Wformat` 会让编译失败。

```c run expect="4" title="long 的宽度"
#include <stdio.h>
int main(void) {
  printf("%d\n", (int)sizeof(long));
  return 0;
}
```

`(int)sizeof(long)` 是为了用 `%d`。`sizeof` 的结果类型是 `size_t`，在这个目标上是 32 位无符号整数。直接用 `%d` 配 `size_t` 会格式不匹配。转换之后，打印的是 4 这个有符号整数。在你自己的 64 位机器上，同一段源码常常印出 8。那不是抽屉坏了，是数据模型不同。写温度程序时不要把「我笔记本上是 8」写进注释当成这里的事实。

字符和字节的分界比 `long` 更容易在中文上爆开。C 的字符串是以空字符结尾的字节序列，不是Unicode 标量值的数组。`strlen` 从指针指向的第一个字节数到空字符为止，空字符本身不算。`"你好"` 两个汉字，UTF-8 各占 3 个字节，一共 6。空字符另算，所以 `sizeof "你好"` 是 7：六个内容字节加上结尾。`sizeof` 认得的是字面量这个数组的总长度，`strlen` 认得的是「到结尾标记为止的内容」。两个数都对，它们回答的不是同一个问题。

```c run expect="6" title="你好的字节"
#include <stdio.h>
#include <string.h>
int main(void) {
  printf("%d\n", (int)strlen("你好"));
  return 0;
}
```

若用这个 6 去给标签居中、去切第一个字，你会切在第一个汉字的中间。切掉三个字节才是一个汉字的边界，而 `strlen` 不会告诉你边界在哪。它也不应该告诉你：标准库的这条函数承诺的就是字节，好让没有 Unicode 表的嵌入式环境也能链接。取舍很清楚。把字符串定义成字节缓冲，发送、拼接、和 `%s` 对齐都简单，也不需要一份 Unicode 数据表进 wasm。代价是「几个字」必须另写算法，或者干脆不要在 C 里做字形排版。温度计的单位若显示成「摄氏」，缓冲至少要装下 6 个内容字节再加空字符，写成 4 个「字符」的数组一定会短。

`char` 是整数类型，宽度 1 字节，能不能装负数由实现决定。这个目标上用来放摄氏字母 `C` 很合适，用 `char` 去装 36 这个温度也可以，因为 36 落在 0 到 127 里。不要用 `char` 去装和 116 以上还会继续长的累加器。一个字节的范围很小，五次读数的和已经 116，再加一个下午就会绕回。绕回是模运算，不是饱和，终端里会突然出现负数或很小的正数，看起来像探头坏了。累加用 `int`。

布尔在这门语言里不是独立的魔法。`stdbool.h` 里的 `bool` 是整数。零为假，非零为真。温度 0 如果出现，它作为条件是假，作为摄氏却是一次真实的结冰读数。后面写 `if (reading)` 会把 0 度吞掉。用 `if (reading >= 30)` 这种比较，不要用读数本身当条件。这一句先放在类型的上下文里，因为坑来自「真假也是整数」，不是来自分支语法。

转换要显式才不容易骗自己。`(double)sum / n` 和 `sum / n` 不同，也和 `sum / 5.0` 相同种类。把浮点平均再转回 `int`，截断会再次发生，23.2 变回 23。你若在日志里同时留两种，后面的人才能看出你是故意丢掉小数，还是根本没做过浮点除法。不要只留 23，然后在散文里口头说「大概二十三度多一点」。源码里没有的小数，复核的人不会替你补。

截断会在后续运算里继续传播。先除后乘，`(116 / 5) * 5` 得到 115，不是 116。少掉的 1 就是余数，它没有被乘回去。若你用这个结果去和原始的和比较，会以为加法本身不稳定。不稳定的是运算顺序。先乘后除在这组数上可以整除时才安全；116 乘 5 再除以 5 能回到 116，是因为中间积没有溢出。五个小温度不会溢出 `int`，更大的累计仍要先想溢出再想结合律。整数没有「先除一下再乘回来等于没除」这种恒等。

无符号是另一条容易和温度符号搞混的路。`unsigned` 的除法没有向零和向负无穷的争论，因为它没有负数。探头若只报告零上的摄氏，无符号装得下。可是差值会穿帮：用无符号计算 18 减 21，结果不是 -3，而是绕回到一个很大的正数。终端里突然出现几十亿，像探头爆炸，其实是模运算。午后的降温是这组数据里真实发生的事，36 回到 22，22 回到 19，差值必须能是负的。累加与差值都用有符号的 `int`。无符号留给字节计数和 `size_t`，不要留给会下降的温度。

`char` 是否带符号由实现决定。36 落在两种 `char` 都能表示的范围内，用它暂存一次读数，数值不会变。若某次错误把 `char` 当成累加器，超过 127 之后，带符号的 `char` 会变成负数，不带符号的会继续到 255 再绕回。两种都不是饱和。饱和才像传感器「顶到量程」，C 的整数溢出不是饱和。需要顶到量程时，要自己写比较：超过 30 就记 30。那是控制流和指针章里的封顶，不是类型自动提供的。

转换的优先级也值得在除法旁边放一句。`sum / 5 * 1.0` 先做整数除法得到 23，再变成 23.0。小数点出现在乘号右边，救不回已经丢掉的余数。要浮点，就让浮点出现在除法发生的那一侧：`sum / 5.0` 或 `(double)sum / 5`。阅读时从左到右看运算符和操作数的类型，不要只看最后一次 `printf` 用了 `%f` 还是 `%d`。格式是最后一步，类型在它之前已经决定了商。

再看一次这五个数的浮点路径。18、21、36、22、19 相加得到的 116 可以精确放进 `double`，除以 5 之后 `%.1f` 修约成 23.2。把每一次先除以 5 再累加，次序不同，中间的二进制近似也可能不同。这组数很小，两条路在一位小数上仍会相遇。相遇不是许可。报表若规定「先求和再除」，源码就要先求和再除，不要为了少写一个变量而拆成五次增量。拆开之后，读者无法对上 116 这个已经反复出现的和。

## 小结

116 和 5 都是 `int` 时，商是 23，向零截断，余数是 1。写成 `5.0` 才做浮点除法，`%.1f` 印出 23.2。这是两次运算，不是两种打印。在这份 wasm32 上 `long` 也是 4 字节，它不会比 `int` 更适合当累加器；更宽要用 `long long` 并配 `%lld`。

`"你好"` 的 `strlen` 是 6 个字节，`sizeof` 那个字面量是 7。库函数数的是字节，不是汉字个数。用 6 去切字符串会切进字的内部。下一章用分支和循环在同一组读数上找阳光那一次，比较用关系运算符，不用读数本身冒充真假。

## 练习

印出 116 除以 5 的余数。用 `%`，格式用 `%d`。余数应当是 1。不要打印商，免得和余数挤在同一行里分不清。

::: answer 参考答案：余数
```c run expect="1" title="参考答案"
#include <stdio.h>
int main(void) {
  int sum = 18 + 21 + 36 + 22 + 19;
  printf("%d\n", sum % 5);
  return 0;
}
```
:::
